# Research: what mason should use for browser use

*Prepared 2026-11-01. All claims sourced to repo files, LICENSE files, OpenAPI specs, or official docs. Where a claim is my reading of code rather than a statement in docs, it is marked **[inference]**.*

**Context assumed:** mason is a TypeScript/Node 22 headless personal-agent backend. The agent runs in a long-lived "tool machine" container; the server drives it over an RPC env daemon; integrations are separate services that lend MCP tools or fire signed events. Single operator, self-hosted. So the browser layer is *one* integration among several, and anything that wants to own the agent loop is a bad fit.

---

## Summary

Nothing in the candidate list is a drop-in "self-hosted browser service with session API + CDP + live view + profiles" *except* **steel-dev/steel-browser** (Apache-2.0, `POST /sessions`, CDP `websocketUrl`, interactive screencast viewer, `persist` + `userDataDir`). Its two real caveats are that self-hosted runs one session at a time and that profiles/credential vaults are a cloud feature. **kernel/kernel-images** is a genuinely good *browser box* (Apache-2.0, WebRTC live view, `/computer/*` + `/playwright/execute` HTTP surface) but ships **no session API** — `openapi.yaml` has no `/sessions`, so container orchestration is yours to write, and its MCP server is hosted-only. **browserless** is disqualified on licensing (SSPL-1.0 or commercial), **neko** is a WebRTC remote-desktop with no CDP and a guest-mode browser, and **KasmVNC** is a VNC server (GPL-2.0), not a browser service. For credentials, the only unattended-safe path is a `bw`-driven sidecar broker that fills via Playwright/CDP inside the browser process and returns only a status to the model — with several hard failure modes (master password still required to unlock; no re-prompt enforcement in the CLI; SSO/Key-Connector orgs can't decrypt from the CLI at all).

### Flags

- **Hosted-only despite looking OSS: kernel.** `kernel/kernel-images` is the *image*, not the service. `README.md` says it plainly: "This repo powers our hosted services." The `server/openapi.yaml` has 40+ endpoints and no `/sessions`; the CDP proxy on `:9222` is a per-container proxy, not a per-session router ([AGENTS.md](https://github.com/kernel/kernel-images/blob/main/AGENTS.md): "CDP proxy on port 9222 routes ALL WebSocket connections to the browser-level endpoint"). The MCP server is hosted with OAuth. You can absolutely self-host the image, but then *you* are the control plane.
- **Hosted-only despite looking OSS: browserbase.** Their OSS is Stagehand (a library) and an archived MCP server. There is no server component to run.
- **License forbids/charges for hosted or commercial use: browserless.** SSPL-1.0 §13 is the MongoDB-style "if you offer it as a service, release your whole stack" clause, and the LICENSE file itself says closed-source commercial use requires purchase. For a single-operator internal tool this is *probably* survivable, but it is an avoidable legal question, and it also gates features: their own comparison table lists "Live debugger: **No**" for Open Source ([docs](https://docs.browserless.io/enterprise/open-source)).
- **Copyleft worth noting: KasmVNC (GPL-2.0), and neko is Apache-2.0 but KasmVNC-based images may pull in more.** KasmVNC is a VNC server, so shipping it as a separate process in a container image is the normal pattern; linking/modifying it into mason is not.

### Resource cost (what is documented vs. not)

- Kernel: "The image requires at least 8gb of memory" for the headful build ([README](https://github.com/kernel/kernel-images)); hosted headful takes "8 GB or 16 GB", headless "from 1 GB up to 4 GB" ([Create](https://www.kernel.sh/docs/introduction/create)).
- Everything else: no published per-session numbers for Steel, Browserless, or Neko in their repos. Don't let anyone quote you a number. The structural fact that matters is **one browser process per session** for Steel/Browserless/playwright-mcp, and **one container per session** for Kernel/Neko/neko-rooms.

## 2. session / handoff — can a human take over the *same* live session?

Yes for several candidates, but only two have a real *protocol*.

| Candidate | Mechanism | API | Exclusive lock / arbitration? |
|---|---|---|---|
| **neko** | Native design. One session holds "host" control; another session can *request* it and the current host gets a `CONTROL_REQUEST` event | `POST /api/room/control…` → `controlRequest`: if a host exists it sends `event.CONTROL_REQUEST` to them and returns `202 "control request sent"`; otherwise `session.SetAsHost()` ([control.go](https://github.com/m1k1o/neko/blob/master/server/internal/api/room/control.go)) | **Yes** — the only candidate with real control arbitration |
| **steel** | The session viewer is interactive (`interactive=true` default) and shares the same CDP-driven browser. The explicit pause/hand-back protocol lives in **steel-mcp-server**, not in steel-browser: `resolveManualHandoff()` uses MCP **elicitation** (`inputRequired` / `inputResponse`) with a viewer that has a "Hand back" button, then returns "The person handed the browser back. Re-read the page before acting; its state may have changed." ([handoff.ts](https://github.com/steel-dev/steel-mcp-server/blob/main/src/core/tools/handoff.ts)) | MCP tool `steel_session_handoff`, reasons `sensitive_input \| file_upload \| review \| manual_step` | **No** — the CDP client is never disconnected; the "pause" is a tool-level await. If the agent keeps calling tools, nothing stops it |
| **kernel (hosted)** | Live view URL is read/write by default (`ENABLE_READONLY_VIEW=true` to lock it) and the browser "stays alive as long as something is driving it — a CDP or WebDriver client, a Live View viewer, or an in-flight computer controls request" ([Create](https://www.kernel.sh/docs/introduction/create)); docs pitch it as "hand a session off to a human-in-the-loop" ([observe.mdx](https://github.com/kernel/docs/blob/main/introduction/observe.mdx)) | `browser_live_view_url`, `?readOnly=true`; `/computer/*` REST also drives the same browser | **No lock.** Human and agent can both drive simultaneously. Real handoff = your code stops calling `/computer/*` |
| **browserbase (hosted)** | Live View with click/type/scroll; docs' "Taking a session's remote control with Session Live View" for 2FA ([authentication](https://docs.browserbase.com/platform/identity/authentication)) | `GET /v1/sessions/{id}/debug` → `debuggerUrl`, `debuggerFullscreenUrl`, per-page URLs, `wsUrl` ([API ref](https://docs.browserbase.com/reference/api/session-live-urls)) | **No lock.** Same "your script must stop" contract |
| **browserless** | `Browserless.liveURL` CDP command returns a shareable URL; Hybrid feature "Allow human intervention in automation workflows / Continue automation after human interaction" ([live debugger docs](https://docs.browserless.io/enterprise/live-debugger)) | CDP command + `Browserless.reconnect` | No lock. Enterprise-tier feature |
| **playwright-mcp** | Two adjacent things, neither a handoff protocol: `--extension` attaches to a browser the human is already using (reverse direction), and `page.pause()` opens the Inspector — "useful during development", headed only ([Playwright debug docs](https://playwright.dev/docs/debug)) | `--extension`, `page.pause()` | n/a |
| **browser-handoff** (library, not a service) | The piece that's actually missing everywhere: `h.pause(page, until=Detection…)` / `h.guard(page, scenarios=[…])` + notifiers (Discord/Slack/email), resume on URL/element/content/LLM detection. Has a **passthrough mode** that iframes Kernel/Browserbase/Steel's own viewer, because relaying frames locally gave "~30 seconds per keystroke" ([repo](https://github.com/synacktraa/browser-handoff)) | Python library | Detection, not a mutex |
| *Cloudflare Browser Run* (context, not a candidate) | The cleanest formal API I found anywhere: `Cloudflare.handoff` CDP command with `instructions` + `timeout`, and a `Cloudflare.handoffComplete` event with `{success, reason}`; `Cloudflare.getLiveView` returns the operator URL ([docs](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/)) | Custom CDP domain | Yes: the operator clicks Done/Failed |

**If none of those is acceptable, here is what it actually takes** (this is the shape I'd build, and it's ~4 pieces):

1. A **session lease** in mason: `{session_id, holder: "agent"|"human", epoch}`. Every browser tool checks `holder == "agent"` and `epoch` matches, else returns "human has control".
2. A **handoff tool** that flips the lease, mints a short-TTL viewer URL, and **returns without the agent being able to act** — the MCP call must block (Steel's elicitation approach) or the agent's next tool call must be rejected by the lease. Kernel/Browserbase give you the URL; they do not give you the block.
3. **Completion signal**: either a "Done" button in your own wrapper page, or a detector (URL/element/LLM) as `browser-handoff` does — do not trust the human clicking done and do not resume from the pre-handoff DOM (Steel's own tool text says exactly this: "Re-read the page before acting").
4. **Re-observation** after hand-back, plus an origin check so a handoff cannot be used to walk the agent onto another domain.

## 3. Bitwarden autofill without leaking secrets to the model

### What the CLI actually requires (quoted)

- **API-key login is not enough.** "No matter which option you use, a master password will be required to `unlock` the client in order to access data with a session key… **Your API key is not a substitute for your master password.**" ([CLI docs](https://bitwarden.com/help/cli/)). The API key is `BW_CLIENTID` + `BW_CLIENTSECRET`, and `bw login --apikey` "will prompt you for your personal `client_id` and `client_secret`" ([personal API key](https://bitwarden.com/help/personal-api-key/)).
- **Headless unlock is supported, via env or file:** `bw unlock --passwordenv BW_PASSWORD` / `bw unlock --passwordfile ~/…` — "If `BW_PASSWORD` is non-empty and has correct values, the CLI will successfully unlock and return a session key" ([CLI docs](https://bitwarden.com/help/cli/)).
- **The session key is the thing you must store/keep:** `export BW_SESSION="5PBYGU+…"`, or pass `--session` per command. "Session keys are valid until invalidated using `bw lock` or `bw logout`, however **they will not persist if you open a new terminal window**." ([CLI docs](https://bitwarden.com/help/cli/)).
- **Reading a secret is one command:** `bw get (item|username|password|uri|totp|exposed|attachment|folder|collection|organization|org-collection|template|fingerprint) <id>`; "the following command would return a Github password: `bw get password Github`" — and it searches by string, erroring if multiple match ([CLI docs](https://bitwarden.com/help/cli/)).
- **A working unattended bootstrap** (this is the canonical pattern, from the External Secrets Operator docs, which is a real production user): `bw config server $BW_HOST` → `bw login --apikey --raw` → `export BW_SESSION=$(bw unlock --passwordenv BW_PASSWORD --raw)` → `bw unlock --check` → `bw serve --hostname all` ([external-secrets.io](https://external-secrets.io/latest/examples/bitwarden/)).
- **`bw serve` exists** as a core command — a local HTTP API ([CLI docs, "serve"](https://bitwarden.com/help/cli/)) — which is the right shape for mason: one long-lived unlocked process, HTTP in, JSON out.

### The three real options

**A. `bw` + `bw serve` sidecar (recommended).**
A small "credential broker" process inside the tool machine (or its own container) holds `BW_PASSWORD`/`BW_SESSION` in **its own** environment, runs `bw unlock --passwordenv … --raw`, then `bw serve`. mason gets exactly one tool: `fill_credential({item, fields, selector_ref})`. The broker resolves the item, calls `bw get password <item>` / `bw get username <item>` **in-process**, and hands the string straight to the browser driver — `page.locator(sel).fill(value)` ([Playwright `fill`](https://playwright.dev/docs/api/class-locator#locator-fill)) or CDP `Input.insertText`. The tool returns `{ok: true, filled: ["username","password"], origin}` — never the value. Model context never sees it; the only copy is in the broker's and the browser's memory.

*Why this works structurally:* the secret never crosses the MCP response boundary. The failure mode to design against is a "helpful" debug path that returns `bw get password` stdout; make that impossible by not exposing a generic shell to the agent in the credential container.

**B. Browser extension in a persistent profile (best secrecy, worst operability).**
Playwright *can* do this: "Extensions only work in Chromium when launched with a persistent context… **Note the use of the `chromium` channel that allows to run extensions in headless mode**", and "Google Chrome and Microsoft Edge removed the command-line flags needed to side-load extensions, so use Chromium that comes bundled with Playwright" ([Playwright chrome-extensions](https://playwright.dev/docs/chrome-extensions)). So `chromium.launchPersistentContext(userDataDir, { channel: 'chromium', args: ['--disable-extensions-except=…','--load-extension=…'] })` with the Bitwarden MV3 extension and `headless: true` is a supported configuration. The fill then happens entirely inside the browser, and mason never holds the plaintext at all — the strongest property of the three.
The catch is **unlock**: the extension needs the master password typed into its own UI (or a PIN), and I could find **no documented programmatic unlock** for the extension. Vault timeout is configurable per app ([vault timeout docs](https://bitwarden.com/help/vault-timeout/)) — "Never" may be offerable, but that's an inference, not a documented guarantee for an unattended headless profile. Operationally: a human unlocks the profile once, the profile file becomes a bearer credential, and any auto-lock setting that expires it silently breaks the agent.

**C. Vaultwarden.** It is a Bitwarden-API-compatible server, so option A works unchanged against it (`bw config server https://vault.example`), which is the point — Vaultwarden is a *server* swap, not a different client story. It does not solve unlock; the CLI still needs the master password. I did not verify Vaultwarden's compatibility claims against its own repo in this pass — treat that as **unverified** (see Missing evidence).

**D. Something else that is actually better for machines: Secrets Manager (`bws`).**
`bws` authenticates with a **machine-account access token** and needs **no master password and no unlock** — "You can authenticate a CLI session by saving an environment variable `BWS_ACCESS_TOKEN`", then `bws secret get <id> | jq '.value'` ([Secrets Manager CLI](https://bitwarden.com/help/secrets-manager-cli/), [access tokens](https://bitwarden.com/help/access-tokens/)). This removes failure modes 1–3 below entirely.
The cost: Secrets Manager is **organization-scoped** (machine accounts live under an org's Billing → Subscription, [machine accounts](https://bitwarden.com/help/machine-accounts/)), and secrets are arbitrary key/value blobs — there are no login *items* with URIs, no TOTP generator, no autofill matching. So it's a good store for "the password for site X", and a bad store for "my Bitwarden vault". For a single operator this is a real decision: either you run a one-person org, or you use option A.

### Failure modes, named

1. **Session expiry by process lifetime.** The session key "will not persist if you open a new terminal window" ([CLI](https://bitwarden.com/help/cli/)). If the broker restarts, it must re-unlock — which means `BW_PASSWORD` must be present at every start, i.e. you are storing the master password on the box. There is no way around this with `bw`.
2. **2FA / new-device login.** API-key login is recommended "if your account uses a 2FA method not supported by the CLI (FIDO2 or Duo)" ([CLI](https://bitwarden.com/help/cli/)), so API key + master password sidesteps the TOTP prompt — but the master password is still required. Rotating the API key "will invalidate your previous key and all active sessions" ([personal API key](https://bitwarden.com/help/personal-api-key/)), i.e. a rotation silently breaks the broker.
3. **SSO / Key Connector orgs: CLI can't decrypt at all.** "Users who join an organization using trusted devices will not be able to access data using the CLI" ([CLI](https://bitwarden.com/help/cli/)). If the vault is in such an org, option A is dead on arrival.
4. **An item that is not a login.** `bw get password` only makes sense for login items; cards/identities/notes have no `login.password`. `bw get totp` only works where a TOTP seed exists. Design the tool to take an explicit field list and fail closed.
5. **Master-password re-prompt does not protect you in the CLI.** Bitwarden staff: "**At this time master password re-prompt is not supported via the CLI**" ([bitwarden/clients#14774](https://github.com/bitwarden/clients/issues/14774)). And the feature is explicitly not a security boundary: "Master password re-prompt is not an encryption mechanism. This feature is an interface-only guardrail… We recommend never leaving your vault unlocked when unattended or on a shared workstation" ([docs](https://bitwarden.com/help/master-password-re-prompt/)). So **`bw`-based autofill on an unattended box is exactly the case Bitwarden tells you not to do.** That's the honest framing: option A is a real weakening of the vault, mitigated only by scoping (a dedicated Bitwarden account whose vault contains only the credentials mason is allowed to use) and by never exposing `bw` itself as a tool.
6. **Item selection ambiguity.** `bw get password Github` searches by string and errors on multiple matches ([CLI](https://bitwarden.com/help/cli/)) — pin exact item IDs in mason's config, not names.

## 4. How it attaches to an agent

**Three shapes, and the candidates cluster cleanly:**

**(a) MCP server that owns the browser** — `microsoft/playwright-mcp`. ~40 `browser_*` tools (click, type, snapshot, navigate, evaluate, console, network, tabs, file upload, drag, pdf…). Crucially it has `--cdp-endpoint` ("CDP endpoint to connect to", env `PLAYWRIGHT_MCP_CDP_ENDPOINT`), so it can be pointed at *any* CDP server — Steel, Kernel, Browserless, browserbase — and it will not try to launch its own Chromium ([README](https://github.com/microsoft/playwright-mcp#configuration)). This is the cheapest way to give mason a browser tool surface. It does **not** call a model and does not fight mason's loop. Note their own advice: for coding agents "CLI + SKILLs" is more token-efficient than MCP; MCP is better "where maintaining continuous browser context outweighs token cost concerns" ([README](https://github.com/microsoft/playwright-mcp)).

**(b) MCP server that owns the *service*** — `steel-dev/steel-mcp-server` (MIT). 19 tools: `steel_scrape`, `steel_screenshot`, `steel_pdf`, `steel_session_create/release`, `steel_navigate`, `steel_snapshot`, `steel_find`, `steel_act`, `steel_wait_for`, `steel_session_diagnostics`, `steel_session_handoff`, `steel_session_replay`, `steel_batch`, `steel_session_options`, `steel_session_live_view` — and the last one is explicitly hidden from the model: "Feeds the inline viewer its connection details. **Hosts hide it from the model**" ([README](https://github.com/steel-dev/steel-mcp-server)). That is the right instinct for a host that already has a model: the viewer URL is UI state, not model state. `STEEL_LOCAL=true` runs it against a self-hosted instance. This is the best-designed MCP surface of the lot, but it is a *second* agent-facing layer on top of the service — you'd be choosing between "mason's own tools over CDP" and "Steel's tools over Steel's REST".

**(c) Libraries that want to be the agent** — **stagehand** and **browser-use**. Both take a `model` and expose `act/extract/observe` (Stagehand: `Stagehand.create({ browser, model: { modelName, apiKey } })`, [README](https://github.com/browserbase/stagehand)) or a full autonomous loop (browser-use: MCP tool `retry_with_browser_use_agent` with `OPENAI_API_KEY` in its manifest, [manifest.json](https://github.com/browser-use/browser-use/blob/main/browser_use/mcp/manifest.json)). These **fight** a host that already has a model: you'd be paying two model bills, two retry policies, two context windows, and you lose the ability to reason across browser + non-browser tools in one turn. The one genuinely useful idea to steal from Stagehand's README: use `observe()` to get **selectors** and then fill credentials with Playwright directly, "so credentials never reach the model" ([README](https://github.com/browserbase/stagehand)) — that's the same trick as §3 above, expressed as an API.

**(d) Nothing** — neko, browserless, KasmVNC, kernel-image. So for those, mason attaches over **CDP**: `chromium.connectOverCDP(wsEndpoint)` ([kernel README example](https://github.com/kernel/kernel-images#connect-to-the-browser-via-chrome-devtools-protocol)). Kernel additionally offers an HTTP computer-use surface (`/computer/click_mouse`, `/computer/type`, `/computer/screenshot`, `/computer/clipboard/{read,write}`) and `/playwright/execute` — `POST /playwright/execute` with code is a genuinely nice fit for a tool machine that doesn't want a persistent Node Playwright client ([openapi.yaml](https://github.com/kernel/kernel-images/blob/main/server/openapi.yaml)).

**MCP inventory, plainly:** playwright-mcp ✅ (Apache-2.0, active), steel-mcp-server ✅ (MIT, active), kernel ✅ but hosted/OAuth-only, browserbase ⚠️ (self-host repo archived; hosted MCP only), browser-use ✅ but it's an agent, neko ❌, browserless ❌, KasmVNC ❌.

## 5. What plain Playwright + Chromium in the tool machine does *not* give you

Concretely, in mason's terms:

1. **Live view.** Nothing. Playwright has no stream. You get `page.pause()` — the Inspector, headed only, "useful during development… not as a durable queue, notification, authentication, or production recovery system" ([Playwright debug](https://playwright.dev/docs/debug)). To get a human-watchable view you add Xvfb + a VNC stack (x11vnc + noVNC, or KasmVNC, or neko) *or* write a CDP screencast pump yourself: `Page.startScreencast` → websocket → JPEG frames → browser canvas, plus an input path back (`Input.dispatchMouseEvent`/`dispatchKeyEvent`) if you want it interactive. Steel's `page-screencast.ts` + `casting.handler.ts` is essentially that, already written ([steel-browser](https://github.com/steel-dev/steel-browser/blob/main/api/src/plugins/browser-socket/page-screencast.ts)).
2. **Session lifecycle.** No sessions, no IDs, no TTL, no idle timeout, no "reconnect to the browser that was running 40 seconds ago". You own: process spawn, port allocation, `--remote-debugging-port`, readiness wait, crash detection, recycling, and the reconnect path (`connectOverCDP` works, but only if *you* kept the process and port alive).
3. **Persistence.** `launchPersistentContext(userDataDir)` gives you cookies/logins — but one profile is one browser, serialized: "A persistent profile can only be used by one browser instance at a time, so concurrent MCP clients sharing the same workspace will conflict" ([playwright-mcp README](https://github.com/microsoft/playwright-mcp#user-profile)). Per-identity profiles are your problem: directory layout, locking, backup, and the fact that a corrupted profile silently logs you out.
4. **Isolation.** One container = one filesystem, one `$HOME`, one set of `/tmp` dirs, one Chromium download. Isolation between two sessions means two processes with separate `user-data-dir`s — and no memory/CPU/PID caps, no seccomp, no network egress policy. Kernel ships exactly those as features (`/network/egress-policy`, `/configure`, per-container limits) ([openapi.yaml](https://github.com/kernel/kernel-images/blob/main/server/openapi.yaml)), and it needs a container (or a microVM) per session to mean anything.
5. **Concurrency.** `CONCURRENT=N` (browserless) and `MAX_SESSIONS` (Steel) are *schedulers*; plain Playwright has none. You get whatever the tool machine's memory allows, and a runaway agent can OOM the whole tool machine, taking the RPC daemon with it. That's the real argument for a separate browser service: **failure isolation**, not features.
6. **Recording/replay.** `recordVideo` per context works ([Playwright videos](https://playwright.dev/docs/videos)) but needs ffmpeg in the image and gives you files, not a stream, not retention, not a seekable artefact with telemetry alongside. Kernel's recorder + SSE telemetry stream and Browserbase's rrweb/HLS replays are product features, not library calls.
7. **Human handoff.** Nothing at all. See §2 — this is the single largest thing you'd build.

What it *does* give you, and you should not give up: zero extra network hop, no second auth boundary, no vendor session semantics, full `page.route()`/`addInitScript()` control, and the ability to run `expect`-style assertions in the same process as the agent's other tools. For a single operator with one or two concurrent tasks, that is a lot.

## Recommendation

**Primary: `steel-dev/steel-browser`, self-hosted, driven by mason over raw CDP — not through steel-mcp-server.**

Why: Apache-2.0 with no service clause; a real session API (`POST /v1/sessions`) that returns a CDP `websocketUrl` *and* an interactive viewer URL in one response; `persist` + `userDataDir` for logins; a screencast viewer you don't have to write; and it is explicitly designed to be self-hosted (`STEEL_LOCAL=true`, `--api-url`). Moving parts: **one container** (api + ui, or the single image on :3000) + mason's existing Playwright/CDP client + a `sessions.create()` call per task. That's it — no new auth system, no vendor account.
The costs you accept: **one session at a time when self-hosted** (so concurrency = N containers behind your own tiny router, or accept serialization); profiles are a bare `userDataDir`, not a managed feature; and the explicit handoff protocol lives in their MCP server, not their REST API — so if you want handoff you either adopt their MCP layer or implement the lease from §2.

**Second: `kernel/kernel-images` headful, one container per session, your own tiny orchestrator.**
Pick this over Steel if the live view quality matters (WebRTC with copy/paste and resize beats screencast), or if you want an HTTP computer-use surface (`/computer/*`) and `/playwright/execute` instead of holding a long-lived CDP socket inside the tool machine. Apache-2.0, and the image is genuinely production-shaped (supervisord, recording, egress policy, `/configure`). The cost is real: **you write the control plane** — container create/destroy, port mapping, CDP URL discovery, idle reaping, and profile persistence via bind-mounted `user-data-dir`. That's the "moving parts" difference: Steel gives you a session API and no WebRTC; Kernel gives you WebRTC and no session API.

**Third (and my actual pick if the answer is "keep it boring"): Playwright in the tool machine + `microsoft/playwright-mcp` + neko *only as a display**, i.e. no service layer at all.
You keep the browser in-process, add `playwright-mcp` for the model-facing tools, and get live view by running the browser headed on Xvfb inside a neko (or KasmVNC) container so a human can watch and grab control. Costs: you own lifecycle and isolation, you accept serialized profiles, and you accept that a browser crash can take out the tool machine — mitigate by running the browser in its *own* container from day one, so the "service layer" is a docker-compose file rather than a product.

**Do not use:** browserless (SSPL/commercial, and live debugging is gated to Enterprise per their own table); neko as the *browser* layer (no CDP flag in its chromium launch, `--bwsi` guest mode, aimed at shared desktops); KasmVNC standalone (GPL-2.0 VNC server with no session model); `browserbase/mcp-server-browserbase` (archived); stagehand/browser-use as the driver (they bring their own model loop).

**Credentials: option A, scoped.** A dedicated Bitwarden account (vault contains only mason-usable logins) + a broker process holding `BW_PASSWORD`/`BW_SESSION` and running `bw serve`, exposing exactly one tool `fill_credential` that returns `{ok, fields}` and nothing else. If you can live with org scope, `bws` (Secrets Manager, access token, no unlock) removes failure modes 1–3 and is strictly better operationally. Do **not** give the agent a shell that can run `bw get password …`.

## What we would have to build ourselves

1. **A session lease + handoff protocol** (holder, epoch, block-on-handoff, re-observe on return, origin check). No candidate's REST API gives you the *block*; Steel's is MCP-elicitation-shaped and Kernel/Browserbase just hand you a URL. ~1 tool + 1 state machine + a wrapper page or a detector.
2. **A credential broker** with no read path — `fill_credential` only, item IDs pinned in config, fail-closed on item type, and a `bw unlock --check` health probe that fires a signed event when the vault is locked.
3. **A per-session container router** if you want more than one concurrent session on any of these (Steel self-hosted serializes; Kernel/Neko need one container each). Includes port allocation, idle reaping, and crash → new-container recovery.
4. **Profile lifecycle**: per-identity `userDataDir` create/backup/restore/lock, and a documented "this profile is a bearer credential" policy.
5. **Live view for the in-process option** — either a VNC sidecar (cheap) or a CDP screencast pump + input path (Steel's `page-screencast.ts` is the reference implementation to read).
6. **Egress policy / isolation** if the browser lives in the same container as everything else: an allowlist at the network layer, and a separate PID/memory cgroup so a browser OOM doesn't kill the RPC daemon.
7. **Replay/retention** if you want post-mortems: `recordVideo` + a retention policy, or consume a service's SSE telemetry stream.

## Contradictions

1. **Browserless live view, three ways.** (a) The OSS feature table says "Live debugger: **No**" for Open Source, "Yes" for Cloud/Enterprise ([docs.browserless.io/enterprise/open-source](https://docs.browserless.io/enterprise/open-source)). (b) The OSS Docker deployment page says the image ships "Session management, health checks, and **a built-in debugger UI**" ([same page](https://docs.browserless.io/enterprise/open-source)). (c) The Live Debugger page says "The Live Debugger ships with all Chromium Docker images… **no Enterprise license is required**" ([live-debugger](https://docs.browserless.io/enterprise/live-debugger)). I could not resolve which is true for the current image; the safe read is "assume live view is gated until proven otherwise on the exact tag you deploy."
2. **Kernel: "open source" vs. what's in the repo.** README says "This repo powers our hosted services" and the image is Apache-2.0, but the thing that creates browsers is not in the repo. Both statements are true; it reads as OSS and is not a self-hostable *service*.
3. **Steel: profiles.** The REST schema has `persist`/`userDataDir`, while the related MCP server's README says self-hosted Steel "has no … browser profiles". These are compatible only if you read the latter as "no *managed* profiles" — which is my interpretation, not their wording. **[inference]**

## Missing evidence

- No primary source states which of these services support **hard** human/agent mutual exclusion during a handoff. Only neko's control-request flow and Cloudflare's `handoff`/`handoffComplete` are actual arbitration protocols.
- No published benchmarks comparing these on render fidelity / input latency. The one concrete latency number I found is third-party and alarming: `browser-handoff` reports "~30 seconds per keystroke" when relaying input through a local process to a Kernel cloud browser ([repo](https://github.com/synacktraa/browser-handoff)) — that is a relay architecture problem, not a Kernel problem, but it's the only number I have and it is **not** a benchmark of any candidate's own viewer.
- No data on Neko's WebRTC quality with an automated browser driving the same X display (screen-cast of an agent-driven window). Plausible fit, unmeasured.
