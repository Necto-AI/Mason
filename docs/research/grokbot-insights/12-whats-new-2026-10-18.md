# What "What's new in Grok Bot" (Oct 18, 2026) says mason should build

> Source: xAI product changelog video, transcript in `.scratch/grokbot-insights/SOURCE-whats-new-2026-10-18.md`
> (raw text supplied by Denis; YouTube is unreachable from this host). Companion to `01`–`11`, but with a
> different source class: those distill a *design lecture*; this is one week of *shipped product*. Half of it
> is table stakes, a third is grokbot-specific plumbing, and four items name real gaps in mason.

The useful signal is not the feature list. It is the shape the surface is converging on:

1. **The agent's output is a typed card, not prose.** Tables, questions with multi-select, drafts with
   highlighted revisions, sign-in prompts. Text is the fallback, not the default.
2. **Attention becomes the product.** Notification collapsing, an unread pill, "the device you are active
   on". Once the agent speaks first, managing its noise is the feature.
3. **Every new surface is a channel into one queue** (X DMs, mentions, email aliases, voice calls, the
   Android assistant), each with its own identity and its own capability limit.

mason has (1) text, (2) nothing, (3) one surface. The notes below are ordered by value per unit of work,
not by the video's order.

## The four that matter

### A. A read cursor is a missing concurrency primitive, not a UI nicety (#12)

mason's whole reason to exist is that the agent speaks first. In that world, "what has the reader already
seen" is state the backend must own — the same class of state as `pi.inbox` or the hook's `fireCount`, and
for the same reason: two tabs, a phone and a desktop must agree, and a reload must not lose it. The video
ships the UI (a pill); the interesting part is that the client cannot own it.

Design:

- A conversation-scoped document, `app.read` (`defineDoc({ scope… })` in
  `vendor/pi/packages/durable/src/documents.ts`), latest-only, replicating over Chord exactly like
  `pi.live`: `{ lastReadEntryId, updatedAt }`. The client writes it through a Chord method, not by
  patching state.
- The client writes on the two events that mean "seen": the transcript is pinned to the bottom, *and* the
  document is visible (`document.visibilityState === "visible"`). A background tab that happens to be
  scrolled to the end has not been read.
- Rendering is then derived, not stored: a "new" divider at `lastReadEntryId`, and the existing jump-pill
  gains a count while scrolled away. `JumpPill` already owns the "scrolled away from the end" state; it
  should own the unread count too rather than a second pill.
- What this buys beyond the pill: a proactive message can be phrased from the backend's knowledge of what
  was seen ("two things happened while you were away"), and (8) below has its precondition.

Why now: it is one document, one method, one divider, one test over `transcript-model.ts` logic, and it
does not touch the run path. It is the cheapest item on this list that changes how the agent feels.

### B. Wall-clock routines, because `intervalMs` is not a schedule (#13)

The one hook the repo ships that looks like a routine is `morning-brief`, and it is the one thing a
personal agent is *for*: "weekdays at 8". `intervalMs: 86_400_000` fires 24h after the process started, so
a restart moves the brief, and a laptop that sleeps skips it. That is a bug in waiting, not a missing
feature.

Design, and the trap:

- `EventHookConfig` gains an optional `schedule: { kind: "daily"; at: "08:00"; days?: number[]; tz: string }`
  beside `intervalMs`, plus a **pure** `nextFireAt(schedule, now): number` — the repo already keeps this
  kind of policy pure and tested (`src/server/run-retry.ts`, `src/server/status.ts`). No cron parser: daily
  + weekday set covers every routine anyone writes, and a parser is a dependency plus a dialect.
- **The identity key must survive an edit.** `scheduledRequestId()` (`src/server/hooks.ts:280`) derives the
  slot from `floor(now / intervalMs)`. A wall-clock slot has to be the *local date of the fire*
  (`2026-10-20`), not a bucket of the current interval, or editing a routine from 08:00 to 08:05 creates a
  second slot in the same day and the brief is delivered twice. Slot identity belongs to the schedule's
  calendar day; the time of day is not part of the key.
- DST and tz changes: a daily slot that does not exist (02:30 on a spring-forward day) must fire once at the
  next existing instant and never twice. One test per case, both pure.
- The debug sheet already lists hooks with `enabled`/`fireCount`; it should show `nextFireAt` as text. That
  is the whole UI for this feature.

### C. Answerable cards, without a second delivery path (#1)

grokbot's question card ("ABC multi select") is the interaction mason lacks. Today the agent can ask in
prose, which costs the reader a typed reply the model then has to re-parse, or emit a sandboxed widget,
which costs an iframe, a CSP document, a streaming pipeline and a bridge — for three buttons. The
middle ground is a native card.

Design:

- Extend `send_to_user` (`src/server/extensions/delivery.ts`) rather than adding a second tool. SPEC §4.3
  rests on "one channel through which the agent's words reach the reader"; a question is still words, and a
  second delivery tool would fork the transcript model, the entry kinds and the UI. The call gains an
  optional `choices: { id, label, multi?: boolean }[]`, carried in the entry's `data` like the hook's
  `hookId`.
- The answer is a **user input**, not a callback: submitting a choice sends a normal submission that quotes
  the question's id, so it lands in the durable log, replays in a rebuilt transcript, and is idempotent by
  construction — the same reasoning that gives hooks their `requestId` tiers.
- The invariant worth writing down: **a card that needs an answer must be a durable entry; a card that does
  not can be a sandbox.** Widgets stay the escape hatch for anything visual; questions, approvals and
  sign-ins are entries with a control.
- The renderer is small: a `Choices` card in `MessageRow`'s delivered-message branch, and the "answered"
  state derived from the entries that follow the question, never from local component state.

### D. Actionable auth and approval errors (#14, and #3's cousin)

The Slack sign-in link is one instance of a general rule already in the lecture notes ("write errors that
say what to do next") taken one step further: some errors have an *action*, and the action is not prose.

Design:

- A tool result can be `{ kind: "needs_action", action: "auth" | "approval", url?, secretName?, detail }`.
  The client renders it as a card with a button; the secret never enters the model's context (lecture `06`),
  and an approval is the same class of object (the video's payment Allow/Deny card is identical in shape).
- For a personal agent the first real instance is the first connector that needs a login — which is (4),
  inbound email. Do not build the mechanism before that adapter exists; do write down that the seam is a
  tool-result kind, because that forces it to be data, not a tool name the UI special-cases.

## The rest, briefly

**Inbound email (`#4`) — next after A/B.** Plus-addressing is not about addresses; it is a free routing
key. `mason+<slug>@…` gives (a) correlation to a routine or task, (b) an identity for dedupe (the
`Message-ID` is the explicit tier of `requestId`), and (c) a way to have *different* trust levels per alias
without new accounts. Requirements before any code: the adapter must admit mail as **untrusted** input
(lecture `06`/`07`), an unknown alias must go to a triage list and never trigger action, and the reply must
be capability-limited (D). This is the cheapest way for mason to stop being a web page you visit.

**Surface capabilities before the second surface (`#5`).** `send_to_user` is surface-blind today because
there is exactly one surface. The moment a second one exists (email, X, SMS), the delivery tool has to know
what the target can render: a choices card or a widget sent to an X DM is a bug. Cheap to do now: pass the
surface's capabilities into the tool's context and refuse to deliver an unrenderable kind, with an error
that names the reason. Expensive to retrofit later, since it changes the tool's contract.

**Voice calls (`#7`) — note, do not build.** The transferable idea is the TTL, not the phone: a call is an
*ephemeral session* whose transcript is working context for a short window and whose residue is one
summarized entry in the durable conversation. If mason ever grows a call path, the raw call transcript must
not enter the main conversation, and the 30-minute expiry is the whole design.

**Notifications (`#8`) — after A.** Web push is easy; the hard part is exactly what the video fixed: one
notification, on the device the reader is actually using. That needs presence (`lastSeenAt` per surface),
which is the same document as the read cursor, and it needs the notification to be derived from the durable
log, never from a socket event — the lecture is explicit that the signal only says "something changed" and
that losing one is harmless. Notification collapsing is then one policy function over (presence, unread,
surface), not per-device fan-out.

**Connectors (`#6`) — as codemode, not as declarations.** The `01`/`11` finding holds: a connector per tool
declaration is a prompt bill. A connector should arrive as a CLI or a codemode API reachable from `bash`,
with a one-line capability note in the prompt — the same treatment `agent-browser` gets today.

**Not for mason, but say why:** multi-user, invites and per-bot ACLs (`#9`, `#11`) — a personal agent with
one principal, and the seam (`principal` threaded through every Chord method, `main.ts:24`) is already
right; keep it threaded, build nothing. The Android assistant remap (`#10`) has a cheap PWA analogue
(web share target + manifest shortcut), worth an hour, worth no design. The 3× computer speed (`#2`) and the
card restyle (`#1`'s visual half) are not design inputs.

## One caution

This is a changelog, so it shows symptoms, not causes. Two of its items (cards, notifications) are the
visible end of architecture the video never describes: grokbot's cards are typed, server-rendered and
durable, and its notifications are collapsed on the server for a set of devices it can identify. Copying
the visible half of either — a prettier card renderer, a per-device push fan-out — reproduces the problem
the video announced it just fixed.
