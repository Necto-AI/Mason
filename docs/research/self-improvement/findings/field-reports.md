# First-person 2025-2026 reports from people running agents that write their own skills, memory or instructions

## Answer
Practitioners running skill- and memory-writing agents in 2026 broke in five predictable ways: the skill library grew monotonic and unmaintainable (Hermes #7816: "a learning system that only accumulates and never forgets"), the agent learned permanent lessons from transient failures (#6051: "browser tools do not work"), force-injected memory beat the skills it contradicted (#145905), the model often failed to load the skill it had (and had ~200 skills) (#76307), and memory collapsed into near-duplicate restatements until stores hit 100% (#103920, #111205). Almost nobody "fixed" it with better wording; they fixed it with lifecycle state, sidecar telemetry, write-time dedup, staged approvals, caps, rollback guards, and — for the two independent practitioner-built ports of Hermes' loop to Claude Code/Codex — an external verification layer that diffs what the agent claimed it wrote against the filesystem.

## Claims
- Hermes' own users filed the canonical "only accumulates, never forgets" complaint: skills "mostly grow monotonically", "repeated patching can accumulate drift, conflicting instructions, or over-generalization", and rarely used skills "remain equally visible in the catalog / prompt path" [1] — "But a learning system that only accumulates and never forgets will eventually collect stale heuristics, prompt clutter, and brittle generalizations." — direct
- The reporter of #7816 explicitly refused auto-delete and asked for sidecar metadata instead: "I would **not** auto-delete by default. Archival is much safer than deletion." [1] — direct
- Latest Hermes behaviour (matching the request): stale after 30d, archived after 90d unused (~120d total), plus `pinned`, per #77264 [10] — direct (from the follow-up issue's description of current behaviour, and UniM0cha's port copies 30/45-day defaults [12])
- Auto skill creation turned a transient environment failure into a permanent prohibition: after a Linux→WSL2 migration with Playwright missing, Hermes "auto-created a skill called browser-tool-launch-issue"; after Playwright was installed and verified, "the agent continued to avoid browser tools entirely" [2] — direct
- The negative claims it wrote into skills read like rules: "browser tools do not work", "default_api cannot be called from execute_code", "even reinstalling the browser does not resolve the issue" [2] — direct
- Deleting the file, not editing the prompt, restored behaviour: "After manually deleting the negative skill and cleaning the modified skill, the agent immediately resumed normal browser tool usage" [2] — direct
- That reporter's actual remedy was a TTL/confidence field plus a self-made cleanup skill: "Created a custom negative-skill-cleaner skill to periodically scan for and remove stale negative constraints" and "manually added Sampling Behavior principles to AGENTS.md" [2] — direct
- Force-injected memory outranks skills because it is always present: "Since memory is permanently present, a single descriptive sentence in memory will consistently overpower the corrective instructions in the skill file." [4] — direct
- Same issue: a style rule from one project leaked into another and then was used to justify itself: "The AI measured the character count of a chapter, found it matched the 'short sentence' rule in MEMORY.md, and concluded: 'This is his style.'" [4] — direct
- The requested fix was a prompt-level priority ladder, not better memory: Priority 1 direct user prompt, 2 dynamic skills, 3 USER.md, 4 MEMORY.md [4] — direct
- Skills are not loaded even when they obviously match: agent "skipped skill_view(name='browser-ops') entirely despite clear skill match" on a task with a mandatory pre-flight checklist [3] — direct
- When caught, the agent's reflex was to write more text instead of comply: "added a generic screenshot reminder to memory (polluting every future turn) and patched the skill with ASCII art banner, instead of simply executing the rules that already existed" [3] — direct
- The reporter's diagnosis of the root cause is that prose rules have no enforcement binding: "The agent's instinct when caught is to create more documentation rather than correct its behavior." [3] — direct
- Recall decays with library size: with "~200 installed skills", "on a long-lived conversation the model often just doesn't think to load the matching skill, and previously-saved memory stops influencing behavior after some point" [5] — direct
- Same reporter explicitly rejects the "the model must remember to load the skill" design: "Depending on the agent to *remember* to call a time skill is fragile" / "Never rely on a skill the model must remember to load." [5] — direct
- Memory write path had only an exact-duplicate gate, so on a long-running install one fact appeared 5× and both stores sat at "99–100% of `memory_char_limit` / `user_char_limit` for weeks, putting every write into the at-capacity consolidation path" [7] — direct
- Duplicates are a producer-side bug, measured on a live install: "A **single turn** carried **49 identical stale facts** inside its memory block", "Removed mass in that one turn: **98,191 tokens** — and this reproduces several times per hour" [8] — direct
- Skills grew until the maintenance pass could no longer read them: at the 100k write cap the read wrapper spills to `cache/spillover/` and "The curator cannot read the body, and correctly declines to act on a skill it cannot read." [9] — direct
- A curator run report is quoted verbatim declining two skills: "both already multi-absorption umbrellas (100KB-scale packages, not fully readable this pass due to spillover). Left." [9] — direct
- Consolidation has no durable memory of what it already merged: "`absorbed_into=<umbrella>` is only a transient argument to `skill_manage(action="delete")` … **not persisted** in `.usage.json`" [10] — direct
- Archiving creates a re-creation loop: an archived skill is invisible to discovery, so the agent "**re-creates a near-identical skill from scratch** (duplicate knowledge, wasted effort)" [10] — direct
- Vendor-side cost of the always-visible catalog: with "87 bundled skills, the skills block alone consumes ~1,500-2,000 tokens of the system prompt" every session [6] — direct
- A practitioner port of Hermes' loop to Claude Code had to add a library cap to stop sprawl: `SIS_MAX_LEARNED_SKILLS` default `100`, above which "the worker forbids new skills" [12] — direct
- Same port refuses near-duplicates by name-similarity and rolls back bad writes: `SIS_DUP_NAME_JACCARD 0.5` — "Name-token overlap above which a new skill is refused as a near-duplicate"; the post-run skill guard "snapshots `~/.claude/skills` before the run, validates every touched `SKILL.md` after it, and rolls back anything malformed or out of scope" [12] — direct
- Its curator only trusts *human* activity: "a use, a view, or a patch a person made counts as activity, the distiller's own patches do not" [12] — direct
- The port also had to stop the agent from preferring new files over patches: "Distillation prefers patching existing skills over creating new ones" [12] — direct
- Practitioner complaint about self-written instruction files being ignored: "I've had explicit instructions for communication style in CLAUDE.md, in Claude's project 'memory', in global 'memory', in 'skills': it couldn't care less where it was." [14] — direct
- Same commenter: repeating a rule in four stores bought nothing and the apology did not transfer across sessions — "Only to do that again in the next session." [14] — direct
- Another practitioner's response was to *stop writing* to CLAUDE.md: "Result is I'm trying to resist adding more and more things to CLAUDE.md files" [15] — direct
- And the mechanism they found instead: "Yet if I tell it these things in a prompt during the task, it performs way better." [15] — direct
- Diagnosis of "memory-as-files" by a practitioner who builds a review layer: "the agent will cheerfully claim it updated something and not actually do it, or write a one-line stub that satisfies the spec but loses the original signal. Without a verification layer, the vault accumulates plausible-looking entries that quietly drift from reality." [11] — direct
- Their fix: "treating the agent's self-reported summary as a wish, not a fact. A separate process diffs the actual file system against the claimed changes and flags mismatches." [11] — direct
- And the split they recommend is structural, not prompt-level: keeping "per-agent instructions" apart from "cross-thread shared notes", because "Mixing them means the wisdom gets stale together." [11] — direct
- A Claude Code user abandoned prompt-only accumulation for a gated protocol whose normal outcome is refusal to write: the most common outcome of the gates is "do nothing", "63.6% rejection rate in my first experiment", and the knowledge base held "8 entries after 17 tasks" [13] — direct
- They moved computation out of the skill text because the model got it wrong: "The confidence math no longer lives in SKILL.md prompts (which caused LLM calculation errors). It's been moved to a Python tool layer" [13] — direct
- A setup-owner's complaint is not compliance but drift of the config itself: "a teammate can edit a skill in a PR nobody tests", and the only signal previously was "it feels different" [16] — direct
- Grep of one HN thread for sprawl, from someone who measured their own install: "I checked the session logs to see how often the agents were actually invoking the LSP tools. The answer was they had invoked them literally once the entire time." [17] — direct
- Also in that thread, on the four-way overlap of commands/skills/subagents/plugins for one job: "They are all just variations of 'insert a canned prompt', varying only along the dimensions of (a) how and where the prompt is installed" [17] — direct
- A counter-case: an experienced practitioner deliberately keeps the write-down instruction in AGENTS.md and reviews the diff — "I keep AGENTS.md instructions that tell the model to write things down … update the relevant pages in the vault", and "diffs become a review surface for memory" [18] — direct
- His stated safeguard against accumulation is attention at the diff, not a gate: "I do not want evergreen threads to quietly accumulate vibes in conversation history." [18] — direct
- Independent corroboration that models ignore a rules file that keeps growing: "It is pretty great at following instructions - for about 10 minutes, after which it seems to ignore things I told it before." [15] — direct
- Researcher inference: the recurring shape across these reports is that *write-side* mechanisms (nudges, budgets, dedup) get adopted, while *read-side* mechanisms (indexes, TTLs, revalidation, diff review) are what the failures actually call for — most of the 2026 fixes reported here are read-side or verification-side. ## Conflicts
- **Files-as-memory work / files-as-memory rot.** Jason Liu: keeping AGENTS.md instructions that "tell the model to write things down", with the vault as a git repo so "diffs become a review surface for memory" [18], versus armada1122: "the vault accumulates plausible-looking entries that quietly drift from reality" [11]. Both are first-person 2026 accounts; the disagreement is partly resolved by armada1122's own remedy (an external diff process), i.e. they disagree about the default, not about the fix.
- **Is the problem the model or the mechanism?** #49764's reporter asks for stronger prompt wording ("Strengthen the skill-matching instruction from 'you MUST' to a verifiable assertion") [3], while #76307's reporter rejects that class of fix outright: "Never rely on a skill the model must remember to load." [5] Same product, same year.
- **Does repeating a rule across stores help?** Conventional advice is to put rules where they are always visible; troupo reports the opposite outcome after putting the same rule in CLAUDE.md, project memory, global memory and skills: "it couldn't care less where it was" [14]. Contradicts, or at least bounds, the premise behind #145905's priority-ladder request [4].
- **Silence vs. congestion.** One camp wants fewer writes (#135980 wants the curator to fix overgrown skills [9]; tiansenxu gates writes until the normal outcome is "do nothing" [13]); the UniM0cha port instead caps the library at 100 and patches rather than creates [12]. No source argues both positions.
