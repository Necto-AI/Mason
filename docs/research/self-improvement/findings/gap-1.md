# Does any shipped prompt or skill-standard doc tell the model to write a small helper script or support file into a skill instead of inlining the code, and what is the exact trigger wording?

## Answer

Yes — exactly one *model-facing* prompt does, and it is Hermes's background skill-review prompt, which lists writing a support file as preference step 3 of 4 and names the script case with a condition: "`scripts/<name>.<ext>` — statically re-runnable actions the skill can invoke directly (verification scripts, fixture generators, deterministic probes, anything the agent should run rather than hand-type each time)." The trigger is therefore **repetition**, not difficulty: if the agent would otherwise re-type the code on each use, it becomes a file. Everything else that states a script-vs-inline rule is addressed to a *skill author* working with eval traces, not to a model mid-session — Anthropic's shipped `skill-creator` skill ("If all 3 test cases resulted in the subagent writing a `create_docx.py` … that's a strong signal the skill should bundle that script. Write it once, put it in `scripts/`, and tell the skill to use it.") and agentskills.io's creation guide ("When a command grows complex enough that it's hard to get right on the first try, a tested script in `scripts/` is more reliable"). The cost side is cheap and well stated by every source: a bundled script is "executed, not loaded" (Claude Code) / "Claude can run this script without loading either the script or the PDF into context" (Anthropic). The cost that is *not* handled anywhere is verification — Hermes's review fork has no shell, so the script it writes is never run before it becomes permanent.

## Claims

### The one model-facing instruction (Hermes)

- **The script affordance is defined in the background review prompt, not in the tool schema**: "`scripts/<name>.<ext>` — statically re-runnable actions the skill can invoke directly (verification scripts, fixture generators, deterministic probes, anything the agent should run rather than hand-type each time)." [1] — direct. The clause after "—" is the trigger; it is a cost/repetition condition ("rather than hand-type each time"), not a difficulty threshold.
- **The sibling categories are named in the same breath, so the model gets a three-way routing rule, not just "write a file"**: "`references/<topic>.md` — topical depth needed only sometimes … `templates/<name>.<ext>` — starter files meant to be copied and modified … `scripts/<name>.<ext>` — statically re-runnable actions" [1] — direct.
- **The write mechanism is named explicitly, with the path prefix**: "Add support files via skill_manage action=write_file with file_path starting 'references/', 'templates/', or 'scripts/'. The umbrella's SKILL.md should gain a one-line pointer to any new support file so future agents know it exists." [1] — direct. This is the read-back step for this affordance: the pointer is what makes the script findable later.
- **It is step 3 of a 4-step preference order, i.e. structurally subordinate to editing prose**: "Preference order — prefer the earliest action that fits … 1. UPDATE A CURRENTLY-LOADED SKILL … 2. UPDATE AN EXISTING UMBRELLA … 3. ADD A SUPPORT FILE under an existing umbrella … 4. CREATE A NEW CLASS-LEVEL UMBRELLA SKILL" [1] — direct. A model that follows the order literally writes a script only when no skill body is the right home.
- **The same order appears in the combined memory+skills review prompt, in compressed form**: "`scripts/<name>.<ext>` for statically re-runnable actions (verification, fixture generators, probes). Add a one-line pointer in SKILL.md so future agents find them." [1] — direct.
- **There is no script-specific firing event.** The fork that carries this instruction fires off tool-iteration count, not off anything script-shaped: `agent._skill_nudge_interval > 0 and agent._iters_since_skill >= agent._skill_nudge_interval` with default 10 (see `hermes-skill-loop.md` for the trace). So the write opportunity is "any session that ran ~10 tool calls", identical to the opportunity for a text patch. [1][2] — direct for the prompt, inference for the consequence.
- **The foreground prompt never mentions scripts at all.** Grep of the assembled gold-plate CLI prompt (10,087 bytes) for `script` returns three hits and none concerns skill support files: line 7 is about deliverable mode ("the deliverable is a working artifact backed by real tool output"), lines 53 and 63 are bundled-skill index descriptions. [3] — direct (negative evidence, from the full prompt text).
- **The foreground `skill_manage` description reduces the whole affordance to four words**: "write_file/remove_file (supporting files)" [4] — direct. No trigger, no directory guidance, no "instead of inlining".
- **The only foreground nudge toward scripts is a returned string after a successful create**, i.e. it arrives after the decision point, not before it: `"hint": "To add reference files, templates, or scripts, use skill_manage(action='write_file', name='{name}', file_path='references/example.md', file_content='...')"` [4] — direct. Note the example path is `references/`, so the surfaced default is prose, not code.
- **The schema is what makes scripts legal rather than the prompt**: `_FILE_PATH` = "Path RELATIVE to the skill's own directory, e.g. 'references/api.md' — no leading slash, never absolute; first segment references/, templates/, scripts/, or assets/." and `ALLOWED_SUBDIRS = {"references", "templates", "scripts", "assets"}` [4] — direct.
- **The read side already treats scripts as first-class, and never loads them**: `skill_view`'s description is "Load a skill's SKILL.md, or one of its linked references, templates or scripts" [5]; `_LINKED_FILE_SPECS` includes `("scripts", ["*.py", "*.sh", "*.bash", "*.js", "*.ts", "*.rb"], False, False)`, so a script appears in `linked_files["scripts"]` as a filename only [5] — direct. Cost of a bundled script at invocation time: one filename in a dict, zero body tokens.

### The verification hole (Hermes)

- **The review fork that is told to write scripts cannot execute one.** Its toolsets are `["skills"]` (plus `read_file`/`search_files`), with the code comment: "Write tools stay denied — autonomous maintenance goes through skill_manage's validation." [1] — direct. No `terminal`, no `execute_code` in the whitelist.
- **Consequence, stated as researcher inference**: the only prompt that tells the model to write a script is a prompt under which the script cannot be tested, so `scripts/` accumulates unexecuted code; the papers note's split (playbooks improve only where a deterministic verifier scores each update) predicts this is the branch that does not improve. Not measured anywhere. [1] — inferred.
- **Nothing lints scripts at write time.** The linter's rules named in the skill-loop note (`incident-log-shape`, `references-sprawl`, `oversized-body`) are prose-shaped; script scanning appears only at *install* time ("script lint" as part of NVIDIA SkillEvaluator, "advisory only … the install continues") [6] — direct.

### Anthropic's shipped skill (author-facing, strongest wording anywhere)

- **The clearest script-instead-of-inline trigger in any Anthropic artifact is inside the `skill-creator` skill, and it is an N-of-N repetition test over transcripts**: "**Look for repeated work across test cases.** Read the transcripts from the test runs and notice if the subagents all independently wrote similar helper scripts or took the same multi-step approach to something. If all 3 test cases resulted in the subagent writing a `create_docx.py` or a `build_chart.py`, that's a strong signal the skill should bundle that script. Write it once, put it in `scripts/`, and tell the skill to use it. This saves every future invocation from reinventing the wheel." [7] — direct.
- **Same skill, the packaging rule with a rationale**: "scripts/ - Executable code for deterministic/repetitive tasks" and "**Bundled resources** - As needed (unlimited, scripts can execute without loading)" [7] — direct.
- **Same skill, the write-a-script-instead-of-eyeballing rule (grading context, not packaging)**: "For assertions that can be checked programmatically, write and run a script rather than eyeballing it — scripts are faster, more reliable, and can be reused across iterations." [7] — direct.
- **Precondition that matters**: the trigger requires "the transcripts from the test runs" and a 3-case eval set — infrastructure the model does not have in an ordinary session, and the section is explicitly gated: "This section requires the `claude` CLI tool … which is only available in Claude Code" [7] — direct for the gating sentence; inference that this makes the trigger unusable mid-task.

### The standard (author-facing)

- **agentskills.io states the inline-vs-file boundary as a rule, keyed on fragility rather than repetition**: "**Move complex commands into scripts.** A one-off command works well when you're invoking a tool with a few flags. When a command grows complex enough that it's hard to get right on the first try, a tested script in `scripts/` is more reliable." [8] — direct.
- **And a second, repetition-keyed trigger that requires eval traces**: "When iterating on a skill, compare the agent's execution traces across test cases. If you notice the agent independently reinventing the same logic each run — building charts, parsing a specific format, validating output — that's a signal to write a tested script once and bundle it in `scripts/`." [9] — direct.
- **The standard's own discoverability rule for scripts is an instruction to the author, not the model**: "List available scripts in your `SKILL.md` so the agent knows they exist" [8] — direct. The note that relative paths resolve from the skill root ("the agent runs commands from there") is likewise author-facing [8].
- **agentskills.io gives scripts their own topic page** — `using-scripts` is 1 of 10 entries in the doc index, described as "How to run commands and bundle executable scripts in your skills" [10] — direct. The standard treats script bundling as a first-class concern; it just never addresses the model about it.
- **The standard's guidance on what makes a script usable by an agent is unusually concrete and is the best available checklist for a self-written script**: "Agents operate in non-interactive shells — they cannot respond to TTY prompts"; "`--help` output is the primary way an agent learns your script's interface"; "send structured data to stdout and progress messages, warnings, and other diagnostics to stderr"; "Many agent harnesses automatically truncate tool output beyond a threshold (e.g., 10-30K characters)" [8] — direct.

### Anthropic's two engineering posts (descriptive, not imperative)

- **The Skills post describes the script as authored ahead of time, with the cost argument in one sentence**: "In our example, the PDF skill includes a pre-written Python script that reads a PDF and extracts all form fields. Claude can run this script without loading either the script or the PDF into context. And because code is deterministic, this workflow is consistent and repeatable." [11] — direct. "Pre-written" is the load-bearing word: in the shipped Skills model the model runs scripts, it does not author them.
- **Same post, the one clause that grants discretion**: "Skills can also include code for Claude to execute as tools at its discretion based on the nature of the task." [11] — direct.
- **Same post, the author-side rule that code must be unambiguous about its role**: "Finally, code can serve as both executable tools and as documentation. It should be clear whether Claude should run scripts directly or read them into context as reference." [11] — direct.
- **The only Anthropic text describing the model authoring its own script uses permissive modality and no trigger**: "Agents can also persist their own code as reusable functions. Once an agent develops working code for a task, it can save that implementation for future use:" — followed by a code comment `// In ./skills/save-sheet-as-csv.ts` — and then "Adding a SKILL.md file to these saved functions creates a structured skill that models can reference and use. Over time, this allows your agent to build a toolbox of higher-level capabilities, evolving the scaffolding that it needs to work most effectively." [12] — direct. This is exactly the "values, not conditions" shape the brief warns about, in the primary source.
- **Same post states the cost honestly, which is the cost figure for this affordance**: "Running agent-generated code requires a secure execution environment with appropriate sandboxing, resource limits, and monitoring. These infrastructure requirements add operational overhead and security considerations that direct tool calls avoid." [12] — direct.

### Claude Code (a shipped, automatic writer of skill files)

- **Claude Code's `/verify` writes a skill file itself, with an absence trigger**: "When it has to build and drive your app without a recorded recipe, it writes what worked to `.claude/skills/verify/SKILL.md` at the repo root … so later runs and other agents follow the same steps." [13] — direct.
- **Its update rule is the sharpest "when to rewrite the artifact" condition I found, and the rationale is noise control**: "Claude edits the recorded file only when it steered a run wrong, such as a command that failed or a missing step, so you can commit the file without per-session diffs." [13] — direct.
- **`/run-skill-generator` is the same pattern with a user-invoked entry point**: "It gets your app running from a clean environment, captures what worked (the install commands, the env vars, the launch script), and commits it as a per-project skill at `.claude/skills/run-<name>/`." [13] — direct. Caveat: the capture target is the skill directory; I did not verify that a standalone `scripts/` file is written rather than prose steps.
- **Claude Code's layout note is the crispest statement of why a file beats inlined code**: "└── scripts/ └── helper.py (utility script - executed, not loaded)" [13] — direct.
- **Claude Code's stated boundary for supporting files is size, not execution**: "Large reference docs, API specifications, or example collections don't need to load into context every time the skill runs" and "Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files." [13] — direct. Note it says *reference material*; it does not tell the model to externalize code.

### Hermes docs vs Hermes prompt

- **The user-facing Hermes guide presents `scripts/` as a human authoring convention and never tells the agent to write one**: the directory tree annotates "`scripts/` — Scripts the agent can execute" [14], and the agent-writes-skills note covers only SKILL.md: "The agent can also create and update skills itself using `skill_manage`. After solving a complex problem, Hermes may offer to save the approach as a skill for next time." [14] — direct. The model-facing instruction exists only in the review prompt [1].
- **The features doc likewise lists the directory and stops**: "`scripts/` # Helper scripts callable from the skill" [6] — direct.

## Conflicts

**Four different trigger conditions for the same decision.** Hermes (model-facing) keys on repetition of *action*: "anything the agent should run rather than hand-type each time" [1]. agentskills.io keys on fragility: "When a command grows complex enough that it's hard to get right on the first try" [8]. Anthropic's skill-creator keys on N-of-N repetition of *authoring*: "If all 3 test cases resulted in the subagent writing a `create_docx.py`" [7]. agentskills.io's creation guide keys on reinvention observed across eval traces: "the agent independently reinventing the same logic each run" [9]. Only the first is usable without an eval harness; the other three presuppose transcripts from a test set.

**Who authors the script.** Anthropic's Skills post: the creator does — "a pre-written Python script" [11]. Anthropic's code-execution post: the agent does — "Once an agent develops working code for a task, it can save that implementation for future use" [12]. Hermes: the background review fork does, and the foreground agent gets only a hint string [1][4]. Claude Code: a bundled skill (`/verify`, `/run-skill-generator`) does, on the user's behalf [13]. Four answers, no source acknowledging the others.

**Externalize code, or externalize prose?** Claude Code's only externalization rule is about prose size — "Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files" [13] — while its layout diagram marks scripts as "executed, not loaded" [13]. Hermes's routing table treats `references/` and `scripts/` as peers chosen by *kind of content* [1]. agentskills.io's "Move complex commands into scripts" [8] is the only one that frames it as code-vs-inline at all.

**Hermes doc against Hermes prompt.** The guide's agent-writes-skills note covers only SKILL.md and presents `scripts/` as a human convention [14]; the review prompt tells the agent to write scripts [1]. A reader of the docs would not know the affordance exists.

## Unanswered

- **No adoption number anywhere.** Nothing counts how often a model writes a script versus inlining it, under either trigger. All five sources give wording, none gives a rate. This is the same gap the other notes report for skills generally.
- **No separate cost figure for authoring a script.** The write is one `write_file` op inside a fork already costed at "~30K tokens / event" (`hermes-skill-loop.md`, vendor claim), so the marginal cost is unmeasured and probably small; the *verification* cost is unbounded because the fork cannot run the code [1]. No source discusses the second.
- **Whether Hermes's self-written scripts are ever executed.** I established the review fork has no shell; I did not establish whether a later foreground session actually runs them, and no telemetry exists to check. Treat "unverified by construction" as a mechanism, not a measured failure.
- **Claude Code `/verify`: script file or prose?** The doc says it records "the install commands, the env vars, the launch script" into `.claude/skills/verify/SKILL.md` [13]. Whether a `scripts/` file is also emitted is not stated and I did not inspect the bundled skill.
- **No independent practitioner report.** `web_search` was unusable for this hole: Exa returns 403 auth on every call, and SearXNG ignored all quoted phrases and returned dictionary and course-site hits for "skill" (4 calls, 2 providers). Every claim above is from a primary page I fetched directly. Whether anyone has reported an agent writing helper scripts into its own skill directory in 2025-2026 is therefore unestablished, not refuted.
