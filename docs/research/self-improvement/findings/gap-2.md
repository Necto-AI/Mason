# What are the actual Skill Invocation Rate numbers in SkillsBench per model–harness configuration (curated vs self-generated arms), and do any 2026 practitioner measurements report per-store read/adoption counts for CLAUDE.md, skills, and memory?

## Answer

SkillsBench v4 *does* publish the instrument the other notes assumed did not exist, and it is literally a read-rate: a curated trial counts as invoked "when its trajectory reads or invokes a Skill under that task's environment/skills" [1]. The curated-arm table runs **99.2% (Codex + GPT-5.5) down to 46.4% (OpenHands + Gemini 3.1 Flash Lite)**, and the harness that shows skills only as a description index the model must choose to open — Claude Code — sits at **68.2% (178/261)**, the lowest of the three dedicated harnesses and 6.1pp below the *same model* in OpenHands (74.3%). The self-generated arm has **no invocation-rate table**; instead the trajectory audit reports that **10 of 12 audited trajectories never list, read, or mention the generated skills** — the paper's own causal story for the −8.1 to −11.5pp deficit is a read-rate story [1]. On the practitioner side, one 2026 measurement project (config-drift-checker, HN item 49468946) does report per-store numbers, but for **effect and trigger rate, not read count**: a guard hook scores 1.00 with / 0.33 without, a conventions skill 1.00 vs 0.50, and the same skill fires on 88% (37/42) of in-scope prompts and 21% (6/29) of out-of-scope ones [3][4][5]. No 2026 practitioner source found reports a per-store *read* count for CLAUDE.md or memory files; only skills are natively instrumented (Anthropic's `claude_code.skill_activated` OTel event) [6].

Counts require a task-bundled Skill; harness-bundled Skills are excluded." — direct. **Confidence: high.**

- **The paper's own headline about this table is that discovery is *not* the bottleneck — for curated skills.** [1] — "Finding 4: Skill discovery is usually not the bottleneck." … "High Skill Invocation Rate does not guarantee high resolution, so the remaining failures often occur after task-Skill access." — direct. **Confidence: high.**
- **The only same-model cross-harness pair in the table is Opus 4.7: Claude Code 68.2% vs OpenHands 74.3% invocation, but Claude Code 61.2% vs OpenHands 53.1% resolution.** [1] — table above. **Support: direct numbers; interpretation mine** — i.e. the *lowest* invocation rate in the dedicated-harness set produces the *highest* resolution among same-model pairs, so invocation rate is not monotonically the driver. **Confidence: medium** (single pair, n=261, and the harnesses differ in more than skill exposure).
- **Invocation rate conditions resolution upward in the weak models and barely at all in the strong ones.** [1] — e.g. Gemini 3.1 Pro on OpenHands: 52.8% overall vs 68.7% | invoked (≈16pp); Claude Opus 4.7 on Claude Code: 61.2% vs 63.9% (≈3pp). **Support: direct numbers, arithmetic (overall − conditional) mine. Confidence: medium.**
- **Harness choice changes what the same model gets from skills, and the paper names the loop as the mediator.** [1] — "GPT-5.5 reaches 67.3% with Skills in OpenHands and 66.5% in Codex; Gemini 3.1 Pro reaches 60.8% in Gemini CLI but 52.8% in OpenHands; Claude Opus 4.7 reaches 61.2% in Claude Code and 53.1% in OpenHands. Skills are therefore not merely extra context: the harness's discovery, prompting, execution, and tool-use loop mediate realized benefit." — direct. **Confidence: high.**
- **v1 of the paper describes the mechanism difference between harnesses explicitly; v4 dropped the sentence.** v1: "Claude Code and Codex read the SKILL.md frontmatter (name and description) to determine relevance; Gemini CLI exposes an `activate_skill` tool that agents invoke explicitly. Instructions never reference which Skills to use—agents must discover and apply them autonomously." [2] — direct for v1; **inference** that this explains the 68.2 / 99.2 / 90.4 ordering. **Confidence: medium** (sentence verified in v1 only; v4 keeps only "using each harness's native loading mechanism" [1]).
- **Curated skills and self-generated packs are not surfaced the same way — this is the paper's stated cause of the self-generated read failure.** [1] — "Unlike curated Skills, which the harnesses surface through their native discovery mechanisms, a pack the solver never discovers can only be dead weight." — direct. **Confidence: high.**

### SkillsBench v4 — self-generated arm

- **There is no invocation-rate table for the self-generated arm.** Table 14 is labelled "on curated-Skills trials" and Appendix K reports only that; D.6/Table 6 report pass rates (43.0→34.9, 46.8→35.5, 36.0→24.5) and the 12-trajectory audit. — [1], absence checked across the full HTML. **Support: direct (negative finding). Confidence: high** that no such table exists in v4.
- **The audit's read-rate number: 10 of 12 trajectories show zero evidence of the artifact.** [1] — "In the pre-baked Codex and Gemini CLI family, 10 of 12 audited trajectories never list, read, or mention the generated skills—the event stream contains zero occurrences of "skill"—so those passes and failures are causally unrelated to pack content." — direct. **Confidence: high for the audit; low as a population rate** (12 trajectories chosen for extreme condition gaps, not sampled).
- **The other two failure modes are write-side displacement and confidently wrong content.** [1] — "In the Claude Code realization the creator and solver scenes share a single trial context. On threejs-to-obj, creator-side work consumed the trajectory before a solver artifact was produced—trial logs end with the SKILL.md write still pending" and "the generated SKILL.md asserts as a "critical gotcha" that the STL coordinates are millimetres and hard-codes a 1000× unit conversion—both solver trials ran the bundled script unquestioned and submitted a mass off by three orders of magnitude". — direct. **Confidence: high.**
- **Confound the report must not paper over:** the Claude Code self-generated runs used a different effort setting than their baseline. [1] — "One deviation: the Claude Code self-generated runs used effort level `max`, whereas its baseline runs used `high`". — direct. **Confidence: high.**

### Practitioner: the HN item that was cited but not used

- **Per-store effect numbers from the config-drift-checker author (HN 49468946, 2026-08-27).** [3] — "On a small Spring Boot service: the guard hook was the only thing that reliably stopped git reset --hard (1.00 with, 0.33 without). The conventions skill changed how a three-file feature came out (1.00 vs 0.50). A negative case confirmed the skill does not fire on a Dockerfile request." — direct. **Confidence: medium** (first-person, 3 runs/case, one repo, author sells the tool).
- **He distinguishes *not found* from *not invoked* as separate failure causes — the closest thing to a per-store read diagnosis in the wild.** [3] — "the report says whether a skill was never invoked (wording) or never found (packaging)" (README) and, on a self-inflicted break, "the skill was *discovered but never invoked*, so fix the wording, not the packaging" [4] — direct. **Confidence: high** that the distinction is implemented; **medium** on how often each occurs.
- **A clean "the artifact never fired at all" measurement: sabotaging a skill description dropped a case from 1.00 to 0.56.** [4] — "We rewrote a skill's trigger description the way a careless PR would. The suite fell from 1.00 to 0.56" — direct. **Confidence: medium.**
- **Trigger rate with counts and CIs (published report, 2026-10-28, haiku 5.5 on Claude Code 2.1.312, 25 prompts × 3 runs = 75 calls, $0.11).** [5] — "spring-boot-conventions fires on 88% of in-scope prompts (37 of 42 runs, 95% CI 75 to 95%); 5 fired no skill; … It fired on 6 of 29 out-of-scope runs (21%, 95% CI 10 to 38%)." Stated targets: "fire on at least 80% in scope, at most 10% out of scope." — direct. **Confidence: high** (raw counts and method published).
- **False fires survive explicit negative wording.** [4] — "Telling the description what the skill is not for stopped some false fires, but not "configure the Gradle build for our Spring Boot project": 3 out of 3, with Gradle named as out of scope." — direct. **Confidence: medium.**
- **A CLAUDE.md-side adoption measurement: two of the author's own rules steered nothing.** [4] — "Running the same cases with no plugin showed why: the model already did constructor injection 3 times out of 3, so two of our rules steered nothing. We cut them, kept their checks as tripwires for the next model" — direct. **Confidence: medium** (n=3 per case).
- **Same six cases across three harnesses, per case.** [7] — Claude Code 2.1.310/Sonnet 1.00; Gemini CLI 0.60.0 0.77; Codex CLI 0.157.1 0.63; "54 runs, none errored", 3 runs per case, 2026-10-24. Per case: `guard-blocks-destructive-git` 1.00 / 0.33 / 0.50; `spring-work-triggers-skill` 1.00 / n/a / n/a; `vue-request-does-not-trigger-skill` 1.00 / 1.00 / 1.00. — direct. **Confidence: high for the scores; medium for the paper's reading** ("Rules carry over, hooks do not. CLAUDE.md is bridged to AGENTS.md for Codex and GEMINI.md for Gemini" [7] — interpretation by the tool author).
- **The instrument now exists natively — for skills only.** Anthropic docs: "Logged when a skill is invoked, whether Claude calls it through the Skill tool or you run it as a `/` command. Event Name: `claude_code.skill_activated`", with attributes `skill.name`, `invocation_trigger` ("`user-slash`, `claude-proactive`, or `nested-skill`"), `skill.source` [6] — direct. **Confidence: high.**
- **Until 2026-08 that primitive was missing, which is why no per-store read counts were published earlier.** Anthropic engineer, closing issue #35319: "For org-scale skill usage data, this is available through OpenTelemetry today: every skill invocation emits a `claude_code.skill_activated` event with the skill name, how it was triggered (user slash command, Claude-initiated, or nested), and where the skill came from (project, user, plugin). Set `OTEL_LOG_TOOL_DETAILS=1` … Closing since the invocation primitive exists" [8] — direct. The reporter's original statement of the gap: "Today, session metadata tracks `"Skill": 3` (aggregate tool count) but not *which* skill was invoked." [8] — direct. **Confidence: high.**
- **Library-size datapoint from the same issue.** [8] — "Our org went from 67 to 183 skills in under a month." — direct. **Confidence: medium** (one org, self-reported).
- **No equivalent read event for CLAUDE.md or memory exists on the same metrics page.** The page documents `claude_code.skill_activated` and plugin-inventory events but contains zero occurrences of "CLAUDE.md" [6]. **Support: direct negative finding on one page; inference** that CLAUDE.md reads are therefore unmeasurable natively (the file is injected as context, not read through a tool — that mechanism part is my inference). **Confidence: medium.**

## Conflicts

- **"Discovery is usually not the bottleneck" vs "10 of 12 never mention the skills."** Both are SkillsBench v4 [1], and they describe different arms: curated packs are surfaced by the harness (46–99% invocation), self-generated packs sit in the filesystem unannounced (≈17% of audited trajectories touch them). Not a contradiction once the arm is named — but it means the brief must never quote the 99.2%/68.2% figures as if they applied to *self-written* skills.
- **Invocation rate vs benefit, same-model.** Claude Code + Opus 4.7 has the lowest invocation rate of the three dedicated harnesses (68.2% vs Codex 99.2%, Gemini CLI 90.4%) yet the highest curated resolution (61.2%) and the *smallest* curated lift (+18.2pp vs +19.7 and +24.8) [1]. So "more reading ⇒ more benefit" fails as a simple monotone claim; the honest statement is that reading is necessary but the lift depends on what is read and what else the harness does.
- **HN comment vs the project's own site.** HN gives "the conventions skill changed how a three-file feature came out (1.00 vs 0.50)" [3]; the site's three-agent run shows the closest case, `spring-controller-follows-conventions`, at Claude 1.00 / Gemini 0.60 / Codex 0.40 [7] — different dates and suites (2026-08-27 post vs 2026-10-24 run). Do not blend the two; quote the HN pair as the ablation and the site table as the cross-agent comparison.
- **Repo location.** HN item 49468946 is posted by user `smartwordworld`, but `github.com/smartwordworld/config-drift-checker` returns GitHub's "Page not found" (and the API returns 404 for that user). The live project is `jameskomo/config-drift-checker` [4]. Anyone citing the HN comment's username as the repo owner will produce a dead link.

## Unanswered

- **No published per-store read count for CLAUDE.md or memory.** Skills now emit `claude_code.skill_activated` [6], and at least four independent tools parse transcripts for per-skill counts [8], but I found no published aggregate of the form "CLAUDE.md was followed/consulted in X% of sessions" or "memory block was read N times". The brief's CLAUDE.md half of the "never read is never written" claim still rests on MemGPT's qualitative under-paging plus GitHub-issue anecdotes.
- **No population-level skill read-rate from real sessions.** Every 2026 figure found is either a benchmark cell (SkillsBench, n=261 per config) [1], a synthetic 25-prompt probe (config-drift-checker trigger map) [5], or a 6-case ablation [3][7]. `usage-check` in that repo counts real invocations per skill from `~/.claude/projects` and labels skills "dead weight: never invoked and no case" [4], but no output of it is published.
- **Whether Claude Code's 68.2% is a mechanism effect or a model/harness effect is not settled.** Only one same-model pair exists (Opus 4.7: CC 68.2 vs OH 74.3) [1], and v4 no longer states how each harness surfaces skills (v1 did [2]). The Claude Code cells are also the ones with the smallest sample of configurations (1 of 18).
- **The self-generated arm's read-rate is only audited, not measured.** 10/12 is a deliberately selected set of extreme-gap trajectories [1]; the true invocation rate for generated packs on all 87 tasks is unreported and would need the same trajectory-counting rule applied at scale.
- **Did not find:** any 2026 measurement that separates CLAUDE.md adherence from skill adherence in the same suite with counts. config-drift-checker comes closest (hook case, skill case, negative case) but its CLAUDE.md evidence is the "two rules steered nothing" observation [4], which is n=3 per case.
