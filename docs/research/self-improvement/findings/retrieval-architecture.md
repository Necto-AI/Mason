# How do good designs get a written note back into context at the right moment: MemGPT/Letta memory blocks and self-editing, Generative Agents' retrieval scoring (recency, importance, relevance), Anthropic's context-engineering guidance on just-in-time retrieval, and any measured comparison of 'index in prompt, body on demand' versus loading everything up front. Include the token cost of turn-start injection and what it displaces.

## Answer
Two working designs exist and they are not the same mechanism. MemGPT/Letta put a small, size-capped, always-resident `label / description / value` block in the prompt and give the model write tools plus a token-pressure warning; everything large lives outside and is paged in by a tool call (paginated, deliberate, often under-used). Anthropic and the Skills format do the opposite for bulk content: only a one-line identifier per item is resident, the body is fetched by a tool read at the moment of use — measured against tools, the resident-index version cost ~8.7K tokens where the load-everything version cost ~77K (85% less, 95% of the window preserved) and raised accuracy (49%→74%) at the price of one extra latency-adding read step. Nothing in this body of work measures that trade for *your own notes* specifically; the closest measurements are for tool definitions (Anthropic) and for document QA / multi-hop lookup (MemGPT), plus Generative Agents' ablation, which only shows that *having* memory retrieval beats not having it.

## Claims
- MemGPT's prompt is three sections: read-only system instructions, a writable "working context", and a rolling FIFO queue. [1] — "Working context is a fixed-size read/write block of unstructured text, writeable only via MemGPT function calls." — direct
- All memory movement in MemGPT is model-initiated through functions, not a framework-side retriever. [1] — "Memory edits and retrieval are entirely self-directed: MemGPT autonomously updates and searches through its own memory based on the current context." — direct
- The write-back moment is created by a threshold warning, not by the model's judgement: at ~70% of the window a system message tells it to save before eviction. [1] — "the queue manager inserts a system message into the queue warning the LLM of an impending queue eviction (a 'memory pressure' warning)" — direct
- Reads are deliberately paginated so a retrieval cannot itself flood the window. [1] — "our memory retrieval mechanisms are designed to be cognizant of these token constraints and implement pagination to prevent retrieval calls from overflowing the context window" — direct
- Measured weakness of the read path: given an index and a paging tool, the model stops early and never reaches the right record even though it is in the index. This is the clearest evidence that "index in prompt" is not the same as "note got read". [1] — "we observe that MemGPT will often stop paging through retriever results before exhausting the retriever database" — direct
- On multi-document QA (NaturalQuestions-Open, 50 questions, same retriever for both arms), the fixed-context baseline is capped by the retriever and degrades under truncation, while MemGPT does not degrade as the document set grows. [1] — "MemGPT's performance is unaffected by increased context length." — direct
- The large, clean win was multi-hop lookup, not single-hop QA: the long-context baseline collapses at depth. [1] — "GPT-4 and GPT-4 Turbo are better than GPT-3.5, but also suffer from a similar dropoff, and hit 0 percent accuracy by 3 nesting levels" — direct
- MemGPT's own framing of why you don't just stuff the window matches Anthropic's: attention is uneven and truncation is lossy. [1] — "they find uneven attention distributions in large context models (the model is more capable of recalling information at the beginning or end of its context window, vs tokens in the middle)." — direct
- Letta memory blocks are the productionized version: always resident, no retrieval step, injected as XML. [7] — "Under the hood, memory blocks are simply prepended to the agent's prompt in an XML-like format." — direct
- That is an explicit design choice against retrieval-on-demand for the small stuff. [7] — "They are always visible - no retrieval needed." — direct
- The per-block `description` is the trigger text: it is what tells the model when to read and when to write. Change the description, change the behaviour. [7] — "The description is the main information used by the agent to determine how to read and write to that block." — direct
- Each block carries a character budget that caps how much of the window memory may occupy; the docs' example uses 5000 chars per block. [8] — "These blocks were editable by the agent, and also restricted to a certain character limit (to limit context window allocation to those memories)." — direct
- The model can see its own budget: current/limit chars are rendered into the block's metadata next to the value. [7] — "<metadata> - chars_current=128 - chars_limit=5000 </metadata>" — direct (verbatim from the documented prompt format)
- Blocks are re-assembled from the database on every call, so "in context" is a compile step, not a cached blob. [8] — "When Letta makes a request to the LLM, the context window is 'compiled' from existing DB state, including current block values." — direct
- Cache economics shape placement: volatile memory goes last in the prompt so the stable prefix stays cacheable. [9] — "placing frequently updated memories near the end of the system prompt to minimize cache invalidation" — direct
- Letta's written policy for the read path is progressive disclosure: keep an index resident, load the body only when the task demands it, then release. [9] — "The Letta agent maintains compact summaries or indexes at all times and loads full content — skill documents, retrieved records — only when a task demands it" — direct
- And it names the failure mode you are designing against: index-everything is not free either. [9] — "stuffing the system prompt with rarely-needed instructions instead of moving them to skills" — direct (listed as a failure mode of a badly managed window)
- Crucially, moving a note out of the prompt is only allowed once retrieval is known to work. [9] — "Context should only be removed from the in-context memory and placed externally if the Letta agent is confident that it has laid the groundwork (e.g. through updating its index) to retrieve the context reliably when necessary in the future." — direct
- Letta's hierarchy has a concrete read ladder: match an in-context memory → read the file's metadata/frontmatter → read the full file → follow its references. [9] — "Observe that the current situation matches what's described in an in-context memory, which references a skill; Read the top-level metadata of the skill..." — direct
- Generative Agents scores every memory on three axes and takes the top of a normalized weighted sum. [2] — "s​c​o​r​e=α_recency·recency+α_importance·importance+α_relevance·relevance" with "all αs are set to 1" — direct
- Recency is an exponential decay per game-hour, so "recent" means recent in the agent's world, not in wall-clock or token count. [2] — "we treat recency as an exponential decay function over the number of sandbox game hours since the memory was last retrieved. Our decay factor is 0.995" — direct (ar5iv renders the constant twice: "0.9950.995")
- Importance is an LLM-assigned 1–10 poignancy score written at creation time, i.e. an extra inference per note. [2] — "The importance score is generated at the time the memory object is created." — direct
- Relevance is cosine similarity between the note's embedding and a "query memory" — the query is itself a memory, not the raw user turn. [2] — "we calculate relevance as the cosine similarity between the memory's embedding vector and the query memory's embedding vector" — direct
- What enters the prompt is however many top-ranked memories fit — the retrieval budget is the window, not a tuned k. [2] — "The top-ranked memories that fit within the language model's context window are included in the prompt." — direct
- Reflections are a second memory type, triggered by accumulated importance rather than by a schedule. [2] — "we generate reflections when the sum of the importance scores for the latest events perceived by the agents exceeds a threshold (150 in our implementation)" — direct
- Generative Agents rejects full-load for the same two reasons Anthropic gives. [2] — "the full memory stream can distract the model and does not even currently fit into the limited context window" — direct
- Its ablation is a retrieval-vs-nothing test, not an index-vs-full-load test: removing memory access entirely costs ~8.7 TrueSkill points and d=8.16 vs the full architecture. [2] — "the full generative agent architecture produced the most believable behavior (μ=29.89; σ=0.72) ... no access to memory, planning, or reflection performed the worst (μ=21.21)" — direct
- The residual errors in that system were read-path errors. [2] — "the most common errors arose when the agent failed to retrieve relevant memories" — direct
- Anthropic's rule: keep identifiers resident, load bodies at runtime through tools. [3] — "agents built with the 'just in time' approach maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools" — direct
- Claude Code is the explicit hybrid: the conventions file is *not* indexed, it is dumped in up front, and everything else is fetched. [3] — "CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time" — direct
- Anthropic names the price of the read step rather than hiding it. [3] — "there's a trade-off: runtime exploration is slower than retrieving pre-computed data" — direct
- And gives the reason full-load loses: attention budget, not window size. [3] — "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases" — direct (Anthropic summarising Chroma's context-rot work)
- Any new token costs something even when the window is big enough. [3] — "Every new token introduced depletes this budget by some amount, increasing the need to carefully curate the tokens available to the LLM." — direct
- Skills hard-code the split: name+description resident for every installed skill, body on read. [4] — "At startup, the agent pre-loads the name and description of every installed skill into its system prompt." — direct
- The second level is the SKILL.md body, triggered by the model deciding relevance; the third is bundled files it opens only if needed. [4] — "If Claude thinks the skill is relevant to the current task, it will load the skill by reading its full SKILL.md into context." — direct
- Because the body is never resident, the amount a skill may bundle is not bounded by the prompt. [4] — "the amount of context that can be bundled into a skill is effectively unbounded" — direct
- Measured index-vs-upfront, tools, 50+ MCP tools across 5 servers: everything up front ≈72K tokens of definitions, ~77K consumed before any work. [5] — "Total context consumption: ~77K tokens before any work begins" — direct
- Same setup with a search tool resident and definitions deferred: ~500 tokens + 3–5 loaded tools ≈3K, i.e. ~8.7K total. [5] — "Total context consumption: ~8.7K tokens, preserving 95% of context window" — direct
- The headline efficiency number for the resident-index design. [5] — "This represents an 85% reduction in token usage while maintaining access to your full tool library." — direct
- What it displaces, stated in tokens: ~68K of a ~200K window that the load-everything design was giving away before the first turn. [5] — "Tool Search Tool preserves 191,300 tokens of context compared to 122,800 with Claude's traditional approach." — direct
- Anthropic's own worst case in production: 134K tokens of tool definitions before optimization, i.e. a majority of the window spent on an index that is mostly irrelevant. [5] — "At Anthropic, we've seen tool definitions consume 134K tokens before optimization." — direct
- Accuracy moved with the architecture, so this is not only a cost result. [5] — "Opus 4 improved from 49% to 74%, and Opus 4.5 improved from 79.5% to 88.1% with Tool Search Tool enabled" — direct
- The same effect measured a second way (MCP tools presented as files read on demand). [6] — "This reduces the token usage from 150,000 tokens to 2,000 tokens—a time and cost saving of 98.7%" — direct
- Anthropic's own heuristic for when a resident index pays: keep a few hot items loaded, defer the rest. [5] — "Keep your three to five most-used tools always loaded, defer the rest." — direct
- And when it does not pay: a small library that is used every session. [5] — "Less beneficial when: Small tool library (<10 tools)" — direct
- The on-demand design buys latency: a search step precedes every use. [5] — "The feature adds a search step before tool invocation, so it delivers the best ROI when the context savings and accuracy improvements outweigh additional latency." — direct
- Researcher inference: at typography sizes like these, a ~10-line index entry per note is ~15–40 tokens, so 100 notes of index ≈1.5–4K tokens — cheap compared with 77K of full bodies, but not free, and it is paid every turn. — inferred
- Researcher inference: the two designs optimise different things. Always-resident blocks (Letta) buy zero-latency, zero-decision recall at a hard char budget and a permanent tax; index+read (Skills, Tool Search, MemGPT archival) buys capacity at the cost of (a) a decision the model can skip and (b) a latency step. MemGPT's under-paging is the empirical evidence that (a) fails in practice. — inferred

## Conflicts
- **Load up front vs index-and-read.** Anthropic pushes JIT for everything except one file: "Rather than pre-processing all relevant data up front, agents built with the 'just in time' approach maintain lightweight identifiers" [3] — but the same post says Claude Code's conventions file is an exception, "CLAUDE.md files are naively dropped into context up front" [3]. Letta resolves it by size and volatility, not by category: memory blocks are "always visible - no retrieval needed" [7] yet "The Letta agent maintains compact summaries or indexes at all times and loads full content ... only when a task demands it" [9]. These are two answers to the same question; neither source reconciles them.
- **Is an index enough?** Anthropic's numbers say yes for tools (85% fewer tokens, +25 accuracy points) [5]. MemGPT's qualitative result says the model does not reliably follow an index to the end: "MemGPT will often stop paging through retriever results before exhausting the retriever database" [1]. Both can be true — a single search hit is one step, exhaustive paging is many — but the disagreement matters for notes, where the model has to decide to go look at all.
- **Retrieval sophistication.** Generative Agents builds a three-term weighted score [2]; Letta's actual product uses none of that for the important memory — it just pins the block in the prompt and lets the description do the work [7]. No source argues they measured the simpler approach against the scored one.

## Unanswered
- **No measurement exists for the exact case in the brief**: a self-written note (skill, profile, log entry) where the comparison is "one-line index in the system prompt" vs "whole file in the system prompt", same task, same model. Tool Search [5] and MCP code execution [6] are the closest proxies and they measure tool definitions, not prose notes. Searched: Anthropic engineering index, Skills post, advanced-tool-use post; arXiv listings for MemGPT/Generative Agents; Letta docs + blog + Context Constitution. Nothing measured this.
- **Does the model actually open the indexed note?** Only qualitative evidence found (MemGPT under-paging [1]; Generative Agents "failed to retrieve relevant memories" [2]). I found no published read-rate / retrieval-trigger-rate for "skill referenced in prompt but never opened". This is the single most decision-relevant gap for the brief's "an artifact that is never read is never written" claim, and it is unresolved.
- **Turn-start cost for prose memory specifically.** Numbers exist for tool definitions (77K / 134K [5]) and per-block char caps (5000 [7][8]) but I found no published token figure for a real memory block set or CLAUDE.md at turn start. My 1.5–4K-per-100-index-lines figure is arithmetic, not a measurement.
- **What the displaced tokens would have bought.** Anthropic asserts degradation ("attention budget", context rot [3]) and cites Chroma's report; I could not fetch the Chroma report itself (research.trychroma.com returned ~60 bytes / JS-only), so the underlying numbers behind "context rot" are unverified here.
- **Cache effects of re-compiling blocks per call** [8] vs the Constitution's "place volatile memory last to minimize cache invalidation" [9]: no numbers on either side.
- **Generative Agents' α weights were never ablated** (all set to 1 [2]); whether importance and recency actually earn their inference cost is untested in that paper.
