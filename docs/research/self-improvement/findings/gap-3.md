# What are Hermes's shipped curator stale/archive defaults on current main — 14/30 or 30/90 — and does `hermes curator status` print the same numbers the docs and issue #77264 claim?

## Answer

**Current main ships 14 / 30** — stale at 14 days unused, archived at 30 — and `hermes curator status` prints exactly those numbers because it calls the same two getters that the automatic transition pass uses. **30 / 90 was also real code, not a doc error**: it was the shipped default from the day the curator landed (2026-04-26) until commit `be2f7e9c36` on **2026-09-12** deliberately tightened it ("curator prunes unused skills at 30 days (was 90), stale at 14"). So #77264's parenthetical "(stale after 30d, archived after 90d unused — ~120d total)" was accurate when the issue was filed (2026-08-03) and has been stale for about two months; `hermes-skill-loop.md:43` (14/30, read at `ea6b6027`) and `field-reports.md:9` (30/90, quoted from #77264) are both correct *for their dates* and there is no live contradiction between code and CLI. The only surviving 30/90 in the repo is one lifecycle bullet in the English docs page (`curator.md:311`), which contradicts the other three places on the same page; an open, unmerged PR (#136040) fixes precisely that line. The latest release tag `v0.22.7` (2026-11-03) also ships 14/30.

## Claims

1. **Current main's constant is 14/30, one line, named.** `DEFAULT_STALE_AFTER_DAYS, DEFAULT_ARCHIVE_AFTER_DAYS = 14, 30` — `agent/curator.py:32` [1] — direct (code). **Confidence: high.**
2. **The config default surface agrees, with prose.** `hermes_cli/config_defaults.py` `"curator": { …, "stale_after_days": 14,  # mark "stale" after this many unused days`, `"archive_after_days": 30,  # move to skills/.archive/ (recoverable) after this many` [2] — direct (code). This file is the source `hermes config` renders from and is actively maintained (30 commits in the last two weeks), so it is not a leftover. **Confidence: high.**
3. **`hermes curator status` prints the numbers from the same getters, so it cannot disagree with the shipped defaults.** `print(f"  stale after:    {curator.get_stale_after_days()}d unused")` / `print(f"  archive after:  {curator.get_archive_after_days()}d unused")` — `hermes_cli/curator.py:96-97` [3]; `get_stale_after_days()` / `get_archive_after_days()` both read `curator.<key>` from config and fall back to the `DEFAULT_*` constants [1] — direct (code). Corroborated by a PR author reading the same lines: "Both readouts echoed the incoherent pair verbatim — `hermes curator status` (`hermes_cli/curator.py:96-97`) and the dashboard status endpoint (`hermes_cli/web_routers/status.py:636`)" [6] — direct. **Confidence: high.**
4. **The transition pass measures both thresholds from the same anchor (`last_activity_at`), so the shipped lifecycle is stale at 14 days and archived at 30 days *from last use*, not 30-then-90-after-going-stale.** `stale_cutoff = now - timedelta(days=get_stale_after_days())`, `archive_cutoff = now - timedelta(days=get_archive_after_days())`, `anchor = _parse_iso(row.get("last_activity_at")) or …`, archive branch tested before the stale branch [1] — direct (code). This is also why #77264's "~120d total" arithmetic does not describe the shipped behaviour: it assumed 90 days *after* going stale. **Confidence: high.**
5. **30/90 was the shipped default for ~4.5 months and was changed on purpose, with a migration.** Commit `be2f7e9c36` (2026-09-12), "feat: curator prunes unused skills at 30 days (was 90), stale at 14": "A skill nobody has loaded in a month is prompt weight, not knowledge, and archival is recoverable (`hermes curator restore`). [4] — direct (commit message + 8-file diff: `agent/curator.py`, `hermes_cli/config_defaults.py`, `config_migrations.py`, `hermes_cli/curator.py`, tests, English + zh-Hans docs). **Confidence: high.**

## Conflicts

1. **Resolved: 14/30 vs 30/90 is a date problem, not a code/docs disagreement.** `be2f7e9c36` (2026-09-12) moved the defaults; #77264 was filed 2026-08-03 against 30/90. `field-reports.md:9` should carry the date of its source. This supersedes `hermes-skill-loop.md` Conflicts item 1's framing ("doc against doc") — the doc line is stale *because* the default changed, and the commit that changed it did edit the docs (4 lines) but missed the lifecycle bullet.
2. **Live: `curator.md` contradicts itself on current main** — `:38`/`:58-59`/`:120` say 14/30, `:311` says 30d/90d. PR #136040 fixes it and is unmerged. Anyone quoting "the docs" can get either number.
3. **Live: `hermes curator status` vs a customized config.** The CLI reports the *resolved* pair, so a profile with `curator.archive_after_days: 60` prints 60. Not a contradiction, but it means "what status prints" is not a fixed number — quote the default plus the readout.
4. **Unresolved ordering bug (not affecting shipped defaults):** nothing enforces `archive_after_days > stale_after_days`, and the archive branch is tested first, so an inverted pair archives a skill without ever marking it stale. With the shipped 14/30 the ordering is correct. PR #122746 (open) proposes `_lifecycle_days()`. Relevant only if the report claims the `active → stale → archived` lifecycle always holds for any config.
