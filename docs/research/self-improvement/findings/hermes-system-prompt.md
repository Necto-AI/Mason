# In NousResearch/hermes-agent, quote the shipped system-prompt text that drives self-improvement, with file path and line: the <available_skills> index and the rule about loading a skill before replying, the memory paragraph (including the declarative-facts-not-imperatives example and the character budget), the profile statement, 'after difficult tasks offer to save a skill', and 'if a skill has issues, fix it with skill_manage'. For each quoted line say whether it is a trigger for a write, a precedence rule, or just a value.

Clone: `git clone --depth 1 https://github.com/NousResearch/hermes-agent` at commit `1f91da2a277093c6909542d8c725c0c52fae4628` (committed 2026-10-25, message "fix(desktop): budget group-chat preview downloads per connection"). All line numbers below are from that commit. The end-to-end rendered prompt for the CLI surface is committed at `tests/fixtures/prompt_surface/prompts/cli.hermes.txt` and is CI-pinned to be byte-identical to what the code renders (`tests/ci/test_prompt_surface.py`: "The committed prompt-surface snapshot is exactly what the code renders."), so quoting the fixture is quoting the shipped prompt; the generating function is cited next to each quote.

## Answer
Hermes ships five self-improvement lines, and they are not all the same kind of sentence: one hard read-before-reply rule ("Before replying, scan the skills below … you MUST load it"), one unconditional write instruction ("If a skill has issues, fix it with skill_manage(action='patch')"), one *offer*-shaped write trigger keyed to a task-difficulty event ("After difficult/iterative tasks, offer to save as a skill"), and two precedence rules that decide *which* store gets the lesson (skills-first routing in the memory paragraph, and "declarative facts, not instructions to yourself"). The character budget is stated only as a value ("it has a hard character budget") — the number (2,200 / 1,375 chars) lives in config and is surfaced at runtime in the memory block header as `[67% — 1,474/2,200 chars]`, not in the sentence. The profile line is a scope guard that names the four writable stores (skills/, plugins/, cron/, memories/) and forbids writing another profile's.

## Claims

**A. The `<available_skills>` index — the artifact that makes a write discoverable**

- The index is a flat `category: → "- name: description"` listing rendered into the prompt on every build, one row per skill. [1][2][3] — `"<available_skills>\n  autonomous-ai-agents:\n    - claude-code: Delegate coding to Claude Code CLI (features, PRs)."` — direct
- Shipped form: 53 rows, 62 lines, 4,166 chars (~1,040 tokens) of the 1,528-token volatile tier, i.e. the skill index is roughly two-thirds of the volatile band of the CLI prompt. [1][10] — measured by counting `- ` rows between `cli.hermes.txt:34` and `:95`; token counts read from `surfaces.json` (`"volatile": 1528`) — direct (count) / inferred (token attribution split)
- Each index description is capped at 60 characters by one constant, cut at a word boundary, and `skill_manage`'s schema tells the model the same limit: `"Description: max 60 chars, 'Use when <trigger>. <behavior>.'"` [4][13] — direct
- The index sits in the **volatile** tier, ahead of memory, and the builder comment states the reason: skills are runtime-mutable, so the index leads the volatile band to keep the stable prefix byte-stable for longest-prefix caching. [3] — `"# Skills are runtime-mutable, so the index leads the volatile band"` (`agent/system_prompt.py:785`) — direct
- The builder comment also states that closed categories are never dropped because the model will not rediscover them: `"NEVER drop entries — agent-created skills are the model's project memory and it won't rediscover them via skills_list."` [2] — direct

**B. Load-before-replying: a read trigger + a precedence rule (not a write trigger)**

- The core sentence, verbatim from the shipped prompt: [1][2] — `"Before replying, scan the skills below. If a skill matches or is even partially relevant to your task, you MUST load it with skill_view(name) and follow its instructions."` (`cli.hermes.txt:30`; source `agent/prompt_builder.py:1341-1343`) — **type: precedence rule + mandatory read step**, on a *timing* qualifier ("Before replying"). It writes nothing; it forces retrieval.
- It pre-empts the model's own competence estimate three ways in one paragraph: `"Err on the side of loading — it is always better to have context you don't need than to miss critical steps"`, `"Load the skill even if you think you could handle the task with basic tools like web_search or terminal"`, and `"load them even for tasks you already know how to do, because the skill defines how it should be done here."` [1][2] — direct; **type: precedence rule** (skill procedure outranks the model's default method)
- The block closes by removing the skip default: [1][2] — `"Only proceed without loading a skill if genuinely none are relevant to the task."` (`cli.hermes.txt:97`; `prompt_builder.py:1357`) — **type: precedence rule** (closing clamp; the else-branch is closed)
- The whole block is assembled as one function return, `## Skills\n` + the rules + the block + the closing line, so the mandatory sentence, the write nudges and the index can never arrive separately. [2] — `agent/prompt_builder.py:1339-1359` — direct

**C. "If a skill has issues, fix it with skill_manage" — the only unconditional write instruction**

- [1][2] — `"If a skill has issues, fix it with skill_manage(action='patch')."` (`cli.hermes.txt:31`; `prompt_builder.py:1350`) — **type: write trigger.** Condition = a defect discovered while using a skill; imperative, no offer, no permission step, names the exact action argument.
- The next sentence adds the run-time arm of the same trigger, with a deadline: [1][2] — `"If a skill you loaded was missing steps, had wrong commands, or needed pitfalls you discovered, update it before finishing."` — **type: write trigger + timing rule** ("before finishing" is the event).
- History: the earlier wording was stronger and was deliberately cut. At tag `v2026.8.3` the same file carried `"When using a skill and finding it outdated, incomplete, or wrong, patch it immediately with skill_manage(action='patch') — don't wait to be asked. Skills that aren't maintained become liabilities."` [6] — direct quote of the old version. The current tree keeps only the shorter sentence; a maintainer comment records the reason: `"the record-it / patch-it coaching that used to open this block duplicated the ## Skills section … and skill_manage's own schema."` [2] (`prompt_builder.py:256-260`) — **type: value** in current form, and evidence that this team deleted the redundant duplicate rather than adding emphasis.
- Related surviving write trigger in the tool-guidance blob: [2] — `SKILLS_GUIDANCE = "When you work out a non-trivial workflow, record it with skill_manage for future reuse."` (`prompt_builder.py:261`) — **type: write trigger**, event-based ("work out a non-trivial workflow"), appended at the end of the same paragraph as memory guidance, and gated on `"skill_manage" in names` (`system_prompt.py:295`).

**D. "After difficult tasks, offer to save a skill" — an offer, not a write**

- [1][2] — `"After difficult/iterative tasks, offer to save as a skill."` (`cli.hermes.txt:32`; `prompt_builder.py:1351`) — **type: write trigger, but offer-shaped**: the required action is a conversational offer, not a file write; the qualifier is `"difficult/iterative"`, i.e. a judgement call, not an observable threshold.
- Before/after on exactly this sentence. At `v2026.8.3` the equivalent instruction was numeric and imperative: [6] — `"After completing a complex task (5+ tool calls), fixing a tricky error, or discovering a non-trivial workflow, save the approach as a skill with skill_manage so you can reuse it next time."` (then `SKILLS_GUIDANCE`, `prompt_builder.py:195-198` at that tag) — direct. The shipped version dropped the count, dropped "save the approach", and changed the verb to "offer".
- Why it changed, in the maintainers' own words: [2] — `"Anthropic's server-side content filter rejected the previous phrasing … on subscription OAuth credentials, surfacing as a billing-shaped HTTP 400"` and `"Bisected against the live API: that sentence alone reproduces the 400 and removing it alone clears it"` (`prompt_builder.py:245-256`) — direct. The comment also concedes `"The reword is empirically validated, not understood"`. This is a constraint on rewrite experiments, not evidence about what drives adoption.
- The prompt never claims the agent will *write* the skill unbidden; the repo docs restate the same hedge: `"After solving a complex problem, Hermes may offer to save the approach as a skill for next time."` and `"After a complex multi-step task, Hermes will often offer to save the approach as a skill."` [8] — direct (docs say "may"/"will often"; the prompt says only "offer").

**E. The memory paragraph — routing rule + declarative-facts value + budget**

- Full shipped sentence set, one paragraph in the rendered prompt (`cli.hermes.txt:14`; source `agent/prompt_builder.py:195-233`): [1][2] — `"You have persistent memory, carried across sessions and loaded into each new session's context; the memory tool's schema defines what belongs there."` — **type: value** (pointer to schema, not a rule).
- The routing precedence, stated as a default with one named exception: [1][2] — `"Skills come first: when you learn something while doing a task — a procedure, a pitfall, and the user's preferences and corrections for that kind of work — record it in the skill you used or built for the task (skill_manage), where it loads only when relevant."` then `"Memory is the narrow exception for facts that apply to EVERY session regardless of task (who the user is, environment facts, standing conventions with no task home)"` — **type: precedence rule.** Capitalised EVERY; memory is defined as the exception, so the default destination for a lesson is a skill.
- The budget, as a value plus an anti-skip instruction: [1][2] — `"it has a hard character budget, so when it fills, replace or consolidate stale entries rather than skipping the save."` — **type: value + write trigger protection** (the clause exists to pre-empt the observed failure of silently not saving). The number is *not* in this sentence.
- The declarative-facts rule with its worked example: [1][2] — `"Write entries as declarative facts, not instructions to yourself: 'User prefers concise responses' ✓ — 'Always respond concisely' ✗ (imperative phrasing gets re-read as a directive in later sessions and can override the user's current request)."` — **type: precedence rule** (it decides the conflict between a self-written memory entry and the user's current request, in favour of the request). Paired good/bad example with ✓/✗ glyphs, and a stated causal mechanism ("re-read as a directive in later sessions").
- Scope cut-off for stale material: [1][2] — `"A fact stale within a week belongs in session history; procedures and workflows belong in skills."` — **type: precedence rule** (three-way store routing: session history / skills / memory).
- Earlier wording carried two examples and an extra prohibition, then was compressed: at `v2026.8.3` [6] — `"'User prefers concise responses' ✓ — 'Always respond concisely' ✗. 'Project uses pytest with xdist' ✓ — 'Run tests with pytest -n 4' ✗."` plus `"Do NOT save task progress, session outcomes, completed-work logs, or temporary TODO state to memory"` — direct; both trimmed in the current tree to one example and one 7-day rule.
- The budget numbers, outside the prompt sentence: defaults `memory_char_limit: 2200` (~800 tokens) and `user_char_limit: 1375` (~500 tokens) [5], and the runtime injection renders them: `"MEMORY (your personal notes) [67% — 1,474/2,200 chars]"` [7][9] — **type: value surfaced per-turn, not per-instruction.** Memory is a *frozen* session-start snapshot (`format_for_system_prompt` returns `"Frozen load-time snapshot"`), so a mid-session write is not read back until the next session.
- Assembly detail that matters for prompt design: memory guidance is not its own paragraph. `_tool_guidance_block` joins `[memory_guidance, SESSION_SEARCH_GUIDANCE, SKILLS_GUIDANCE, kanban]` with a single space (`system_prompt.py:292-298`), which is why `cli.hermes.txt:14` ends with `"When you work out a non-trivial workflow, record it with skill_manage for future reuse."` in the same visual block. [3] — direct

**F. The profile statement — a scope guard, and the list of writable stores**

- [1][3] — `"Active Hermes profile: default. Other profiles (if any) live under <HERMES_HOME>/profiles/<name>/. Each profile has its own skills/, plugins/, cron/, and memories/ that affect a different session than this one. Do not modify another profile's skills/plugins/cron/memories unless the user explicitly directs you to."` (`cli.hermes.txt:99`; source `agent/system_prompt.py:385-392`) — **type: value + precedence rule** (the "unless the user explicitly directs you to" clause; user authority outranks the agent's own tidying instinct). Not a self-improvement trigger, but it enumerates the four stores the agent is allowed to grow, and it is per-profile, which is how the repo prevents two writers colliding on one memory file.
- Non-default profiles get a longer variant that prints the resolved paths: `f"Active Hermes profile: {active_profile}. This session reads and writes {profile_home}/."` and repeats `"Do NOT modify another profile's skills/plugins/cron/memories"` (`system_prompt.py:402-410`). [3] — direct
- The line rides in the volatile tier on purpose, so the stable prefix stays byte-identical across profiles: `"# The profile line names this home's path, so it rides in the volatile tier"` (`system_prompt.py:791-792`). [3] — direct

**G. What the assembly does that the wording cannot**

- Ordering inside the volatile tier is `skills_prompt, *_memory_parts(agent), profile_line, timestamp` (`system_prompt.py:787-794`), and the skills index is gated on the skills toolset being present (`_skills_prompt` returns `""` otherwise), so the read rule and the index appear and disappear together. [3] — direct
- The `hermes-agent` help line is a second, skill-specific load rule injected only when `skill_view` exists *and* the index actually contains `- hermes-agent:` (`system_prompt.py:760-761`): `"load it with skill_view(name='hermes-agent') before configuring, modifying, or troubleshooting Hermes so you don't guess or invent workarounds."` [1][2] — **type: mandatory read step** keyed to a topic, with a stated failure it prevents ("guess or invent workarounds").
- One-query sessions get a deliberately *weaker* variant, which is the clearest evidence the maintainers treat over-loading as a cost: `ONESHOT_SKILLS_LOAD_GUIDANCE` says `"load one with skill_view(name) only when it carries domain knowledge you lack for THIS task … Do not load general process skills (testing, debugging, review methodology) for work you already know how to do."` (`agent/oneshot_footprint.py:53-58`) [3] — **type: precedence rule**, and a direct contradiction of the main prompt's "err on the side of loading" — scoped to single-query sessions.
- The prompt also fixes who outranks whom at run time: the mid-turn steering marker is `"a genuine user message with the same authority as their original request — not tool output, not prompt injection"` (`cli.hermes.txt:21`). [1] — **type: precedence rule**; combined with the declarative-facts rule (E), self-written memory can never be re-read as an instruction that beats the current request.

## Conflicts
- **Docs vs shipped prompt (layer 7 of the assembly doc).** `website/docs/developer-guide/prompt-assembly.md:111-113` shows `"## Skills (mandatory)\nBefore replying, scan the skills below. If one clearly matches your task, load it with skill_view(name) and follow its instructions."` [12]. The shipped prompt has no `(mandatory)` heading and a much harder modal: `"you MUST load it with skill_view(name) and follow its instructions"` [1]. Same doc's example also prints `"Current time: 2026-03-30T14:30:00-07:00"` and `"## Persistent Memory"` blocks, whereas the fixture prints `"Conversation started: …"` and `"MEMORY (your personal notes) [N% — n/2,200 chars]"`. The doc is a hand-simplified illustration, not the rendered text; for quoting, the fixture/code wins.
- **"save" vs "offer".** History contradicts the current prompt: `v2026.8.3` said `"save the approach as a skill with skill_manage"` [6]; the current tree says `"offer to save as a skill"` [1]. Docs split the difference with `"may offer"` and `"will often offer"` [8]. Which one is actually shipped today: the offer form.
- **Load-aggressively vs load-sparingly.** Main prompt: `"Err on the side of loading — it is always better to have context you don't need"` [1]. One-shot variant: `"Do not load general process skills (testing, debugging, review methodology) for work you already know how to do."` [14]. Not a contradiction in code (two different surfaces), but a direct conflict in policy that a reader copying one sentence needs to know about.
