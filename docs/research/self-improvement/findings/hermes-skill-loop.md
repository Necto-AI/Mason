# Trace Hermes's agent-managed skill loop end to end: the skill_manage and skill_view tool schemas and descriptions, what the prompt says about when to create versus patch, the background skill self-improvement nudge (its text, its trigger, which model runs it, whether it can write), and the curator (states active/stale/archived, defaults, pinning, locking, consolidate opt-in, no auto-delete). Name what actually stops the library rotting and where the design still leaks.
## Answer
The foreground prompt only *asks* the agent to save skills ("After difficult/iterative tasks, offer to save as a skill") — the real write pressure lives in a background review fork that fires after ~10 tool iterations, replays the whole conversation on the same warm model, and is told "Be ACTIVE — most sessions produce at least one skill update". What actually stops rot is not prompt wording but four enforcing mechanisms: a read-before-write guard inside the fork, a delete that is only legal with `absorbed_into=<umbrella>`, a deterministic 14d/30d stale/archive transition that runs with no model in the loop, and archive-instead-of-delete plus a JSONL ledger and snapshots for undo. The leaks: the curator only manages skills the *background fork* created (foreground `skill_manage` writes are marked `created_by: learn` and are permanently invisible to it), the consolidation pass is off by default and carries a "fewer than 10 archives = you stopped too early" quota, `skill_view` bumps `use_count` so "unused" mostly measures "never even glanced at", and the strongest threshold-based write nudge was deleted because Anthropic's server-side filter 400'd it.
## Claims
- **skill_view is deliberately thin**: "Load a skill's SKILL.md, or one of its linked references, templates or scripts." [1] — direct. Params: `name` (required), `file_path`. Returns JSON with `content`, `linked_files`, `path`, `skill_dir`, readiness fields.
- **The first skill_view of a skill returns the body plus a `linked_files` dict; a repeat identical view returns a short stub** ("Repeat-view dedup mirrors read_file's unchanged-stub") [2] — direct. Dedup is disabled inside the review fork so the read-before-write guard always sees a fresh load.
- **Viewing counts as using**: `_skill_view_with_bump` calls `bump_view` *and* `bump_use` — "Viewing is actively loading the skill to act on it — that counts as use (the curator's stale timer keys off last_used_at)." [2] — direct. Consequence: a skill the agent merely opens can never go stale.
- **skill_manage's advertised description opens with the affordance, not the schema**: "Create, update or delete skills: your procedural memory for recurring tasks." [3][19] — direct.
- **patch is named as the default, full rewrite as the exception**: "patch (targeted old_string/new_string fix — preferred; content alone REPLACES the whole file, read it via skill_view() first)" [3][19] — direct.
- **Content shape is specified in the tool description itself**: "Write lessons, not logs: imperative rule + why, no PR numbers/dates/incident narration, one rule per lesson, references/ named by topic (extend before adding)." [3] — direct.
- **The call shape is a batch that fails atomically**: "The call is an operations array (a single edit is a list of one); it applies atomically — any failure rolls every touched skill back." [3] — direct.
- **Per-action discriminated shapes exist because a weak model filled the wrong text slot**: comment at the schema — "a 27B model that just used write_file kept emitting file_content on create and the whole batch rolled back (#112677)" [3] — direct.
- **The description is hard-capped at the width the index shows**: `SKILL_PROMPT_DESC_LIMIT = 60`; a create or an edit that *changes* the description over 60 chars is refused; an unchanged legacy over-limit description stays editable [3][4] — direct.
- **skill_manage echoes the compile-time consequence back to the model**: `system_prompt_preview` = "System prompt will show: \"…\" — shorten the description to 60 chars so the index shows all of it." [3] — direct. This is a read-back step the turn cannot skip.
- **The foreground prompt's write instruction is one sentence, in the memory block, with no threshold**: "When you work out a non-trivial workflow, record it with skill_manage for future reuse." [5] — direct.
- **The `## Skills` section teaches load-first and patch-on-contact, and "offer", not "write"**: "Before replying, scan the skills below… you MUST load it with skill_view(name)" / "If a skill has issues, fix it with skill_manage(action='patch')." / "After difficult/iterative tasks, offer to save as a skill." [6] — direct.
- **The strongest create trigger Hermes ever wrote was removed for provider-filter reasons, not design reasons**: "Anthropic's server-side content filter rejects the previous phrasing (\"After completing a complex task (5+ tool calls)…\") on subscription OAuth credentials, and surfaces that rejection as a billing-shaped HTTP 400"; "that sentence alone reproduces the 400 and removing it alone clears it"; "If you rewrite this sentence, re-verify with a subscription OAuth token" [5] — direct.
- **The same block was also dieted as redundant**: "the record-it / patch-it coaching that used to open this block duplicated the ## Skills section … and skill_manage's own schema" [5] — direct.
- **The background review fires off tool iterations, not task difficulty**: `agent._skill_nudge_interval > 0 and agent._iters_since_skill >= agent._skill_nudge_interval and "skill_manage" in agent.valid_tool_names` [7] — direct. `_iters_since_skill` increments per tool iteration and resets to 0 whenever skill_manage is called [8].
- **Default interval is 10, configurable**: `agent._skill_nudge_interval = 10`, override `agent.skills.creation_nudge_interval` [9] — direct. Docs describe this as "~every 10 agent turns" [10] — a doc/code mismatch (counted in tool iterations, not turns).
- **Spawn conditions**: only if there is a final response, the turn was not interrupted, `skip_background_review` is false (cron sets it), and a nudge fired [7]. Fork cost is stated as "~30K tokens / event with no human-in-the-loop benefit" [7] — direct.
- **It runs on the main model by default, with warm cache**: "The review runs on your **main chat model** by default, replaying the conversation" [11]; the fork inherits provider/model/credentials and a byte-identical system prompt and tools[] "so it hits the same prefix cache" [12] — direct.
- **A cheaper model is opt-in and changes the input**: `auxiliary.background_review.model`; when routed elsewhere the fork "replays a compact **digest**" and costs "~3–5×" less [11] — direct quote, but the benchmark is unnamed and unverifiable here (see Unanswered).
- **The nudge prompt is imperative and quota-shaped**: "Review the conversation above and update the skill library. Be ACTIVE — most sessions produce at least one skill update, even if small. A pass that does nothing is a missed learning opportunity, not a neutral outcome." [12] — direct.
- **It carries an explicit preference order, which is the create-vs-patch rule the foreground never gets**: 1) patch a currently-loaded skill, 2) patch an existing class-level umbrella, 3) write a support file under an umbrella, 4) "CREATE A NEW CLASS-LEVEL UMBRELLA SKILL when no existing skill covers the class" [12] — direct.
- **It re-reads before writing, and the guard enforces it**: "Read-before-write (ENFORCED — skill_manage refuses otherwise): before you patch or edit an existing skill's SKILL.md, call skill_view(name) for that skill during this review" [12] — direct. Enforced in `_background_review_read_before_write_guard` [13].
- **It may write but may not delete**: "If you notice two existing skills that overlap, note it in your reply — the background curator handles consolidation at scale. Never delete a skill here." [12] — direct.
- **Write permission is a dispatch-side whitelist, not the advertised tool list**: toolsets `["skills"]` (or `["memory","skills"]` when the memory trigger fired) plus `read_file`/`search_files`; "Write tools (write_file/patch/terminal) stay denied" [12] — direct.
- **The read tools were added because the guard was starving the loop**: "denying read_file/search_files caused a per-review denial storm (~142 denials + ~204 read-before-write refusals over 2 days on one deployment) that starved the self-improvement loop … so almost no patch landed" [12] — direct. Strongest empirical evidence in the repo that a guard without the affordance it needs kills adoption.
- **The nudge prompt spends most of its words on what NOT to write**: an environment-failure/negative-claim/one-off-narrative block, and "Unresolved failures: if the session ended WITHOUT actually finding a working method … do NOT write those attempts up as a 'reliable workflow'" [12] — direct. Rationale given: "these become persistent self-imposed constraints that bite you later".
- **Curator states and thresholds are 14d / 30d, not the 30/90 the same doc states elsewhere**: `DEFAULT_STALE_AFTER_DAYS, DEFAULT_ARCHIVE_AFTER_DAYS = 14, 30`; `DEFAULT_INTERVAL_HOURS, DEFAULT_MIN_IDLE_HOURS = 24 * 7, 2`; `DEFAULT_CONSOLIDATE = False` [14] — direct.
- **The deterministic pass is the part that always runs, with no model**: "Skills unused for `stale_after_days` (14) become `stale`; skills unused for `archive_after_days` (30) are moved to `~/.hermes/skills/.archive/` … This is the always-on pruning behavior — it runs whenever the curator is enabled, with no aux-model cost." [10] — direct.
- **Trigger is idle+interval, not cron**: "The curator is triggered by an inactivity check, not a cron job" — `interval_hours` (7d) since last run AND `min_idle_hours` (2h) idle; first observation on a fresh install seeds `last_run_at` and defers one full interval [10] — direct.
- **The LLM pass is opt-in and told to be aggressive**: `consolidate: false` by default [14]; when on, the prompt is "You are running as Hermes' background skill CURATOR. This is an UMBRELLA-BUILDING consolidation pass, not a passive audit" and "If you end the pass with fewer than 10 archives, you stopped too early — go back and look at the clusters you left alone." [14] — direct. `max_iterations=9999` with the comment "Umbrella-building over hundreds of skills takes 50-100 API calls" [14].
- **The curator fork has no shell, so every mutation is ledgered**: `enabled_toolsets=["skills"]`; "No ``terminal``: a shell mv/cp/rm under the skills tree writes bytes with NO ledger entry, so rollback would restore a hollow skill" [14] — direct. Its prompt repeats: "You have NO terminal access in this pass" [14].
- **Deletion inside the fork requires a verified absorption target, fail-closed**: `_curator_consolidation_delete_guard` refuses `absorbed_into` absent or empty — "the consolidation pass may only archive a skill it has absorbed into an umbrella" — citing that a fail-open version "archived whole clusters of active skills with zero verified consolidations" (#29912) [13] — direct.
- **Autonomous deletes are also refused by ownership**: "Refusing background curator delete … Only curator-managed skills may be archived autonomously" (`created_by == "agent"`), plus pinned/external/bundled/hub guards [13][20] — direct.
- **Nothing auto-deletes**: "never auto-deletes" (docs bold it) — "the worst outcome is archival into `~/.hermes/skills/.archive/`, which is recoverable"; TTL purge is explicit only (`archive_ttl_days: 0` default) [10] — direct. Curator prompt hard rule: "DO NOT delete any skill." [14] — direct.
- **Pinning guards deletion only, and only for agent-created skills**: "Pinning protects a skill from deletion — both the curator's automated archive passes and the agent's `skill_manage(action="delete")` tool call"; "Patches and edits still go through" [10] — direct.
- **Locking is the newer, stronger freeze and gates every agent write path**: "Locking stops the agent from changing a skill at all, while the skill stays readable" (docs bold the middle clause); `skill_manage` refuses patch/edit/write_file/remove_file/delete, `write_file`/`patch` refuse any path inside the skill, `terminal` refuses commands that write there, the curator never archives it, and "The agent cannot unlock it: `terminal` refuses `hermes curator unlock`" [10][15] — direct.
- **The lock is a policy check, not a sandbox**: "a script that writes into the skill through its own logic, or `execute_code`, is not inspected" [10] — direct.
- **The linter is the only size/shape pressure and it never blocks**: rules `incident-log-shape` (≥4 PR/issue refs at ≥0.5/1k chars), `references-sprawl` (>60 files), `oversized-body` (>24,000 chars) — "They warn; they never block a write." [16][17] — direct. Hard caps exist separately (100k chars SKILL.md, 1 MiB per file) [3].
- **A skill written mid-conversation is announced to the model in the same conversation** (the read-back that makes a write observable): "[System: The skills available in this conversation changed after its system prompt was built. Now available (load with skill_view(name) when relevant…)]" [18] — direct. Without it, "a skill installed, created or removed after the prompt was built … never reached the index the model routes on" [18] — direct.
- **The curator's jurisdiction is narrow by construction**: only the background fork sets the marker. "Skills the foreground agent creates via `skill_manage(action="create")` during a conversation (including `/learn`) are **not** marked as agent-created — they are recorded as `created_by: learn`" [10]; a real `hermes curator status` sample shows "foreground-created  78" unmanaged against 43 managed, and "A large library can therefore look fully curated while most of it is untouchable." [10] — direct. The escape hatch is manual: `hermes curator adopt <name>` writes the `created_by: agent` marker by declaration and deliberately does not reset the inactivity clock [10].
- **The curator maps to the `auxiliary.curator` model slot, "auto" = main chat model**, and the fork "uses the auxiliary client and never touches the main session's prompt cache" [14] — direct.
- **Researcher read of where rot is actually stopped**: three enforcement points (hard 60-char description budget at write time, read-before-write inside the fork, `absorbed_into`-gated delete) plus one automatic decay mechanism (14/30 deterministic transition). Wording contributes almost nothing; every one of these is a tool-schema refusal or a scheduled pass. — inferred.
- **Researcher read of the biggest leak**: the writes the *foreground* agent makes — which is where a user-visible "save this as a skill" happens, and where `/learn` lands — are structurally exempt from curation, so the library that actually grows from conversation is the part nothing prunes. The pass that is allowed to grow the library (background fork, `created_by: agent`) and the pass that is allowed to prune it (curator) are the same jurisdiction, so "what I asked for last week" accumulates unchecked. — inferred.
- **Researcher read of the second leak**: `bump_use` on every `skill_view` converts "unused" into "never opened", so a skill that is opened once and misleads every time resets its own staleness clock; the 14/30 decay measures attention, not value. — inferred.

## Conflicts
1. **Curator thresholds, doc against doc.** curator.md's config block and prose say `stale_after_days: 14`, `archive_after_days: 30`, and "skills unused for `stale_after_days` (14) become `stale`; … (30) are moved to `.archive/`" — but the same page's lifecycle bullet says "`active` → (30d unused) `stale` → (90d unused) `archived`". The code resolves it: `DEFAULT_STALE_AFTER_DAYS, DEFAULT_ARCHIVE_AFTER_DAYS = 14, 30`.
2. **Protected built-ins.** The curator prompt says "currently: plan", while curator.md says "The set is currently empty — `plan` … graduated to a built-in `/plan` command". Either the prompt string is stale or the docs are; I did not resolve which (the list is data-driven at runtime).
3. **Turn vs iteration.** curator.md: "during its periodic review pass (~every 10 agent turns)". turn_finalizer.py/turn_iteration_prep.py: the counter is tool-calling iterations, `_iters_since_skill`, reset on any skill_manage call. A 3-iteration turn blocks nothing; a 10-iteration turn fires.
4. **Pin eligibility.** curator.md: "Only **agent-created** skills can be pinned" vs "Any skill that resolves in the profile can be locked". Different scopes for the two protective flags — not a contradiction so much as an asymmetry worth knowing.
5. **Read-before-write: intended as a quality gate, empirically a throttling gate.** The prompt treats it as quality ("Content quoted earlier in the conversation transcript does NOT count"), while the whitelist comment records it as the thing that stopped patches landing at all (~204 refusals) until read tools were whitelisted. Both quotes in the Claims section, both from background_review.py.
