# Prompting a model to run its own harness

## Short answer

Wording decides whether the model knows the affordance exists; mechanism decides whether it gets used. Everywhere in this material that adoption actually happens, the write is fired by something the model cannot skip — a counter that spawns a review pass, a schema that refuses a malformed write, a scheduled transition with no model in it — and the read is fired by text injected at turn start, not by the model preferring its notes to the context it already has. Hermes Agent is the one full harness whose prompt and background passes are both readable, and its only instructions about creating a skill are two lines — "When you work out a non-trivial workflow, record it with skill_manage for future reuse" and "After difficult/iterative tasks, offer to save as a skill" ([cli.hermes.txt](https://github.com/NousResearch/hermes-agent/blob/1f91da2a277093c6909542d8c725c0c52fae4628/tests/fixtures/prompt_surface/prompts/cli.hermes.txt), [prompt_builder.py](https://github.com/NousResearch/hermes-agent/blob/1f91da2a277093c6909542d8c725c0c52fae4628/agent/prompt_builder.py)) — while the writes themselves come from a forked review pass that fires after ~10 tool iterations and is told "Be ACTIVE — most sessions produce at least one skill update, even if small. A pass that does nothing is a missed learning opportunity, not a neutral outcome." ([background_review.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/agent/background_review.py)). Everything that keeps that library from rotting is a refusal or a schedule, not a sentence the model has to believe: a 60-character description budget enforced by `skill_manage`, a read-before-write guard inside the fork, a delete that only works with `absorbed_into=<umbrella>`, and a no-model 14-day/30-day stale→archive transition ([skill_manager_tool.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/tools/skill_manager_tool.py), [skill_manager_guards.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/tools/skill_manager_guards.py), [curator.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/agent/curator.py)).

Two consequences for a system prompt you are about to write. First, the read path has to be involuntary or it does not happen: index-announced *curated* skills get loaded in 68.2% of Claude Code trials and 99.2% of Codex trials, but skills the agent wrote itself that no harness index announces were never listed, read or mentioned in 10 of 12 audited trajectories ([SkillsBench](https://arxiv.org/html/2602.12670)). Second, "the model may call it" is a design smell: MemGPT hands the model an index and a paging tool and observes that it "will often stop paging through retriever results before exhausting the retriever database" ([MemGPT](https://arxiv.org/abs/2310.08560)), and a practitioner who measured his own install found he had invoked his language-server tools "literally once the entire time" ([HN](https://news.ycombinator.com/item?id=48289950)).

## What Hermes actually ships

The prompt is CI-pinned byte-for-byte to what the code renders ([test_prompt_surface.py](https://github.com/NousResearch/hermes-agent/blob/1f91da2a277093c6909542d8c725c0c52fae4628/tests/ci/test_prompt_surface.py)), so quoting the fixture is quoting the product. The load-bearing lines are not the same kind of sentence:

- **A mandatory read, keyed to a moment:** "Before replying, scan the skills below. If a skill matches or is even partially relevant to your task, you MUST load it with skill_view(name) and follow its instructions." It closes its own escape hatch: "Only proceed without loading a skill if genuinely none are relevant to the task."
- **An unconditional patch:** "If a skill has issues, fix it with skill_manage(action='patch')." — the only write instruction in the prompt with no offer and no permission step.
- **A write trigger with a deadline:** "If a skill you loaded was missing steps, had wrong commands, or needed pitfalls you discovered, update it before finishing."
- **An offer, not a write:** "After difficult/iterative tasks, offer to save as a skill."
- **A routing rule and a format rule for memory:** "Skills come first: when you learn something while doing a task — a procedure, a pitfall, and the user's preferences and corrections for that kind of work — record it in the skill you used or built for the task (skill_manage), where it loads only when relevant. Memory is the narrow exception for facts that apply to EVERY session regardless of task" … "Write entries as declarative facts, not instructions to yourself: 'User prefers concise responses' ✓ — 'Always respond concisely' ✗ (imperative phrasing gets re-read as a directive in later sessions and can override the user's current request)."

The index those rules point at is a flat list of `category: → "- name: description"` rows: 53 skills in 62 lines at the commit pinned here, ~4,166 characters of content between the `<available_skills>` tags (about 1,040 tokens) inside a 1,528-token volatile tier — both figures measured at that commit, `1f91da2`, since `main` now reports a different tier total ([surfaces.json](https://github.com/NousResearch/hermes-agent/blob/1f91da2a277093c6909542d8c725c0c52fae4628/tests/fixtures/prompt_surface/surfaces.json)). The character count is a real count of everything between the tags — 53 rows plus 7 category headers, excluding the tags themselves; the token attribution is arithmetic from the tier totals, not a measured per-row cost. That cost is why every description is capped at 60 characters, why `skill_manage` refuses a description over the cap, and why it echoes the consequence back at the model: "System prompt will show: "…" — shorten the description to 60 chars so the index shows all of it."

The background pass is where the volume comes from. It fires when `_iters_since_skill` reaches `_skill_nudge_interval` — default 10, and the counter is tool iterations rather than turns, which is why the docs' "~every 10 agent turns" is a doc/code mismatch ([turn_finalizer.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/agent/turn_finalizer.py), [agent_init.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/agent/agent_init.py), [curator.md](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/website/docs/user-guide/features/curator.md)). It re-runs on the main model with a byte-identical prompt so it hits the same cache, carries a stated cost of "~30K tokens / event", and is graded by an explicit preference order: patch the loaded skill, else patch an existing umbrella, else add a support file, else create a new class-level umbrella. Its tool whitelist is a dispatch-side decision — `["skills"]` plus `read_file`/`search_files`, with "Write tools (write_file/patch/terminal) stay denied".

Two internal disagreements are worth knowing before you copy a sentence out of this product. The main prompt says "Err on the side of loading — it is always better to have context you don't need than to miss critical steps", while the single-query surface ships the opposite rule: "Do not load general process skills (testing, debugging, review methodology) for work you already know how to do" ([oneshot_footprint.py](https://github.com/NousResearch/hermes-agent/blob/1f91da2a277093c6909542d8c725c0c52fae4628/agent/oneshot_footprint.py)). And the developer docs' illustration of the skills layer shows "## Skills (mandatory) … If one clearly matches your task, load it with skill_view(name)" — softer than the shipped modal, "you MUST load it" ([prompt-assembly.md](https://github.com/NousResearch/hermes-agent/blob/1f91da2a277093c6909542d8c725c0c52fae4628/website/docs/developer-guide/prompt-assembly.md)). The doc page is a hand-simplified illustration; the fixture wins.

## The mechanisms, separated from the wording

| Mechanism | What it is | Evidence it moves behaviour | What it costs |
|---|---|---|---|
| Resident index + mandatory read | One line per artifact in the prompt, plus a rule that makes loading the default | Curated skills: 99.2% (Codex/GPT-5.5) down to 46.4% (OpenHands/Gemini 3.1 Flash Lite) invocation, Claude Code 68.2% ([SkillsBench](https://arxiv.org/html/2602.12670)) | ~1,040 tokens per turn in Hermes; the 60-char cap is the tax collector |
| Resident capped block | The whole artifact in the prompt, hard character budget | Letta: "They are always visible - no retrieval needed"; the per-block `description` "is the main information used by the agent to determine how to read and write to that block" ([Letta](https://docs.letta.com/v1-sdk/memory/memory-blocks)) | Permanent token tax and a hard ceiling; Hermes memory is 2,200 / 1,375 chars ([memory.md](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md)) |
| Background pass | A second model call after the work, told to write | "~142 denials + ~204 read-before-write refusals over 2 days on one deployment" starved the loop until read tools were whitelisted — the guard, not the wording, was the binding constraint | ~30K tokens/event (vendor comment, unmeasured); ~$7,000 for SICA's 15 self-improvement iterations ([SICA](https://arxiv.org/abs/2504.15228)) |
| Tool-schema refusal | The write fails unless it is shaped right | `skill_manage` refuses over-60-char descriptions, refuses delete without `absorbed_into`, and a fail-open version "archived whole clusters of active skills with zero verified consolidations" (#29912, quoted in [skill_manager_guards.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/tools/skill_manager_guards.py)) | Model spends turns retrying; three failed memory consolidations in one turn end the retry loop |
| Deterministic lifecycle | A scheduled transition with no model in the loop | 14 days unused → `stale`, 30 → `.archive/`, "the always-on pruning behavior" ([curator.md](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/website/docs/user-guide/features/curator.md)) | Archive-only, so nothing is really removed; recoverable, so no real pressure either |
| Environment read-back | The model is told the world changed | "[System: The skills available in this conversation changed after its system prompt was built. Now available…]" ([skills_index_delta.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/agent/skills_index_delta.py)) — without it a skill written mid-conversation "never reached the index the model routes on" | ~nothing, and it is the only feedback that the write landed |

The distinction worth carrying into your design: **a write is only as durable as the read path that announces it.** Two of the cheapest working designs put the trigger in a tool description rather than in a prompt paragraph. Letta's per-block `description` is the trigger text — "The description is the main information used by the agent to determine how to read and write to that block" — so changing the description changes the behaviour without touching the prompt. Hermes does the same for its log: the `session_search` description carries the situation that should fire it, "Use for questions about past conversations: 'what did we do about X', 'where did we leave Y'" ([session_search_tool.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/tools/session_search_tool.py)). A trigger inside a tool description is resident in the same place as the affordance, cannot get lost in a long prompt, and is the one form of trigger that does not depend on the model having read the right paragraph.

Hermes memory, by contrast, is a frozen session-start snapshot (`format_for_system_prompt` returns "Frozen load-time snapshot"), so a mid-session memory write is invisible until a compaction or a new session — the docs put it as "The system prompt injection is captured once at session start and never changes mid-session", which holds between rebuilds, since `invalidate_system_prompt` reloads memory from disk on compaction and on session switch ([memory.md](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md), [system_prompt.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/system_prompt.py)). Either way the model gets a 2,200-character budget it can fill but not read back in the turn it fills it. The skill index, by contrast, is rebuilt and announced mid-conversation. Same product, two different half-lives for the same act of writing.

## Trigger wording: values versus conditions

The clearest before/after in the corpus is on Hermes's main create trigger, and it went the wrong way for reasons that have nothing to do with adoption. At tag `v2026.8.3` the sentence was numeric and imperative: "After completing a complex task (5+ tool calls), fixing a tricky error, or discovering a non-trivial workflow, save the approach as a skill with skill_manage so you can reuse it next time." ([prompt_builder.py at v2026.8.3](https://raw.githubusercontent.com/NousResearch/hermes-agent/v2026.8.3/agent/prompt_builder.py)). Today it is "After difficult/iterative tasks, offer to save as a skill." The maintainer comment explains why: "Anthropic's server-side content filter rejects the previous phrasing … on subscription OAuth credentials, and surfaces that rejection as a billing-shaped HTTP 400", and "Bisected against the live API: that sentence alone reproduces the 400 and removing it alone clears it." It also concedes: "The reword is empirically validated, not understood." Read that as a constraint on what you may ship, not as evidence about what works. The docs hedge in the same direction the prompt does: "Hermes may offer to save the approach as a skill."

Where the wording is instructive is the shape of the condition. Four shapes exist in the material:

- **Value with no event.** "Agents can also persist their own code as reusable functions. Once an agent develops working code for a task, it can save that implementation for future use" ([Anthropic, code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)). Nothing fires this.
- **Judgement, offloaded.** "difficult/iterative" and "non-trivial workflow" are the model's own estimates, and the estimate is exactly what the prompt elsewhere tries to overrule ("Load the skill even if you think you could handle the task with basic tools").
- **Named event.** "before finishing", "when a skill has issues", "when you work out a non-trivial workflow". These need no threshold and cannot be argued with.
- **Count or quota.** "5+ tool calls" (deleted for provider reasons); the curator's "If you end the pass with fewer than 10 archives, you stopped too early — go back and look at the clusters you left alone" ([curator.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/agent/curator.py)). Crude, and the only quota in the corpus that visibly drives aggressive action.

Two more conditions worth stealing, both from outside Hermes. Claude Code's `/verify` writes a skill file on an *absence* trigger — "When it has to build and drive your app without a recorded recipe, it writes what worked to `.claude/skills/verify/SKILL.md`" — and updates it on a *failure* trigger, arguably the sharpest update rule anywhere: "Claude edits the recorded file only when it steered a run wrong, such as a command that failed or a missing step, so you can commit the file without per-session diffs" ([Claude Code skills docs](https://code.claude.com/docs/en/skills.md)). For script-vs-prose, the model-facing trigger in Hermes is repetition over difficulty — "`scripts/<name>.<ext>` — statically re-runnable actions the skill can invoke directly (verification scripts, fixture generators, deterministic probes, anything the agent should run rather than hand-type each time)" — while the author-facing guides key on fragility: "When a command grows complex enough that it's hard to get right on the first try, a tested script in `scripts/` is more reliable" ([agentskills.io](https://agentskills.io/skill-creation/using-scripts.md)). Only the first is usable by a model mid-task; the others assume eval transcripts.

## What has been measured

Every number below is a *paired score delta*, with-artifact minus without. Not one of these papers measures write-rate or read-rate as an outcome, with the single exception of SkillsBench's invocation table. That gap matters more than any individual result.

**SkillsBench** is the most decision-relevant and the least flattering: 87 tasks, 8 domains, 18 model-harness configurations, paired design. Curated skills raise average pass rate from 33.9% to 50.5% (+16.6pp). Self-generated skills — the agent authors packs with `skill-creator`, then uses them — "land below the no-Skills baseline on all three configurations (-8.1 pp on Claude Code + Opus 4.7, -11.3 pp on Codex + GPT-5.5, -11.5 pp on Gemini CLI + Gemini 3.1 Pro)", while curated skills add +18.2 to +24.8pp on those same configurations. The paper's own causal story is a read-path story: "generated packs the solver never discovers, creator-side authoring that displaces solver work, and confidently wrong pack content", and in the trajectory audit "10 of 12 audited trajectories never list, read, or mention the generated skills". Two caveats the paper states and a summary would drop: the self-generated Claude Code runs used effort `max` against a `high` baseline, and the audit's 12 trajectories were selected for extreme gaps, so 10/12 is not a population rate.

**Library growth hurts through selection, not context length.** Going from a small helpful set to a 202-skill library degrades performance "by up to 21%", while "the context overhead effect remains small and indistinguishable from zero" ([More Skills, Worse Agents?](https://arxiv.org/abs/2605.24050)). Focus beats completeness inside a skill too, though that result is SkillsBench's, not the library-growth paper's: "Focused Skills with at most three modules outperform larger or exhaustive bundles" ([SkillsBench](https://arxiv.org/html/2602.12670)), and "Comprehensive prose is essentially flat while focused documentation yields larger aggregate lift (+0.7 pp vs. +19.0/+21.5 pp)" ([SkillsBench](https://arxiv.org/html/2602.12670)).

**Library Drift** restates the gap and adds the lifecycle diagnosis: "LLM-authored skills deliver +0.0pp gain while human-curated ones deliver +16.2pp", and "unbounded skill accumulation without outcome-driven lifecycle management causes retrieval degradation, false-positive injections, and performance stagnation"; its repair lifts held-out pass@1 "from a 0.258 baseline to a late-window mean of 0.584" on MBPP+ hard-100 over 100 rounds ([Library Drift](https://arxiv.org/abs/2605.19576)). Note the conflict with SkillsBench v4, which reports strictly negative self-authored deltas rather than zero: the notes' reading is that the direction is agreed and the magnitude is version-dependent, and Library Drift cites an earlier aggregate.

**Sentry** is the sharpest result for anyone planning a `profile.md`: "kept in the agent's context, they misfire when their failure is absent, and removing them from an evolving playbook improves performance", and in a controlled test "exposing the full playbook to the agent lowers performance even when relevant lessons remain available on demand" ([Sentry](https://arxiv.org/abs/2610.02994)). That directly contradicts **ACE**, which reports "+10.6% on agents and +8.6% on finance" from an evolving playbook kept in context, and AppWorld 42.4 → 59.4 for ReAct+ACE ([ACE](https://arxiv.org/abs/2510.04618)). The notes' reconciliation is worth keeping: ACE's own context-collapse case study sides with Sentry — at step 60 the playbook held 18,282 tokens at 66.7 accuracy and "collapsed to just 122 tokens, with accuracy dropping to 57.1—worse than the baseline accuracy of 63.7 without adaptation". What survives both is update discipline — ACE merges deltas "deterministically … by lightweight, non-LLM logic" rather than letting the model rewrite the whole artifact — and conditional exposure.

**The 2023 papers are all toy-or-sandbox, and the framing around them is usually wrong.** Voyager's 3.3×/2.3×/15.3× are Voyager-versus-baselines in Minecraft, not library-versus-no-library; the library effect is the ablation ("Voyager w/o skill library exhibits a tendency to plateau in the later stages") and Table 2 zero-shot iteration counts, 19/18/21/18 with the library against 36/30/27/26 without ([Voyager](https://arxiv.org/abs/2305.16291)). Reflexion's 91% HumanEval pass@1 and +22% AlfWorld are 2023 toy-benchmark numbers with no replication found in 2025–2026, but its 8pp ablation is the cleanest write-path/read-path separation in the literature: "self-reflection improves learning by an 8% absolute boost over the episodic memory learning advantage" — i.e. the *text*, not the retry, did the work ([Reflexion](https://arxiv.org/abs/2303.11366)). SICA's abstract claims "from 17% to 53% on a random subset of SWE Bench Verified" while its Table 1 ends at 0.51, dips to 0.14 at iteration 1, and its authors concede "much of the initial improvement we report arises from features speeding up file editing and agent cost" ([SICA](https://arxiv.org/abs/2504.15228)) — quote the direction, not the number.

**Retrieval architecture has hard numbers even though notes do not.** Anthropic's tool-search comparison, 50+ MCP tools: everything up front is "~77K tokens before any work begins" against "~8.7K tokens, preserving 95% of context window" — "an 85% reduction in token usage" — and accuracy moved with it, "Opus 4 improved from 49% to 74%, and Opus 4.5 improved from 79.5% to 88.1%" ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)). Their production worst case: "At Anthropic, we've seen tool definitions consume 134K tokens before optimization." The cost of the index-and-fetch design is a decision the model can skip; MemGPT's under-paging is the empirical evidence that it does.

Practitioner measurements are few but pointed. A published trigger map (25 prompts × 3 runs, Haiku 5.5 on Claude Code) reports one skill firing "on 88% of in-scope prompts (37 of 42 runs, 95% CI 75 to 95%)" and "on 6 of 29 out-of-scope runs (21%)", against their own targets of 80% in-scope and 10% out-of-scope ([trigger report](https://jameskomo.github.io/config-drift-checker/triggers/report.html)). In the same project's README, rewriting a skill's trigger description "the way a careless PR would" dropped the suite "from 1.00 to 0.56" ([config-drift-checker README](https://raw.githubusercontent.com/jameskomo/config-drift-checker/main/README.md)). And there is no native instrument for the conventions file: Anthropic emits `claude_code.skill_activated` with an `invocation_trigger` of "`user-slash`, `claude-proactive`, or `nested-skill`" ([monitoring docs](https://code.claude.com/docs/en/monitoring-usage)), and the same metrics page has no CLAUDE.md or memory read event at all.

## How it fails, in the words of people who ran it

**Skill sprawl, and the reason nobody deletes.** Hermes issue #7816 is the canonical statement: "a learning system that only accumulates and never forgets will eventually collect stale heuristics, prompt clutter, and brittle generalizations." The reporter's own remedy was a refusal: "I would **not** auto-delete by default. Archival is much safer than deletion." Current behaviour is 14 days unused → `stale`, 30 days → archived ([curator.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/agent/curator.py)). There is a live conflict here: the user-facing [curator.md](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/website/docs/user-guide/features/curator.md) documents both 14/30 (three times) and "`active` → (30d unused) `stale` → (90d unused) `archived`"; #77264, filed 2026-08-03, still says "30d, archived after 90d unused"; and 30/90 really was the shipped default from 2026-04-26 until commit `be2f7e9c36` on 2026-09-12 ("curator prunes unused skills at 30 days (was 90), stale at 14"). So both numbers are true of some date, the code is 14/30 today (release `v0.22.7`, 2026-11-03), and the doc bullet is a known bug with an unmerged fix, [PR #136040](https://api.github.com/repos/NousResearch/hermes-agent/issues/136040). Don't quote the docs page.

**Learned helplessness.** After a Linux→WSL2 migration with Playwright missing, Hermes "auto-created a skill called browser-tool-launch-issue"; once Playwright was installed and verified, "the agent continued to avoid browser tools entirely". The skill contained rules like "browser tools do not work" and "even reinstalling the browser does not resolve the issue". Deleting the file, not editing the prompt, restored behaviour: "After manually deleting the negative skill and cleaning the modified skill, the agent immediately resumed normal browser tool usage" ([#6051](https://github.com/NousResearch/hermes-agent/issues/6051)). This is the single most persuasive argument for putting your write trigger behind a background pass with a "do not write" list in it — Hermes's nudge prompt spends most of its words there, including "Unresolved failures: if the session ended WITHOUT actually finding a working method … do NOT write those attempts up as a 'reliable workflow'".

**Self-written notes outranking the user.** "Since memory is permanently present, a single descriptive sentence in memory will consistently overpower the corrective instructions in the skill file." The same report shows the loop closing on itself: "The AI measured the character count of a chapter, found it matched the 'short sentence' rule in MEMORY.md, and concluded: 'This is his style.'" The requested fix was a prompt-level ladder — "Priority 1 direct user prompt, 2 dynamic skills, 3 USER.md, 4 MEMORY.md" ([#145905](https://github.com/NousResearch/hermes-agent/issues/145905)). Caveat: every quote I have is memory-versus-skill or memory-versus-earlier-preference; no report shows a self-written skill beating an *explicit instruction in the current turn*. Unverified, and worth treating as the risk you cannot yet cite.

**The read that does not happen.** With "~200 installed skills", "on a long-lived conversation the model often just doesn't think to load the matching skill, and previously-saved memory stops influencing behavior after some point" — and the reporter's conclusion is a design rule, not a wording fix: "Never rely on a skill the model must remember to load" ([#76307](https://github.com/NousResearch/hermes-agent/issues/76307)). The behaviour when caught is diagnostic: "added a generic screenshot reminder to memory (polluting every future turn) and patched the skill with ASCII art banner, instead of simply executing the rules that already existed" … "The agent's instinct when caught is to create more documentation rather than correct its behavior" ([#49764](https://github.com/NousResearch/hermes-agent/issues/49764)).

**Logs only a few readers want.** The two failure shapes are opposite and both documented. Duplication: a write path with only an exact-duplicate gate left one fact 5× while both stores sat at "99–100% of `memory_char_limit` / `user_char_limit` for weeks" ([#103920](https://github.com/NousResearch/hermes-agent/issues/103920)); on a production install "A **single turn** carried **49 identical stale facts** inside its memory block" and removing them freed "**98,191 tokens**" ([#111205](https://github.com/NousResearch/hermes-agent/issues/111205)). At the other end, an audit trail built for humans: OpenBot's audit rows redact `prompt`, `tool_arguments`, `tool_result` and are append-only by database trigger — "retention removes history, it never rewrites it" — so that table can never serve as memory, which must be rewritable ([OpenBot audit.ts](https://raw.githubusercontent.com/CopilotKit/OpenBot/main/server/src/audit.ts), [audit-retention.ts](https://raw.githubusercontent.com/CopilotKit/OpenBot/main/server/src/audit-retention.ts)).

**Consolidation that eats the thing it consolidates, or cannot read it.** Beyond ACE's collapse numbers: at the 100k write cap Hermes's read wrapper spills to `cache/spillover/` and "The curator cannot read the body, and correctly declines to act on a skill it cannot read", with a run report saying "both already multi-absorption umbrellas (100KB-scale packages, not fully readable this pass due to spillover). Left." ([#135980](https://github.com/NousResearch/hermes-agent/issues/135980)). And `absorbed_into=<umbrella>` "**not persisted** in `.usage.json`", so an archived skill is invisible to discovery and the agent "**re-creates a near-identical skill from scratch**" ([#77264](https://github.com/NousResearch/hermes-agent/issues/77264)).

**Claims that are not writes.** "the agent will cheerfully claim it updated something and not actually do it, or write a one-line stub that satisfies the spec but loses the original signal. Without a verification layer, the vault accumulates plausible-looking entries that quietly drift from reality" — the fix being "treating the agent's self-reported summary as a wish, not a fact. A separate process diffs the actual file system against the claimed changes and flags mismatches" ([HN](https://news.ycombinator.com/item?id=48189475)). Hermes's own docs name the same failure without a number: "Small local models (roughly under 30B parameters) and models with weak tool-calling do this often — they produce the confirmation without the tool call" — a vendor claim, unmeasured in the repo.

**What Hermes does about each.** States (`active`/`stale`/`archived`) plus a deterministic transition; archive-instead-of-delete with `archive_ttl_days: 0` ("never auto-deletes"); **pinning**, which "protects a skill from deletion … Patches and edits still go through" and applies only to agent-created skills; **locking**, newer and stronger — "Locking stops the agent from changing a skill at all, while the skill stays readable", enforced in `skill_manage`, `write_file`/`patch`, `terminal`, and the curator, and "The agent cannot unlock it: `terminal` refuses `hermes curator unlock`" — with the honest caveat that it is a policy check, not a sandbox: "a script that writes into the skill through its own logic, or `execute_code`, is not inspected" ([curator.md](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/website/docs/user-guide/features/curator.md)). Plus a JSONL ledger and pre-run snapshots, and a linter whose rules (`incident-log-shape`, `references-sprawl`, `oversized-body`) "warn; they never block a write".

Two leaks are structural and worth copying carefully around. The curator only manages skills the *background fork* created; foreground `skill_manage` writes and `/learn` are recorded as `created_by: learn` and are "permanently invisible to it" — a real status sample shows "foreground-created 78" unmanaged against 43 managed, and "A large library can therefore look fully curated while most of it is untouchable". And `skill_view` bumps `use_count`, so "unused" mostly measures "never even glanced at": a skill opened once and misleading every time resets its own staleness clock. My reading, marked as inference: the pass allowed to grow the library and the pass allowed to prune it are the same jurisdiction, so the part that really grows from conversation is the part nothing curates.

## `profile.md`: who writes it, and what beats what

There is no consensus, and the disagreement is about authorship, not layout.

| File | Who writes it | When it enters context | Budget | Conflict rule |
|---|---|---|---|---|
| `CLAUDE.md` | "**Who writes it** \| You" — the human | "delivered as a user message after the system prompt" | "target under 200 lines per CLAUDE.md file" | "Claude treats them as context, not enforced configuration"; "if two instructions contradict each other, Claude may pick one arbitrarily" |
| Claude Code auto memory | "Claude" — "As it works, Claude saves four kinds of notes for itself" | "first 200 lines of MEMORY.md, or the first 25KB" | error on overflow, "telling Claude to rewrite the index" | deduped: "It also skips anything your CLAUDE.md files already say" |
| `AGENTS.md` (Codex) | Human, or `/init` on request — "If it does, do not overwrite or modify it" | nearest file in the tree, root one preloaded | "200-400 words is optimal"; byte budget in code | "The closest AGENTS.md to the edited file wins; explicit user chat prompts override everything"; prompt: "Direct system/developer/user instructions … take precedence over AGENTS.md instructions" |
| Hermes `MEMORY.md` / `USER.md` | Model via one `memory` tool; humans via `hermes journey edit` | always, frozen snapshot, 2,200 / 1,375 chars | refusal + retry protocol on overflow | declarative facts only; "Skills come first"; user authority outranks agent tidying |
| `SKILL.md` (agentskills.io) | Author or model; the spec is silent on a profile | name + description resident, body on read | "~100 tokens" metadata, "< 5000 tokens recommended", "under 500 lines" | none — the standard has no field for user facts |

Sources for that table: [Claude Code memory](https://code.claude.com/docs/en/memory.md), [AGENTS.md](https://agents.md/), [Codex prompt](https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/gpt_5_2_prompt.md), [Codex /init prompt](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/assets/prompt_for_init_command.md), [Codex agents_md.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/src/agents_md.rs), [agentskills.io specification](https://agentskills.io/specification.md), [Hermes memory docs](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md).

Three things fall out. First, **the model writing the human's conventions file unprompted is nowhere shipped**: Claude Code's `/init` "suggests improvements rather than overwriting it", its instruction audit changes nothing "until you ask Claude to apply them", Codex's `/init` is a flat prohibition on overwriting, and Cursor's rule generation is user-invoked ("Agent generates the rule file with proper frontmatter"). The one file the model does write unprompted is auto memory, and it is a separate file from the human's.

Second, **only Hermes turns the precedence question into a format rule.** "Write entries as declarative facts, not instructions to yourself" is not politeness — the stated mechanism is that imperatives "get re-read as a directive in later sessions and can override the user's current request". That, plus "Skills come first", plus "A fact stale within a week belongs in session history; procedures and workflows belong in skills", is the closest thing in the corpus to a complete routing table for a self-editing harness: session history for the perishable, skills for the procedural, memory for the facts that apply to every session regardless of task, and the current request above all of it. Claude Code states its conflict rule by disclaiming rather than ranking; AGENTS.md and Codex state it cleanly, but for a file a human wrote.

Third, **repetition across stores does not buy compliance**. One practitioner put the same rule in "CLAUDE.md, in Claude's project 'memory', in global 'memory', in 'skills': it couldn't care less where it was" ([HN](https://news.ycombinator.com/item?id=49299380)); another reports the opposite pull — "I'm trying to resist adding more and more things to CLAUDE.md files" … "Yet if I tell it these things in a prompt during the task, it performs way better" ([HN](https://news.ycombinator.com/item?id=49097308)). Against that, #145905's requested ladder and Jason Liu's practice of keeping "AGENTS.md instructions that tell the model to write things down" with "diffs become a review surface for memory" ([jxnl.co](https://jxnl.co/writing/2026/05/10/codex-maxxing/)) are both live counter-positions. The disagreement is unresolved in the sources; my reading is that it tracks how long the session is, which nobody measured.

Hermes is also the place where the routing table is contradicted by its own docs. The memory page's save list says "**Completed work:** 'Migrated database from MySQL to PostgreSQL on 2026-01-15' → save to `memory`", while the `memory` tool schema's SKIP list routes "completed-work logs, task progress, temporary TODO state (use session_search for those)" ([memory.md](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md), [memory_tool.py](https://github.com/NousResearch/hermes-agent/blob/main/tools/memory_tool.py)). The schema is the text injected on every turn; the notes' reading, shared here, is that the prose is older than the schema.

## What I would write

Fifteen lines of prompt text, each traceable to a finding above. "Skills" here means files in your skills directory; "the log" means the session or decision log; `profile.md` is the always-loaded facts file.

```
## Skills
Before replying, scan the skill index below. If a skill matches or is even partly relevant, load it and follow it; skip only if none are relevant.
When you work out a non-trivial workflow, record it with skill_manage; if a skill you loaded was missing steps or had wrong commands, patch it before finishing.
One rule per lesson: imperative rule plus why. No dates, no PR numbers, no incident narration.
A description is one line under 60 characters — it is all you see next session, so it names the trigger.
If you would otherwise re-type the same code on each use, put it in scripts/ and add one line to the skill saying it exists.
## Memory: profile.md
Skills come first. profile.md is the narrow exception: facts that apply to every session regardless of task — who the user is, environment facts, standing conventions with no task home.
Write declarative facts, not instructions to yourself: "User prefers concise replies" ✓ — "Always reply concisely" ✗.
Imperatives get re-read as directives and can override what the user asks now. The current request always wins.
A fact stale within a week belongs in the log. When the budget is full, replace or shorten an entry; never skip the save.
## Log
After a task that took three or more attempts, or a correction that changed your approach, append one line: what you tried, what failed, why.
Add the index line too — future sessions find this only if it is indexed.
If the session ended without a working method, write nothing.
```

Why these lines and not others. The read rule is first because retrieval is the binding constraint (SkillsBench's 10/12; #76307's ~200 skills). The 60-character description rule belongs in the tool schema as well as the prompt, because the schema is the copy the model cannot route around. "No dates, no PR numbers, no incident narration" is Hermes's `skill_manage` description verbatim in spirit, and it is the write-side fix for the incident-log shape its linter only warns about. The script rule uses the repetition trigger, because it is the only script trigger a model can evaluate mid-task without an eval harness. The declarative-facts rule with the ✓/✗ pair is Hermes's, and the "current request always wins" clause is the #145905 ladder compressed to one sentence — the thing Claude Code admits it cannot guarantee. "Never skip the save" exists because the documented failure is a model silently declining to write when the budget looks full. "Write nothing" after an unresolved failure is the #6051 learned-helplessness fix, and it is the one line most worth having in a background pass rather than the main prompt, since that is where the write volume is.

What I would leave out, on the evidence: a numeric tool-call threshold in the main prompt (deleted upstream for provider-filter reasons, and #76307's complaint is not that writes are rare but that reads are); "be proactive"; any instruction that depends on the model remembering to check its own notes; and a second copy of the rules in a second file. And what I would make automatic rather than prompted: the stale/archive transition (14/30, no model in the loop), the archive-instead-of-delete default, a read-before-write guard on patches, and a diff of what the model *claimed* it wrote against the filesystem.

## What remains open

The honest hole is that **no one has measured whether these prompts get followed.** Hermes contains no adoption metric anywhere — the maintainers' comments prove they iterate wording, but the one documented rewrite reason is an Anthropic content filter, not a number. The repo-internal cost figures ("~30K tokens / event", "50-100 API calls", "~3–5×" for a cheaper review model) are comments and docs prose with no benchmark behind them. SkillsBench's invocation table is the only read-rate instrument in the corpus, and it covers curated skills, not an agent's own notes. Anthropic now emits `claude_code.skill_activated`, which is the right instrument for skills and does not exist for CLAUDE.md or memory.

Three specific unknowns any design will have to guess at. Whether a read-rate predicts a write-rate — the principle "an artifact that is never read is never written" is well supported in mechanism (under-paging, un-announced packs, #76307) and unmeasured as a correlation. Whether a self-written skill has ever beaten an explicit instruction in the same turn: every report I have is store-versus-store or memory-versus-earlier-preference, and the strongest reading of the risk is inferred from #145905's requested ladder rather than from an observed failure. And whether consolidation helps at all in a small library: ACE and Sentry disagree about in-context exposure, Library Drift and Hermes both ship pruning, and the curator's own "fewer than 10 archives means you stopped too early" quota has no test, artifact or log sample confirming or refuting over-merging.

Also unresolved, and cheap to get wrong: the curator threshold conflict above is a date problem, not a disagreement, but it means any number you lift from a Hermes doc page may be two months stale. And the field evidence in this corpus is almost entirely from one product's issue tracker plus a handful of HN comments — no Reddit data was reachable, and the search backend returned `403` on nearly every query across these notes, so the field-report base is thinner than its confident tone suggests.
