# If mason wants connector code, what are the real isolation options in Node, and what does each one actually contain?

*Researched 2026-10-30. All Node quotes are from the current docs (`nodejs.org/api/*.md`, which tracks the main branch, plus the v26 pages); all local experiments ran on the Node in this checkout's shell: `v24.21.0`.*

## Answer

Node has exactly three real boundaries and they nest: nothing (`import` in-process, or `node:vm`, which is the same thing with a fresh global object), a thread in your process (`worker_threads` — contains hangs, contains throws only if you listen, contains heap only approximately, contains no I/O), and a process (child process / utility process / container — contains crash, heap, event loop and, with a user or namespace, fs and network too). `isolated-vm` is the fourth and it buys a V8 heap boundary plus real timeouts inside your process, at the price of a native addon that must be rebuilt per Node major, no module loading, a soft memory limit, maintenance mode since 2024, and a critical guest→host escape in August 2026 — its own README says to put it "in a different nodejs process than other critical infrastructure", which is the answer the OS already gave you. Deno's permission model and VS Code's extension host both confirm the shape that actually ships: capability checks are per-process, not per-module, and the process boundary is what protects the host's responsiveness, not its integrity.

## The options, what they contain, what they cost

| Option | crash | memory | fs / network | host's in-memory objects | cost | who ships it |
|---|---|---|---|---|---|---|
| **In-process `import`** (today's `src/`, jiti/tsx boot-loaded code) | no — an uncaught throw or rejection exits the process by default [5][6] | no — shares the heap; only `--max-old-space-size` on the whole process | full: same uid, same `process.env`, same `~/.mason/service/` | full: the connector *is* the host; can mutate the tool list, the prompt prefix, the projection | zero latency, zero serialisation, best ergonomics; one bad connector owns the server | Home Assistant-style in-tree code, pi extensions, most agent runtimes |
| **`node:vm` context** | no — same process, same event loop | no | full via anything passed in, plus `require` sharing state [1] | full — "not a security mechanism" [1] | `timeout`/`breakOnSigint` "result in new event loops and corresponding threads being started" [1]; no memory cap | nobody, for untrusted code; `vm2` did and was abandoned |
| **`isolated-vm`** | no — a JS-triggered V8 abort takes the process; `onCatastrophicError` says call `process.abort()` [9] | approximate: "more of a guideline instead of a strict limit… 2-3 times this limit" [9] | none out of the box — no fs, no net, no timers, **no module support** [9] | none implicitly: separate isolate, nothing crosses but what you hand over, and every handle you hand over is a hole [9][10] | native addon, compiler at install, `--no-node-snapshot` on Node ≥20, one IVM major per Node major; ~ms isolate create; all marshalling is yours | Screeps, Fly, Algolia, Tripadvisor [9]; **not** a "safe sandbox": GHSA-864f-rcv7-6rh4, ≤7.0.0, CVSS 10, patched 7.0.1/6.2.0 on 2026-08-05/06 [10][11] |
| **`worker_threads`** | **yes if you attach an `'error'` listener** — otherwise the `'error'` becomes an unhandled EventEmitter error and the process dies (experiment [18]); worker exits 1 either way [2] | yes, approximately: `resourceLimits` → `ERR_WORKER_OUT_OF_MEMORY`, worker terminated, parent alive (experiment [18]); but "the process may still abort if it encounters a global out-of-memory situation" [2] | **no** — same process, same uid, full `fs`/`net`/`process.env` | **no** — values cross only by structured clone or `SharedArrayBuffer` [2] | structured clone on every call; worker boot ~10-30 ms; ~few hundred µs per round trip; IPC-shaped API (no live callbacks) | the Node docs themselves [2]; jest-worker and friends; the cheapest shape that survives a hang |
| **`child_process` / Electron `UtilityProcess`** | yes — separate address space, killable, restartable | yes — real, and reclaimable on exit | **no** by default: same uid, same cwd, same env, full fs/net. You get a boundary only by adding a user, a container, or a seccomp profile | no | JSON/stdio or fd IPC; ~50-100 ms+ boot; process supervision code | VS Code's extension host [12][14], every language server, mason's current MCP peer |
| **Container / separate service behind MCP** (today's mason integration) | yes | yes | yes — you choose the mount and the network | no | a container per connector, a restart story, and a protocol that must carry everything | mason today; VS Code language servers |
| **Deno process with `--allow-*`** | yes (it's a process) | yes | **yes, at runtime level** — deny-by-default, scoped per path/host [15] | no | a second runtime; permissions are per-process anyway, so one Deno process = one privilege level | Deno itself, Deno Deploy |

Two structural facts fall out of the table and they are the whole decision:

- **Capability limits are per-process, not per-module.** Deno states it flatly: "All code executing on the same thread shares the same privilege level. It is not possible for different modules to have different privilege levels within the same thread" [15] — and "All JavaScript run in a single Deno process is considered to be part of the same program and is not isolated from itself" [16]. So "a connector that can read `service/` but not `agent/`" is not expressible in Node or Deno without giving each connector its own process.
- **What the process boundary actually buys is responsiveness plus restartability, not secrecy.** VS Code says so in its own docs: the Extension Host exists to stop extensions from "Impacting startup performance", "Slowing down UI operations", "Modifying the UI" [12] — and it explicitly does *not* separate extensions from each other [13].

## Claims

- `node:vm` contains nothing: "The `node:vm` module is not a security mechanism. Do not use it to run untrusted code." — [1] — direct
- A vm context is not even a state boundary: "The `require()` in the above case shares the state with the context it is passed from. This may introduce risks when untrusted code is executed" — [1] — direct
- vm's only containment knob is a synchronous timeout, and it costs threads: "Using the `timeout` or `breakOnSigint` options will result in new event loops and corresponding threads being started, which have a non-zero performance overhead." — [1] — direct
- Worker threads share the process, not just the event loop: "Unlike `child_process` or `cluster`, `worker_threads` can share memory. They do so by transferring `ArrayBuffer` instances or sharing `SharedArrayBuffer` instances." — [2] — direct
- A throw is contained only if the host listens: "The `'error'` event is emitted if the worker thread throws an uncaught exception. In that case, the worker is terminated." — [2] — direct
- Confirmed locally: with an `'error'` listener the parent survived a worker `throw` and the worker exited 1; **without** one, the whole process exited 1 — [18] — direct
- A hang is contained: "Execution may stop at any point as a result of `worker.terminate()` being invoked." — [2] — direct; locally a spinning worker left the main thread's 50 ms interval running (9 ticks in 500 ms) and `terminate()` resolved — [18] — direct
- Worker memory limits are honest but soft: "Reaching these limits leads to termination of the `Worker` instance. These limits only affect the JS engine, and no external data, including no `ArrayBuffer`s. Even if these limits are set, the process may still abort if it encounters a global out-of-memory situation." — [2] — direct; locally `maxOldGenerationSizeMb: 32` produced `ERR_WORKER_OUT_OF_MEMORY`, worker exit 1, parent alive — [18] — direct
- isolated-vm's own comparison marks `worker_threads` as isolated (heap) and multithreaded but leaves **Secure** and **Memory Limits** blank, and leaves **Module Support** blank for itself — [9] — direct (table cells); consequence — a third-party npm/TS connector cannot be `require`d inside an isolate as-is — [9] — inferred
- isolated-vm's memory limit is advisory: "Note that this is more of a guideline instead of a strict limit. A determined attacker could use 2-3 times this limit before their script is terminated." — [9] — direct
- isolated-vm itself disclaims process-level safety: "It's a good idea to keep instances of `isolated-vm` in a different nodejs process than other critical infrastructure." — [9] — direct
- …and that a JS-triggered catastrophic failure is unrecoverable: "If you receive this error you should log the error, stop serving requests, finish outstanding work, and end the process by calling `process.abort()`." — [9] — direct
- isolated-vm is in maintenance mode: "`isolated-vm` is currently in *maintenance mode*. It will continue to be supported for as long as is technically feasible." — [9] — direct
- isolated-vm constrains the host's own runtime: "If you are using a version of nodejs 20.x or later, you must pass `--no-node-snapshot` to `node`." — [9] — direct; and its compatibility matrix is one IVM major per Node major (26.x → 7.x only) — [9] — direct
- isolated-vm's boundary is glue, not V8: "a guest that holds a single `ivm.Reference` can obtain the `ExternalCopy` constructor and trigger the bug, so this breaks isolated-vm's core guest/host boundary" — [10] — direct; affected ≤7.0.0, CVSS 3.1 base 10, patched in 7.0.1 and 6.2.0 — [10] — direct; npm `latest` is 7.0.1, published 2026-08-05, 6.2.0 on 2026-08-06 — [11] — direct
- `child_process` docs make no isolation claim at all; the only security sentence in the whole page is about shell injection ("Never pass unsanitized user input to this function") — [3] — direct (absence of a claim)
- Deno enforces capabilities above the JS layer only: "`--allow-ffi` loads native libraries through FFI or Node-API addons. Deno enforces permissions in the JavaScript layer, but a native library runs as compiled machine code in the same process" — [15] — direct
- Deno: permissions do not partition modules: "All code executing on the same thread shares the same privilege level. It is not possible for different modules to have different privilege levels within the same thread." — [15] — direct
- Deno, like Node, treats the V8 realm as sound and the process as the unit of trust: "We consider the V8 VM to be a secure sandbox." — [16] — direct; "All JavaScript run in a single Deno process is considered to be part of the same program and is not isolated from itself." — [16] — direct
- VS Code's extension host isolates the editor, not extensions from each other: "This isolates extension code from VS Code itself, but it doesn't isolate different extensions from each other." — [13] — direct
- …so one connector can still starve all the others: "an extension can, willingly or not, monopolize the extension host thread, block all other extensions, and make operations appear as unresponsive" — [13] — direct
- What the host is *for*, in VS Code's own words: "The Extension Host in VS Code prevents extensions from: Impacting startup performance / Slowing down UI operations / Modifying the UI" — [12] — direct
- VS Code puts the host in an Electron `UtilityProcess`, one per window, and does not try to stop extensions spawning children: "There is one extension host per window and extensions are free to spawn as many child processes as they require." — [14] — direct
- In-process, the module cache is permanent, so "reload" is a lie: "Modules are cached after the first time they are loaded." — [4] — direct; and a second instance is made by a different query, not by reclaiming the first — "Modules are loaded multiple times if the `import` specifier used to resolve them has a different query or fragment." — [8] — direct; locally: two plain imports returned the same instance (load count 1), `?v=2` gave a **second** live instance (load count 2) — [18] — direct
- In-process, one unhandled rejection is fatal by default: "`throw`: Emit `unhandledRejection`. If this hook is not set, raise the unhandled rejection as an uncaught exception. This is the default." — [5] — direct; locally `node -e "Promise.reject(new Error('boom'))"` exited 1 — [18] — direct
- …and so is one uncaught throw: "By default, Node.js handles such exceptions by printing the stack trace to `stderr` and exiting with code 1" — [6] — direct
- Runtime TypeScript in Node cannot load the way mason's own source does: "Node.js ignores `tsconfig.json` files and therefore features that depend on settings within `tsconfig.json`, such as `paths` or converting newer JavaScript syntax to older standards, are intentionally unsupported." — [7] — direct; locally on v24.21.0 a file containing `enum` failed with `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX: TypeScript enum is not supported in strip-only mode` — [18] — direct; so a boot-loaded connector authored like `src/` (tsconfig `paths`, enums, `.tsx`) needs jiti/tsx, which lands it in the host's own `require.cache` — "Node.js native `require.cache` integration" — [17] — direct
- **Cheapest option that survives a broken connector:** `worker_threads` with an `'error'` listener, `resourceLimits`, and a `terminate()` watchdog; it is the only boundary that keeps the event loop, the crash and (approximately) the heap out of the host while still being one process, one build and no container. What it gives up: all fs/network separation (a connector in a worker holds the server's uid and secrets), live-object contribution (no sharing of the tool registry or the projection — contributions must be serialisable declarations plus RPC), and the guarantee against a native OOM abort. Anything more (per-connector secrets, per-connector network allowlist, a connector that can be killed and restarted without losing the process) requires `child_process` and therefore a protocol — which is what mason already has. — [18]/[2]/[3] — inferred

## Conflicts

- **Does isolated-vm count as isolation you can rely on?** Its README markets it as "environments which are completely *isolated* from each other" and the same file says "Your application must be resilient to these kinds of issues and attacks. It's a good idea to keep instances of `isolated-vm` in a different nodejs process than other critical infrastructure" [9]. The advisory adds that a single handed-over `Reference` sufficed for a full guest→host escape in every version ≤7.0.0 [10]. Reading: the *V8 claim* is accurate and the *operational claim* is "wrap it in a process anyway" — those are consistent, but only if you read the security section, not the tagline.
- **Deno says V8 is a secure sandbox; Node says `vm` is not a security mechanism.** Both are true and about different things: Deno means "we can rely on V8 to keep a realm's JS objects inside the realm, so we only check I/O at the runtime layer" [16]; Node means "a fresh global object is not a boundary against escapes via host objects you passed in" [1]. Do not read Deno's sentence as a defence of in-process plugin isolation — Deno's own next sentence rules that out ("All JavaScript run in a single Deno process is considered to be part of the same program and is not isolated from itself") [16].
- **Worker threads: "isolated" or not?** isolated-vm's comparison table ticks `Isolated` (defined there as "Is garbage collection, heap, etc isolated from application") and leaves `Secure` (defined as "Obstructs access to unsafe nodejs capabilities") blank [9]. Node's docs describe the same object in terms of `SharedArrayBuffer` sharing and `process.env` copies [2]. Not a contradiction — a definitional split, and the split is the whole point: a worker isolates the heap, not the capabilities.
- none found between VS Code's account of "what the extension host prevents" [12] and "what it does not isolate" [13]; those two are the honest pair, and the second is on their wiki rather than the API docs.

## Unanswered

- **Anything about pi's own loader was out of my scope** (it belongs to another searcher): whether pi loads extensions via jiti or dynamic `import`, and whether it does anything beyond a version gate. My claims about out-of-tree loading are about Node's primitives only.
- **Could not establish cost figures with a primary source.** The "~10-30 ms worker boot", "~50-100 ms fork/utility-process boot" and "few hundred µs per message" numbers are orders of magnitude from experience, not measurements I took or a paper I read. I did not benchmark structured-clone vs JSON for a realistic tool payload. If mason's decision turns on per-turn latency of a worker-hosted tool, measure it — that is a half-hour experiment, not a research question.
- **I did not find a primary statement that `worker_threads` is explicitly *not* a security mechanism.** Node's docs simply never claim it is, and isolated-vm's table leaves `Secure` blank [2][9]. I state this as an absence of a claim, not as a Node warning.
- **No primary evidence found for the maintainer quote "with the current architecture there can be process crashes on certain user code"** (attributed to a laverdet GitHub issue by the rivet.dev comparison page). I did not use it; the README's `onCatastrophicError` / `process.abort()` advice [9] supports the same point from a source I could read.
- **Did not investigate** `ShadowRealm` (TC39) as a future in-process option — it is a realm, not a capability boundary, so it would land in the `node:vm` row, but I did not confirm its Node status or stage as of 2026-10-30.
- **Did not investigate** WASM/WASI or QuickJS-as-a-sandbox as candidate runtimes for connector compute. If mason ever wants third-party code with *no* filesystem reach without a container, that is the missing row in my table.
- **Node version drift in mason itself:** `AGENTS.md` says Node 22 with `--experimental-strip-types`, the shell in this checkout reports `v24.21.0`, where stripping is on by default and the flag is a no-op.
