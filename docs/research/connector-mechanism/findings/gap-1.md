# What does mason do today when a version it does not recognise arrives — the event envelope's `v` and Chord's `remote(..., { version: 1 })` — and what exact refusal or behaviour does each produce?

## Answer

There are exactly two version gates in mason today, and they fail in opposite directions. The event envelope is **hard-refused**: `readEnvelope` returns `{ error: '"v" must be the integer 1' }` for any `v` that is not the integer `1` (`src/server/events.ts:109`), the route logs a warning and answers `400` with that string (`src/server/main.ts:574-577`), and nothing is fired — a route test asserts both the `400` and zero hook entries (`test/events.test.ts:383-400`). There is no negotiation, no list of versions mason would accept, and no degrade path: the file's own comment says "one mason does not know is a sender's bug, refused rather than guessed at" (`src/server/events.ts:10-12`). Forward compatibility on this door exists only *inside* v1 — unknown keys are ignored and a v1 sender grows, which the tests pin (`test/events.test.ts:217-222`, `src/server/events.ts:8-9`).

The Chord side is not mason's code at all. `AgentService` declares `version: 1` (`src/shared/contract.ts:202-203`), and the gate that consumes it lives in the vendored library: `bind()` in `vendor/pi/packages/chord/src/contract.ts:326-349` throws `contract_mismatch` when the versions differ and the provider offers no `accepts[consumer.version]` adapter, or when the versions match but the provider's description no longer **covers** the consumer's ("forgotten version bump?"). mason passes no `accepts` anywhere (`grep -rn "accepts" src/` → no hits), so **every** `AgentService` version or shape mismatch is a refusal, with no degradation possible — even though the library provides the mechanism (`contract.ts:321-323`). The only version story mason actually *exercises* end to end is the coarser Chord wire-protocol gate, whose answer to a mismatch is to close the link (`connection.ts:651-663`) and whose only degrade path in this repo is the browser doing `location.reload()` (`src/web/client.ts:66-69`). Beware the asymmetry this hole was opened for: mason's doc `docs/CONNECTOR-PROTOCOL.md:62-67` *claims* a connector contract version story ("refuses the boot with the field's name"), and the code does not implement it — see Conflicts.

## Conflicts

1. **The doc promises a connector-entry version gate the code does not implement.** `docs/CONNECTOR-PROTOCOL.md:63-67` says: "The connector contract's own version is the file's: an entry that uses `state` or `reply` without a mason that knows them refuses the boot with the field's name… A connector built against a newer mason degrades: it loses the channels that mason does not have and keeps the rest, because every channel is declared separately." No such refusal exists: `validate()` returns `{ ...raw, enabled, … }` — every unknown key survives and is ignored (`src/server/integrations.ts:179-183`), and `grep -rn '"state"\|reply\b' src/server/integrations.ts` finds nothing. The `connector-surface-gap.md` table row "any unknown key — survives rewrite, ignored" is the accurate half. So mason's *only* implemented version gate is the envelope's `v`; the connector-entry version story is prose. This is the honest answer to the brief's item 5: mason has one hard version gate and one plan.
2. **The Chord library offers degradation; mason declines it.** `contract.ts:321-323` (`Accepts`/`Adapter`) and `guide.md:155-163` show the intended use (`accepts: { 1: (current) => … }`). mason's `host.serve(AgentService, …)` (`main.ts:160`) passes no `accepts` option, so a version bump on `personal.agent` reaches every stale bundle as `contract_mismatch`. Not a contradiction inside the library — a gap between what the dependency can do and what mason declares.
3. **`connector-surface-gap.md:30` under-describes the row it owns.** The row `| envelope v (1) | contract version | readEnvelope() events.ts:98 | 0 |` gives the mechanism and the prefix cost but not the consequence. The consequence is a `400` + warn + no fire (`main.ts:574-577`, `test/events.test.ts:383-400`), and the citation should be `events.ts:109` for the gate (98 is inside the doc comment). Correcting rather than disputing.
4. **Three version numbers are in play and none of them is named as the host API version.** `PROTOCOL_VERSION = 4` (`wire.ts:24`) gates the link; `AgentService.version: 1` (`contract.ts:202`) gates the contract; `v` in the envelope (`events.ts:109`) gates the event body. A future connector mechanism that says "declare the host API you were built against" has to decide which of these it extends — picking a fourth would be the fourth number in a codebase that has never had a deprecation window for any of them.

## Unanswered

- **Whether a stale browser bundle can actually reach `contract_mismatch` in practice.** The console imports the same module (`src/web/client.ts:5`), and the server serves the bundle, so a mismatch needs a cached old bundle against a new server — untested here, and no test in `test/` mentions `contract_mismatch` (`grep -rn contract_mismatch test/` → nothing). What I can say: the failure would surface as a `gone` reference whose message reaches the error banner (`main.tsx:55-59`), not as a blank page.
- **Whether the envelope's refusal is ever seen by a real sender.** A v2 body gets a `400` with a precise string, but nothing tells the sender which version is current except out-of-band docs; and because the signature is checked first (`main.ts:569`), only a correctly-signed sender can discover the rule at all. Whether that is intended as an authentication property or an accident is not documented.
- **What Figma does with a declared `api` newer than the host.** The manifest reference and `plugin-api.d.ts` document the field and that Figma does not auto-upgrade it; I found no doc stating a refusal, so the "declare-and-pin" reading in claim 23 covers the field only, not the mismatch behaviour.
- **Whether `pi-durable`'s `checkRecordVersion` is reachable from mason at all** (mason gets durable through the harness, so a stored-record version error might surface as a boot failure deep inside the library). `grep` in `src/` finds no call site; I did not trace the harness path.
