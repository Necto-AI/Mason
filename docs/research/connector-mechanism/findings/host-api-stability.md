# How do long-lived hosts version an extension API and retire it without breaking everything — concretely, what mechanism does each use?

## Answer
There are only three real mechanisms, and every host I checked is a mix of them: (a) a **semver range in the manifest that the host checks against its own version at install/scan time** — VS Code (`engines.vscode`, checked in `extensionValidator.ts`) and Chrome (`minimum_chrome_version`); (b) a **two-tier API surface** — a stable tier that is effectively append-only plus a gated unstable tier (VS Code "proposed" APIs, Node's Stability Index) so new work ships without touching the frozen tier; (c) **a scheduled deprecation with a named removal version enforced by policy, not by the loader** — Home Assistant's `breaks_in_ha_version` + 6/12-month minimum periods, which raises a *repair issue to the user* instead of refusing the code. The strongest evidence on whether versioning the API actually worked is that the mature hosts barely ever remove anything: VS Code has shipped ~144 minor releases and has never shipped a 2.0, so its 30 `@deprecated` API members — including one annotated "will be removed in the next major update" — are still in `vscode.d.ts` today; the one host that did force a mass migration (Chrome MV2 → MV3) took 4 years 8 months from first store lockout to full removal and broke working extensions on a date it selected, not on a date their manifest predicted.

| Host | Mechanism (the key, where checked) | What it protects | What it costs the host |
|---|---|---|---|
| VS Code | `engines.vscode` semver range in `package.json`; checked by `validateExtensionManifest` → `isValidExtensionVersion` → `isVersionValid` at scan/install; separate *proposed* API tier gated by `enabledApiProposals` + `--enable-proposed-api`; code runs in a separate extension-host process | Extensions against API that isn't there; the API itself against its own users (the frozen stable tier is why the gating exists) | An API it can never break — "once we introduce an API, we cannot easily change it anymore"; every new idea must ship behind a proposal flag first; ~30 permanently deprecated members it must keep implementing |
| Chrome extensions | `manifest_version` (2 or 3) in `manifest.json` + `minimum_chrome_version`; store-side gate at publish/install, browser-side gate at load | Users from silently broken extensions; Chrome from supporting `webRequestBlocking`/remote code forever | A hard cut-over date it owns and must communicate; it disabled already-installed extensions in users' browsers and unbroke it only for enterprises on a policy |
| Home Assistant | No version gate in the manifest at all. Policy: deprecate first, minimum 6 months (users) / 12 months (developers), name the removal as `breaks_in_ha_version`, surface it as a repair issue / warning log | The user's home: nothing stops working without a warning that names the version it dies in | Removed code lingers for ≥2 releases; every user-facing deprecation costs a repair issue, a `strings.json` key, and a follow-up PR that deletes both |
| Node.js (API surface, for contrast) | No negotiation. Stability Index markers in the docs (`0 - Deprecated`, `1 - Experimental`, `2 - Stable`) + four deprecation kinds with machine-readable codes and runtime warnings | Callers' upgrades: code keeps working and *warns* | Deprecated APIs are implemented indefinitely; a warning channel and `--pending-deprecation`/`--throw-deprecation` flags to maintain |

**(3) What each host does when an extension is built against a newer API than the host offers:**
- **VS Code — refuse.** Not "degrade": the manifest fails validation with `Extension is not compatible with Code {0}. Extension requires: {1}.`, the extension is scanned with `isValid = false`, and invalid extensions are excluded from the list the host works from unless the caller explicitly asks for invalid ones. The docs frame the same gate as an install filter: "ensure the extension only gets installed for clients that contain the API you depend on."
- **Chrome — refuse at install, then go quiet.** `minimum_chrome_version` is not honoured by degrading: the store shows "Not compatible" instead of an install button, and for existing users "Existing users of your extension won't receive updates when the `minimum_chrome_version` is higher than their current browser version. This happens silently" — i.e. the extension keeps running at an old version forever rather than failing.
- **Home Assistant — ignore, then fail at runtime.** I found no minimum-host-version key in the integration manifest (`loader.py` only reads `version` as its own version and returns `None` when absent), so a custom integration written against a newer core is loaded and raises at import/attribute time.
- **Node — ignore.** There is no host/extension boundary at all; experimental APIs are simply marked "not subject to semantic versioning rules" and removed in a major.

**(4) Does versioning the API actually work?** For VS Code the honest reading is that versioning exists to make *additive* change cheap and *subtractive* change almost impossible. Evidence, all checked 2026-10-30: stable VS Code is `1.144.0` (so ~144 minor releases, ten years, no 2.0); `vscode.d.ts` in `main` carries 30 `@deprecated` markers and not one of them has been deleted — `workspace.rootPath` is still there (`export const rootPath: string | undefined;`), and `TextEditor.hide()` still carries "@deprecated ... will be removed in the next major update." with no major ever arriving. The deprecation *policy* the docs state is not "we remove on a schedule" but the inverse: "We give our best effort to avoid breaking API changes, and extension authors could expect published extensions to continue to work. However, this puts great limitation on us: once we introduce an API, we cannot easily change it anymore." The proposed-API tier is the workaround for that self-imposed freeze, and 185 `vscode.proposed.*.d.ts` files exist against 1 stable `vscode.d.ts` — the ratio is the cost.

## Claims
- VS Code's version key is `engines.vscode`, a semver range, and it is mandatory — "An object containing at least the `vscode` key matching the versions of VS Code that the extension is compatible with. Cannot be `*`." [1] — "An object containing at least the `vscode` key matching the versions of VS Code that the extension is compatible with. Cannot be `*`." — direct
- The field does double duty as an install filter and an API-existence claim — "ensure the extension only gets installed for clients that contain the API you depend on" [2] — "ensure the extension only gets installed for clients that contain the API you depend on" — direct
- A caret range is the documented way to say "this API set and later" — "A value of `^1.8.0` means that your extension is compatible with VS Code `1.8.0` and onwards" [2] — "A value of `^1.8.0` means that your extension is compatible with VS Code `1.8.0` and onwards" — direct
- The runtime check lives in the host, not the marketplace: `validateExtensionManifest` → `isValidExtensionVersion` → `isVersionValid` [3] — "export function isValidExtensionVersion(productVersion: string, productDate: ProductDate, extensionManifest: IExtensionManifest, extensionIsBuiltin: boolean, notices: string[]): boolean" — direct
- Mismatch is an *error*, worded as a refusal — "Extension is not compatible with Code {0}. Extension requires: {1}." [3] — "Extension is not compatible with Code {0}. Extension requires: {1}." — direct
- The host forces the *major* to be pinned, i.e. the major is declared the compatibility boundary — "force that major must be specific" [3] — "force that major must be specific" — direct
- Invalid extensions are dropped from the scanned set rather than loaded optimistically — "if (!scanOptions.includeInvalid && !extension.isValid)" [4] — "if (!scanOptions.includeInvalid && !extension.isValid)" — direct
- Purely declarative extensions skip the version check entirely — "No version check for builtin or declarative extensions" [3] — "No version check for builtin or declarative extensions" — direct
- Proposed APIs are a second, deliberately unstable tier — "They are **subject to change**, **only available in Insiders distribution** and **should not be used in published extensions**." [5] — "subject to change, only available in Insiders distribution and should not be used in published extensions" — direct
- The reason proposed APIs exist is that stable APIs can never be revised — "once we introduce an API, we cannot easily change it anymore" [5] — "once we introduce an API, we cannot easily change it anymore" — direct
- Proposals are opted into per name in the manifest — "To your `package.json`, add `"enabledApiProposals": ["<proposalName>"]`." [5] — "add `"enabledApiProposals": ["<proposalName>"]`" — direct
- Gating is enforced by an allowlist of extension ids, not by a flag an extension can set for itself — "// NEW world - product.json spells out what proposals each extension can use" [6] — "NEW world - product.json spells out what proposals each extension can use" — direct
- Running out of sources or with `--enable-proposed-api` lifts the gate — "always allow proposed API if --enable-proposed-api is provided without extension ID" [6] — "always allow proposed API if --enable-proposed-api is provided without extension ID" — direct
- Extensions run in a separate host process with its own runtime (Node or WebWorker) — "The **Extension Host** is responsible for running extensions." / "Node.js - Extensions are running in a Node.js runtime." [7] — "Node.js - Extensions are running in a Node.js runtime." — direct
- The proposed-API surface is roughly two orders of magnitude larger than the stable surface: 185 `vscode.proposed.*.d.ts` files vs one `vscode.d.ts` in `src/vscode-dts` [8] — "total files 187, proposed 185" (counted from the GitHub contents API, 2026-10-30) — direct
- VS Code stable is at `1.144.0` — the major has never moved past 1 (checked 2026-10-30) [9] — "["1.144.0","1.143.1","1.143.0",...]" — direct
- `vscode.d.ts` carries 30 `@deprecated` markers and, after ten years, none of the members have been deleted; `workspace.rootPath` survives [10] — "@deprecated Use {@linkcode workspace.workspaceFolders workspaceFolders} instead." followed by "export const rootPath: string | undefined;" — direct
- At least one deprecation promises a removal that the version history says cannot have happened — "@deprecated ... This method shows unexpected behavior and will be removed in the next major update." [10] — "This method shows unexpected behavior and will be removed in the next major update." — direct
- VS Code's stated policy is compatibility-first, with removals admitted as self-limitation — "We give our best effort to avoid breaking API changes, and extension authors could expect published extensions to continue to work." [5] — "We give our best effort to avoid breaking API changes, and extension authors could expect published extensions to continue to work." — direct
- VS Code also has a *package-level* deprecation mechanism separate from API versioning: a deprecated extension is greyed out and can be pointed at a replacement, with no API change at all [11] — "The deprecated extension will be rendered with a dimmed strike-through text in the UI" — direct
- Chrome's break is keyed on `manifest_version`, not a semver range — V2 and V3 are different platforms, and the retirement was a calendar, not a range — "Chrome 138 is the final version of Chrome to support Manifest V2 extensions (when paired with the `ExtensionManifestV2Availability` key)." [12] — "Chrome 138 is the final version of Chrome to support Manifest V2 extensions" — direct
- Chrome started by closing the distribution channel, four and a half years before the kill: January 2022 "Chrome Web Store stopped accepting new Manifest V2 extensions with visibility set to "Public" or "Unlisted"." [12] — "Chrome Web Store stopped accepting new Manifest V2 extensions with visibility set to Public or Unlisted" — direct
- Then a warning banner (June 2024), then disable-with-re-enable (31 March 2025), then disable permanently (24 July 2025), then full store removal (31 August 2026) [12] — "All remaining Manifest V2 extensions have been removed from the Chrome Web Store." (Aug 31st 2026) — direct
- The final step is irreversible for the user — "Users can no longer turn them back on." (Jul 24th 2025, Chrome 138) [12] — "Users can no longer turn them back on." — direct
- Enterprise got a one-year, policy-keyed extension — "Enterprises using the `ExtensionManifestV2Availability` policy ... will have one additional year - until June 2025 - to migrate" [13] — "will have one additional year - until June 2025 - to migrate" — direct
- The MV3 timeline slipped between announcement and enforcement: the May 2024 post said pre-stable would run "at least a month" before stable rollout, while the stable disable landed in October 2024 [13][12] — "We expect it will take at least a month to observe and stabilize the changes in pre-stable" (May 2024) vs "We will now begin disabling installed extensions still using Manifest V2 in Chrome stable." (9 Oct 2024) — direct
- Chrome's forward-compat answer for a newer API is `minimum_chrome_version`, and it refuses rather than degrades — "the Chrome Web Store will show a "Not compatible" message in place of the install button" [14] — "the Chrome Web Store will show a "Not compatible" message in place of the install button" — direct
- But for already-installed users the failure mode is silent staleness, not an error — "Existing users of your extension won't receive updates when the `minimum_chrome_version` is higher than their current browser version. This happens silently" [14] — "This happens silently so you should exercise caution" — direct
- Home Assistant's mechanism is a *policy with a clock*, not a version gate — "Anything you remove has to be deprecated first." [15] — "Anything you remove has to be deprecated first." — direct
- The clocks are explicit: 6 months for user-facing surface, 12 months for anything a custom integration can call — "Users: YAML configuration, actions, entities, attributes, integrations 6 months / Developers: constants, helpers, entity properties, platform APIs that custom integrations use 12 months" [15] — "A deprecation period can be extended when the ecosystem has not caught up yet, but it is never shortened." — direct
- The removal version is a declared, calendar-versioned field, and the API validates its format — "Name the release in which the removal happens as `breaks_in_ha_version`, in the version format, like "2027.1.0"" [15] — "Name the release in which the removal happens as breaks_in_ha_version" — direct
- `breaks_in_ha_version` is a first-class argument of the repair-issue API and is format-checked against the calendar-version strategy at call time [16] — "breaks_in_ha_version: str | None = None" then "AwesomeVersion(breaks_in_ha_version, ensure_strategy=AwesomeVersionStrategy.CALVER)" — direct
- Severity encodes whether the old thing still works, which is how HA distinguishes "warning" from "already broken" — "Use IssueSeverity.WARNING as long as the old behavior still works." [15] — "Use IssueSeverity.WARNING as long as the old behavior still works." — direct
- Developer-facing removals in HA get a warning log attributed to the offending integration instead of a user repair issue [15] — "These mechanisms log a warning attributed to the offending integration." — direct
- HA has no minimum-host-version key in the integration manifest: `loader.py` reads `version` only as the integration's own version and returns `None` when it is absent [17] — "if "version" not in self.manifest: return None" — direct (absence of a min-host gate is inferred from reading `loader.py` and the manifest reference, not stated)
- Node's answer is documentation-level stability tiers, not negotiation — "Stability: 1 - Experimental. The feature is not subject to semantic versioning rules. Non-backward compatible changes or removal may occur in any future release." [18] — "Stability: 1 - Experimental. The feature is not subject to semantic versioning rules. Non-backward compatible changes or removal may occur in any future release." — direct
- Node grades deprecation rather than gating it — "Node.js uses four kinds of deprecations: Documentation-only, Application (non-`node_modules` code only), Runtime (all code), End-of-Life" [19] — "Node.js uses four kinds of deprecations: Documentation-only, Application (non-`node_modules` code only), Runtime (all code), End-of-Life" — direct
- Node lets the operator turn a deprecation into an error, which is the closest thing it has to a gate — "When the `--throw-deprecation` command-line flag is used, a Runtime deprecation will cause an error to be thrown." [19] — "When the `--throw-deprecation` command-line flag is used, a Runtime deprecation will cause an error to be thrown." — direct
- Grade: for a host that must not break a working system, the VS Code shape (range + frozen tier + proposal gate) is the one with a decade of evidence behind it; the Chrome shape only works if the host owns the client and can force an upgrade date; the HA shape presupposes an out-of-process boundary where failure is containable and a user who can be notified. — inferred from [1]–[17]

## Conflicts
1. **VS Code promises it will not break, and annotates removals anyway.** Using Proposed API: "We give our best effort to avoid breaking API changes, and extension authors could expect published extensions to continue to work." [5] — versus current `vscode.d.ts`: "@deprecated ... This method shows unexpected behavior and will be removed in the next major update." [10]. Both sentences are live in `main` at 2026-10-30; the reconciliation ("next major update" never came, because stable is 1.144.0 [9]) is my inference, not a stated policy. No document states a removal schedule, and none states that removals never happen.
2. **Chrome's announced schedule versus its actual schedule.** May 2024: "We expect it will take at least a month to observe and stabilize the changes in pre-stable before expanding the rollout to stable channel Chrome" [13] — versus the timeline entry for 9 October 2024 announcing the stable disable [12]. Roughly four months elapsed, not one. This matters because it is the observed cost of a forced migration: the date moved later, not earlier.
3. **HA's deprecation floor is a policy the loader does not enforce.** "A deprecation period can be extended when the ecosystem has not caught up yet, but it is never shortened." [15] — but nothing in `loader.py` [17] or the HA integration-manifest reference (https://developers.home-assistant.io/docs/creating_integration_manifest/, fetched 2026-10-30, no host-version key present) implements a minimum-version or minimum-age check. The mechanism is reviewer discipline plus a repair issue; a removal PR that skips the period is a review failure, not a load failure. (Interpretation; the docs assert a rule, the code shows no enforcement — I did not find any CI check for it.)
4. **"Versioning the API worked" is contested by construction.** VS Code's evidence says versioning works in the sense that nothing breaks (30 deprecations, zero removals, 1.x for a decade) [9][10]; Chrome's evidence says the version field was irrelevant to the actual retirement, because the change was not expressible as a range at all — MV3 is a different platform, so the mechanism became a calendar [12]. These are not contradictory facts but they support opposite conclusions about whether a version range is the mechanism that protects you.
