# Does Claude Code's mods capability table actually bound what a mod can reach — and what is `environment 2`?

## Answer
Partly, and not in the way the prose implies. The repository publishes **no validator and no worker source** — `mods/` is four built-in plugins plus one generated declaration file, `mods/types/claude-code.d.ts` (13,440 lines, written by `/plugin-types` from a shipped build); `claude plugin validate`, the scanner and the hooks worker live in the closed binary. What the declarations *do* establish, better than the docs, is the shape of the bound: the `$` table removes **ambient** authority (no Node, no `require`, no `fetch`, no `eval`/`new Function`, no `WebAssembly`, timers only through `$.clock`) and enforces the enumeration at load ("spells `on`, `$` or `$.env` other than literally does not load") — but it does **not** bound reach. `$.fs` reads any absolute path as given ("where one may go is an `fs.*` hook's to say"), `$.process.run` runs as the user, and everything a mod does *without* a `$` call — rewriting an event and passing it on, returning a draw tree, hooking `*` — is invisible to the scan. So the table bounds **verbs**, not objects; object-level policy is a hook chain that fails open when it throws. `environment 2` is not a host-API version: it is a per-plugin environment ordinal inside one shared worker (built-ins log `native, environment 1`), documented nowhere by Anthropic and absent from both the declarations and the shipped changelog.

## Claims

### 1. What the repo actually contains — the hole's premise is half false

1. **Claim:** the published `mods/` tree is plugin source only: `mods/types/claude-code.d.ts`, a `tsconfig.json`, four plugin folders (`sec-default`, `diff`, `telemetry`, `agents-md`), and their `tests/`. No scanner, no worker, no loader. **Sources:** [1] repo tree (`GET /repos/anthropics/claude-code/git/trees/main?recursive=1`, 1,966 paths, `truncated: false`) and [2]. **Support:** direct. **Confidence:** high.
2. **Claim:** the declarations say what they are: generated, not the implementation. "Written by `/plugin-types`; regenerate with that command after an update rather than editing. The first line names the Claude Code version that wrote it." **Sources:** [3] lines 1–8. **Support:** direct. **Confidence:** high.
3. **Claim:** the file's own header names the validator as the other half of one mechanism — "…`claude plugin validate <dir>` is the other half: it reads a plugin's manifest and its hooks module's source the way the engine will and reports what the module hooks and calls and everything the engine would refuse, before any session loads it." **Sources:** [3] lines 7–10. **Support:** direct (vendor claim about its own closed code; the code path itself is unreadable). **Confidence:** medium — high that the sentence says it, medium that it holds for every refusal.
4. **Claim:** the declarations are stamped **EARLY ACCESS** with no compatibility promise: "EARLY ACCESS: this surface may change between releases without notice." **Sources:** [3] line 4. **Support:** direct. **Confidence:** high.
5. **Claim:** the published declarations lag the shipped build. The header says it was written by Claude Code **2.1.277**; the repository's `CHANGELOG.md` head entry as read today is **2.1.314**, and the last commit touching `mods/types/` is `bf2323b3`, 2026-10-13. **Sources:** [3] line 1, [4] line 3, [2] (commit list via API). **Support:** direct (both files read from the same HEAD). **Confidence:** high for the two version strings; the causal claim "the types you can read are not the types of the binary you run" is a **researcher inference**.

### 2. What the declarations say the bound is, and where it stops

6. **Claim:** the module environment is an allowlist of globals, stated exhaustively: "The globals of a hooks module's environment: these and no others (no DOM, no Node). No code generation either: `eval` and `new Function` over a string throw, and there is no `WebAssembly` (deliberately; a module that needs compiled code runs it in a process of its own through `$.process.run`)." Timers are absent too; a mod waits on `$.clock`. **Sources:** [3] lines 11570–11578. **Support:** direct. **Confidence:** high as a statement of intent in vendor source; unverified against the runtime.
7. **Claim:** the enumeration is a **load gate**, not a lint — the scan result is typed as host data handed to the gate: "What a hooks module uses, as the host scanned its source before loading it: the same lists `claude plugin validate` prints and the host's rule reads. **Exact**, since a module that spells `on`, `$` or `$.env` other than literally does not load." **Sources:** [3] lines 6280–6287 (`PluginRegisterUses`). **Support:** direct. **Confidence:** high.
8. **Claim:** each such literalness rule is stated as a refusal with the line it names: a computed surface-module path ("a variable, a template with a substitution or a computed path as `module` is refused at load, naming the line"); env names ("`get` and `set` take the variable's name as a string literal, so what a module reads and writes is read off its source … a name the module does not spell is refused"). **Sources:** [3] lines 3131–3135, 3015–3022. **Support:** direct. **Confidence:** high.
9. **Claim (the bound's limit):** `$.fs` is not scoped to the plugin or the project — "The file system as the engine's own process reaches it; a relative path is under the session's working directory… **An absolute path is used as given; where one may go is an `fs.*` hook's to say.**" `$.process.run` "Runs a command on the host by its argument vector (no shell)". **Sources:** [3] lines 2743–2750, 2973–2985. **Support:** direct. **Confidence:** high.
10. **Claim:** that reading is confirmed by an independent, non-vendor test: a mod reading `~/.claude/.credentials.json` and `history.jsonl` and POSTing both out — "Both reads succeed. `$.fs.read` is **not scoped to your project or your session**. An absolute path is used as given… No prompt appeared. No permission was asked." Tested at v2.1.274, article dated 2026-09-22. **Sources:** [5]. **Support:** direct (their run). **Confidence:** medium-high — the *scoping* fact agrees with vendor source [3]; the version tested predates default-on at 2.1.287, so re-test on a current build is warranted ([8]).
11. **Claim (what the scan cannot see):** the `calls:`/`hooks:` list is a lower bound on effect because a mod's cheapest lever costs no `$` call at all — "two hooks working together — one rewriting the command that executes, one rewriting what the transcript displays — can make what ran and what you saw diverge completely, using zero `$` calls. The capability scanner that only watches `$` sees a mod that does nothing." **Sources:** [6] (independent commentary, 2026-10-03). **Support:** interpretation by a third party. **Confidence:** medium — it follows from the API shape (`next(e)` takes a changed event; `prompt.section`/`prompt.compose`/`tool.call`/`session.append` all rewrite) and nothing in [3] contradicts it, but I did not run it.
12. **Claim:** provenance is host-set and not plugin-writable: `next.origin` is "Set by the host alone, from the environment the call came from (its own MessagePort) and that plugin's seat; nothing a plugin writes reaches it." **Sources:** [3] lines 5298–5305. **Support:** direct. **Confidence:** high.
13. **Claim:** authority is ordered in the host, not by the guard mod alone: `TIERS = ["prepend","user","append","builtin","core"]`, "earlier is outer is more authority"; and `next.to` "never skips a tier with more authority, so no user hook skips the org's." **Sources:** [3] lines 9941–9958, 5265–5275. **Support:** direct. **Confidence:** high. **Researcher inference:** this is the structural reason the org tier wins — the guard mod *uses* an ordering the host enforces; the ordering is not the guard's own invention.

### 3. The gate is a mod, and it fails open by default

14. **Claim:** `plugin.register` is judged by a mod (the shipped `sec-default`), and the log shows that adjudication: "`plugin.register: my-mod (user, my-mod@inline), judged by cc-plugin-sec-default: admitted`". **Sources:** [7] (third-party probe log at 2.1.286), corroborated by the adapter in [2] `mods/sec-default/hooks/register.ts`. **Support:** direct (their log). **Confidence:** medium-high.
15. **Claim:** the shipped guard's own source keys its `plugin.register` hook on tier and policy and **never reads `e.uses`**: `on('plugin.register', { tier: 'user' }, …)` → `Policy.isManagedModsOnly(await $.settings.read(Policy.SOURCE)) ? { refuse: managedModsOnlyRefusal(e.name) } : next(e)`, with `.catch` → `next.called ? next(e) : { refuse: … }` (fail closed). **Sources:** [2] `mods/sec-default/hooks/register.ts` lines 209–219 (read at HEAD). **Support:** direct. **Confidence:** high. **Consequence (inference):** blocking a *call* by its scanned name is opt-in — the vendor guard does it for env variables and tool names, not for `process.run`/`http.fetch`; the documented `calls:`-based refusal is an example policy mod ([9] admin §"enforce a policy with a mod of your own").
16. **Claim:** a policy hook that throws fails **open**, by vendor statement: "If your `plugin.register` hook throws or exceeds its time limit, Claude Code skips the hook, so the check fails open and the mod it was checking loads." Independently reproduced for a `tool.call` guard: a 15 s hook was cut at the 10 s budget and "`echo hi` ran anyway". **Sources:** [9], [10]. **Support:** direct. **Confidence:** high (two independent statements).

### 4. `environment 2`

17. **Claim:** the token appears once, in the debug-log example, with no explanation: "`hooks module first-mod@inline loaded (worker, environment 2, tier user); events: …`". **Sources:** [11] (fetched text, log example under "Read the debug log"). **Support:** direct. **Confidence:** high (that it is unexplained).
18. **Claim:** it is **not** in the declarations — a full-text scan of the 13,440-line `claude-code.d.ts` finds no `environment <n>` token, no `apiVersion`/`engines`/`environment` field on `PluginRegisterInput` or `PluginSpec`, and no version field except the manifest's `version?: string` and `$.session.version()`. **Sources:** [3] (`grep -n` over the file; `PluginRegisterInput` at 6225–6259). **Support:** direct. **Confidence:** high.
19. **Claim:** it is **not** in the changelog either — `grep -i "environment 2"` over `CHANGELOG.md` (1,121,848 bytes, entries to 2.1.314) returns nothing; nor does `hooks module` paired with any environment number. **Sources:** [4]. **Support:** direct. **Confidence:** high.
20. **Claim (best available reading):** it is a per-plugin execution-environment ordinal inside one shared worker. A third party probing 2.1.286/2.1.287 logged built-ins loading `native, environment 1`, then `hooks worker spawned (one for every plugin)`, then user mods at `environment 2` and `environment 3`: "Installed mods share one worker thread, and each plugin gets its own numbered environment inside it." **Sources:** [7] (anatomy page, quoted log block). **Support:** interpretation from log lines by a non-vendor author. **Confidence:** medium — it is the only explanation in the corpus that fits both the `native`/`worker` split and the numbering, but I did not reproduce it, and the log line's own wording ("one for every plugin") is what the author says he first read *wrong*.

## Conflicts
- **"One worker" vs "its own MessagePort".** Anthropic's prose: "Installed mods share one worker thread." The declarations describe per-plugin handles ("stays in the plugin's own environment under `press.handle`", `next.origin` "from the environment the call came from (its own MessagePort)"). The vendor's own log line says "hooks worker spawned (one for every plugin)", which [7] says he first read as one worker *per* plugin. Resolution consistent with all three: one worker thread, several isolated contexts handing messages over ports — but no vendor sentence states that, so I record it unresolved.
- **"The validator is a gate" vs "the validator is a report".** [9] and [3] say the engine refuses what the scan cannot read. [5] says the scan's *output* never reaches the user at install time ("`plugin details` … 'Hooks (0)'"). Both true: load-time refusal is real, disclosure is absent. A reader who takes either alone gets the trust model wrong.
- **The guard protects the host vs the guard protects managed configuration.** Unchanged from the first-round note, and now sharper: [2] shows `sec-default`'s `plugin.register` refuses only under `allowManagedModsOnly`; the fail-closed property is its own `.catch`, not a runtime invariant, and [9] confirms any *other* policy mod fails open.
- **Freshness.** [5] tested v2.1.274 while mods sat behind `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`; [8] dates default-on to 2.1.287 (2026-10-01), and today's head is 2.1.314. The `plugin details` blindness may have been fixed since; the changelog through 2.1.314 has no entry naming it (the nearby fixes are component-count and MCP-count bugs), so I record it as *reported at 2.1.274, not contradicted through 2.1.314* rather than as a current fact.

## Unanswered
- **The scanner's implementation is unreadable, so "exact" is a claim, not a proof, and there is still no independent evasion benchmark.** What exists is [5] (reach + disclosure, not evasion) and the changelog's own list of analyser bugs — `validate` once "listing a matcher or state value for a hooks module that the engine reads from elsewhere", once refusing a module "over a rebound top-level `var`", once refusing "a hooks module that destructures an option named like one of its top-level functions", and a module "makes many `$.state` calls through one const taking minutes to load or validate" [4]. These are analyser correctness and cost failures inside one release cycle; none is a documented evasion.
- **`environment 2` is not defined by any vendor source I can reach.** [7] is the only explanation in the corpus and is third-party and unreproduced. Until someone runs two probe mods on 2.1.314 and reads the log, treat it as an opaque per-plugin environment ordinal *and not as a version*.
- **Whether an event-rewriting mod can be bounded at all.** No source, vendor or otherwise, shows a mechanism that constrains what a mod does through `next(e)` beyond tier order and the guard's own hooks — the scan cannot see it ([6]), and [3] gives no per-event field whitelist.
- **Whether the shipped types (2.1.277) match the shipped binary (2.1.314).** Unverifiable without running `/plugin-types` against a current build.
- **Line-count growth of the surface** — 11,783 lines at 2.1.272 per [10] versus 13,440 at HEAD per [3] — is *consistent with* additive-only drift, but the two counts came from different generators/versions and I did not diff the surfaces.
