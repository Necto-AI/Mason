# 3. Qwen 3.8 27B on its own terms

Everything here is from the model card and the chat template Qwen ships with it, unless marked otherwise. These are the
properties a harness either respects or fights. <https://huggingface.co/Qwen/Qwen3.8-27B>

## §1 What it is

- **Dense 27B**, causal LM with a **vision encoder** — a native vision-language model, not a text model with an OCR
  step bolted on. Built on Qwen 3.5.
- Layout is hybrid: `16 × (3 × (Gated DeltaNet → FFN) → 1 × (Gated Attention → FFN))`, 64 layers, hidden 5120, FFN
  intermediate 17,408, MTP-trained. **[documented]**
- Context **262,144 native**, extensible to 1,000,000 with YaRN. YaRN static scaling "potentially impacts performance
  on shorter texts" — so it is a mode, not a free upgrade. **[documented]**
- Qwen's own agentic benchmarks for this model were run **in the Claude Code harness** (WebArena-Verified on the OSWorld
  scaffold), and the card only says "broader support for popular harnesses and development tools" otherwise. **[documented]**

The dense/hybrid choice is the one to internalize: prefill is compute-bound and scales with all 27B, generation is
memory-bandwidth-bound. On a local box that makes **prompt processing the bottleneck for an agent loop**, and it makes
prefix reuse worth more than any prompt trick. **[inference]**

## §2 Thinking is on by default and it is preserved across turns

- Thinking mode is on, emitting ` thinking…</think>`. Disable per request with `chat_template_kwargs:
  {"enable_thinking": false}`. **[documented]**
- `reasoning_effort` is `xhigh` (default), `medium`, `low`. In the shipped template this is a plain paragraph of text
  prepended inside the system message — not a mode, not a token budget. **[documented, from the template]**
- `preserve_thinking` is **true by default**. Qwen's stated reason: "especially beneficial for agent scenarios" —
  decision consistency, less redundant reasoning, and **better KV-cache utilization**. **[documented]**
- What the template actually does when `preserve_thinking` is false: it keeps `reasoning_content` only for messages
  *after the last user query*. So the current turn's tool-loop keeps its thinking, and prior turns' thinking is dropped.

This is the single most consequential context decision for an agent loop on this model. With preservation on, every
assistant turn in the trajectory carries its reasoning tokens forever; a 20-step agent turn produces a prefill that is
mostly old thinking. With it off, the trajectory is roughly the final answers plus the current turn's reasoning.
**[inference]**

Qwen recommends on. Their claim (cache utilization, decision consistency) is about the server-side prefix cache, which
is a different regime than one machine with one user. There is no published ablation either way. This needs measuring,
not choosing from the card.

## §3 Sampling, and the warning Qwen wrote down

| Mode | temp | top_p | top_k | min_p | presence | repetition |
|---|---|---|---|---|---|---|
| Thinking | 1.0 | 0.95 | 20 | 0.0 | 0.0 | 1.0 |
| Non-thinking | 0.7 | 0.80 | 20 | 0.0 | **1.5** | 1.0 |

`presence_penalty` between 0 and 2 reduces endless repetition, and higher values "may occasionally result in language
mixing and a slight decrease in model performance". Note that the non-thinking default is already 1.5 — the model ships
expecting repetition pressure. A harness that overrides sampling to "agent defaults" (temp 0.2) is outside the
configuration Qwen tuned, and there is no published evidence for it either way. **[documented]**

The card's own caveat, verbatim in substance: **in multi-turn agentic tasks, lower `reasoning_effort` does not always
reduce overall task completion time; it may cause insufficient analysis, more failures, retries, and higher total
latency and token use.** **[documented]**

That is the same non-monotonicity HAL measured across 9 models (`01` §6), stated by the vendor about this model. Neither
"turn thinking up" nor "turn thinking down" is a safe default.

Output budgets for agentic use: reasoning max **262,144** tokens, final response max **131,072**, within a 1M context.
On local hardware those are hours. They are ceilings, not targets.

## §4 The tool-call dialect is XML, and the schemas are system prefill

The shipped template injects your tool list into the **system message** as JSON, one `tojson` per tool, under a `# Tools`
heading, and then instructs:

```
If you choose to call a function ONLY reply in the following format with NO suffix:

<tool_call>
<function=example_function_name>
<parameter=example_parameter_1>
value_1
<parameter=example_parameter_2>
...
</tool_call>
```

with the reminders: required parameters must be present; you may give optional natural-language reasoning **before** the
call but **not after**; if no function applies, answer normally and do not mention function calls. **[documented, from
the template]**

Three consequences:

1. **A harness that parses JSON tool-call blocks will drop every call.** Mingbird's format-rescue mechanism (`02` §3) is
   the answer to this class of problem generally; a harness that hard-codes one dialect is the failure it exists to
   prevent.
2. **The tool list is prefill, not a separate field.** N tools cost N JSON schemas on every request, inside the system
   message, before the conversation. Tool count and prompt size are the same budget on this model — which is why the
   tool-count findings in `02` §6 hit harder here than on an API model that bills tools separately or caches them
   server-side.
3. **`tojson` of the schema means description length is paid verbatim.** A 200-token description times 30 tools is
   6,000 tokens of prefill on every single step of the loop.

## §5 The cache is the performance model

Two facts, one documented and one in a neighbouring project's docs:

- Qwen's card: preserved thinking improves "KV cache utilization" — they are thinking about prefix reuse as a first-class
  concern. **[documented]**
- Pi's llama.cpp guide: "Hybrid models such as Qwen3.5 cannot rewind a partially cached prompt without context
  checkpoints. If each question reprocesses the whole state, start the router with `--ctx-checkpoints 32
  --checkpoint-min-step 0`." Qwen 3.8 is built on 3.5 and uses the same hybrid DeltaNet/Gated-Attention layout.
  **[documented for 3.5; inference for 3.8]** <https://raw.githubusercontent.com/badlogic/pi-mono/main/packages/coding-agent/docs/llama-cpp.md>
- Same page: "Context is shared across parallel server slots." **[documented]**

So on one machine: `--jinja` for tool calling, `--ctx-checkpoints` for a hybrid model, and a prompt that is
**append-only and byte-stable at the front**. Anything that rewrites the front of the prompt — a re-rendered profile, a
re-sorted tool list, a compaction summary, a skill index that changed — reprocesses the whole prefix. On a dense 27B
that is the difference between a turn that starts generating in a second and one that starts in half a minute.
**[inference]**

And parallel subagents are not parallel: N children share one context across slots and evict each other's checkpoints.
A fan-out design that is free against an API is a serial queue with cache thrash here. **[inference, from the two
documented facts]**

## §6 Quantization: what is actually known

The evidence is thin and mostly about smaller models, so treat this as a list of failure signatures to watch for rather
than a recommendation:

- Q4_K_M costs about **1.4 points of tool-calling reliability on an 8B** (0.933 → 0.919 in Docker's test) and under
  ~1.5% on task benchmarks; stepping to Q6 or Q8 is the reported fix when schema violations appear. **[measured,
  secondary]** <https://runaihome.com/blog/quantization-q4-q5-q6-q8-quality-loss-2026/>
- "Quantization error accumulates across long reasoning chains — a small token probability shift early in a chain can
  route the model to a wrong step." Same source. Which is exactly the shape of an agent trajectory, and exactly what no
  published agentic benchmark has quantified for this model. **[inference]**
- KV cache at `-ctk q8_0 -ctv q8_0` roughly halves cache memory "with minimal quality impact" per the same source — on a
  hybrid model already prone to cache trouble, that is a compounding risk, not a free win. **[inference]**

Given the card's note that Qwen recommends SGLang, vLLM or TokenSpeed for production serving, the GGUF-on-one-machine
path is a regime the vendor did not tune for. Whatever harness ships should be measurable under two quants cheaply.

## §7 The practical ceiling nobody states in the card

Perplexity measured it and said so: the model advertises 260K, and "we found empirically that they begin to struggle
beyond 100K tokens". **[vendor claim]** They built their entire harness around that — minimal prompt, deferred skills,
compaction.

Nothing in the card contradicts that, and the architecture argues for it: hybrid attention with a DeltaNet recurrence is
built to make long context *affordable*, not to make a model attend to it as sharply as a dense full-attention
transformer of the same width. **[inference]**

The working budget for a 27B agent loop, on the evidence available: keep the steady-state prompt under ~30K, compact
before 100K, and treat anything past that as degradation you will not see in an error message.
