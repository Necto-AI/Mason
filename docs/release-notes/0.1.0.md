# mason 0.1.0

The first public release of mason: an agent runtime for building, connecting and running AI agents on a machine you
control. This is a **developer preview**. Expect breaking changes before 1.0.

## What it does

One process per bot, one owner per bot. mason keeps everything a bot is in one home — `$MASON_HOME`, else `~/.mason` —
and a person speaks to it through a connector. In this release that connector is the terminal.

```sh
npm install -g mason-agent
mason onboard            # provider, model, key verified with one completion, the first bot, its connector
mason up                 # serve it
mason chat               # a conversation in this terminal
```

## Prerequisites

- **Node.js 26.4.0 or newer.** One floor for the runtime, the CLI, the onboarding wizard and the TUI. The onboarding
  renderer loads its native half through `node:ffi`, which does not exist below 26.4. mason refuses to start on an older
  Node and says so, rather than failing inside a dependency.
- **npm 11.**
- A model provider to point it at, or the offline provider (`PI_FAUX_MODEL=1`) for a deterministic local run with no key
  and no network.
- Optional: **podman** if you install a connector that runs as a container. None ship in this release.

## Supported platforms

Linux x64 is what every release check runs on, and the platform the deployment image targets. macOS and Windows are
neither tested nor claimed: `node:ffi` and the renderer need to be proven there before this file says they work.

## Connectors in this release

One: **the console**, built in. `mason chat` opens the same socket every other connector opens, so the protocol path is
the one a person uses.

Telegram is **not** in this release. Its image is unpublished, so the catalog ships empty rather than offering a
connector that cannot pull; `mason setup` names a failed pull as a failed pull and does not record an install that did
not happen. Telegram comes back in 0.1.1, with the transcription service that fed it replaced by a skill over a local
binary rather than a service in the stack.

## Known limitations

- **No web UI.** There is no panel, no roster, no browser client. A person speaks through a connector.
- **One owner per bot.** The actor a connector's grant names is the only person whose words are the owner's; anybody
  else's are refused.
- **Single host.** No clustering, no remote execution, no multi-tenant story.
- **Configuration is JSON on disk.** `mason onboard` writes it, `mason doctor` checks it, and you should not need to
  hand-edit it — but you can, and a mistake there is yours to find.
- **No stable API.** The connector protocol, the CLI flags and the home layout may change in a minor release.
- **Not audited.** This is a preview from one maintainer. Read the source before you run it against anything you care
  about.
