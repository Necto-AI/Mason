# mason 0.1.0

The first public release of mason: an agent runtime for building, connecting and running AI agents on a machine you
control. This is a **developer preview**. Expect breaking changes before 1.0.

## What it does

One process per bot, one owner per bot. mason keeps everything a bot is in one home — `$MASON_ROOT`, else `~/.mason` —
and a person speaks to it through a connector. In this release that connector is the console, in this terminal.

```sh
npm install -g mason-agent
mason init --provider <id> --model <id> --key <key>   # the key is verified with one completion before it is written
mason new bot                                         # the home: soul, profile, skills, the console grant, then a doctor
mason up                                              # serve the bot
mason chat                                            # a conversation in this terminal
```

The first run is flags and nothing prompts: a script and a person take the same path, and a second `mason init` asks
nothing and reports what is already there.

## Prerequisites

- **Node.js 26.4.0 or newer.** One floor for everything — the runtime, the CLI and the connector SDK. mason runs its
  TypeScript from source and keeps a bot's state in `node:sqlite`, so there is no second version to check, and mason
  refuses to start on an older Node with a sentence rather than failing inside a dependency.
- **npm 11.**
- A model provider to point it at, or the offline provider (`PI_FAUX_MODEL=1`) for a deterministic local run with no key
  and no network.

Nothing else: no database server, no container runtime, no queue. mason is one Node process and one directory.

## The three packages

One commit and one tag ship three npm packages:

- **`mason-agent`** — the runtime and the `mason` command.
- **`mason-protocol`** — the connector protocol, major 1: one Chord contract, `mason.peer`, and the shapes it carries.
- **`mason-connector`** — the TypeScript SDK for a connector in another process: the Chord host, the durable journal,
  the conversation it holds, attachments, and a conformance suite measured against a fake mason.

## Installing with Nix

The repository is a flake, built against Node 26 and patched for NixOS: `pi-env`'s prebuilt daemon and the X11 helper
`pi-coding-agent` pulls in are linked the way a Nix system can load them.

```sh
nix run github:DenisSud/mason
nix profile install github:DenisSud/mason
nix develop          # the same toolchain CI uses
```

## Supported platforms

Linux x64 is what every release check runs on, and the only system the flake builds for. macOS and Windows are neither
tested nor claimed.

## Connectors in this release

One: **the console**, built in. `mason chat` opens the same socket every other connector opens, so the protocol path is
the one a person uses.

Telegram is **not** in this release. It returns as an external process on the SDK, in its own repository, and it will
hold no `user` grant: a person's words reach this bot from the console, and a connector that is not the console reports
events and lends tools. A home that grants a person's words to two enabled connectors refuses the boot, with the rule in
the sentence.

## Known limitations

- **No web UI.** There is no panel, no roster, no browser client. A person speaks through a connector.
- **One bot per environment.** A root holds one bot: a second `mason new` refuses, naming the bot that is there.
- **One owner per bot.** The actor a connector's grant names is the only person whose words are the owner's; anybody
  else's are refused.
- **Single host.** No clustering, no remote execution, no multi-tenant story.
- **Configuration is JSON on disk.** `mason init` and `mason new` write it, `mason doctor` checks it, and you should not
  need to hand-edit it — but you can, and a mistake there is yours to find.
- **No stable API.** The connector protocol, the CLI flags and the home layout may change in a minor release.
- **Not audited.** This is a preview from one maintainer. Read the source before you run it against anything you care
  about.
